## Phase Details

### Phase 9: Filter Foundation
**Goal**: The shared filter store and SQL utilities are in place such that any chart or renderer can safely add, replace, and clear equality filters per table, and re-query with the correct WHERE clause injected.
**Depends on**: Phase 8 (v1.1 complete; Zustand store-reset shim exists; `useApiQuery` hook exists)
**Requirements**: FILT-01, FILT-02, FILT-03
**Success Criteria** (what must be TRUE):
  1. Adding a filter for table A does not affect any chart subscribed to table B (table-keyed isolation verified by test)
  2. Clicking a value on the same column twice results in exactly one active filter for that column — the second click replaces the first (last-click-wins, confirmed by a test asserting filter count = 1)
  3. Clicking a value containing a single quote (e.g., `O'Brien`) produces a correctly escaped SQL clause (`col = 'O''Brien'`) with no server error
  4. Clearing all filters for a table triggers a chart re-fetch that fires a new network request (confirmed by test: add filter → assert fetch; clear → assert another fetch fires)
  5. An in-flight SQL request is cancelled when the filter changes before the response arrives (AbortController confirmed by test: second filter add → first fetch aborted)

**Plans**: TBD

**Canonical references for planning:**
- PITFALL D-02: `escapeKineticaStringLiteral` is the ONLY sanctioned interpolation path — no raw string concatenation of user values into SQL
- PITFALL D-03: `column = NULL` must be silently rewritten to `column IS NULL` in the filter builder
- PITFALL D-04: 10-filter cap per table enforced at `addFilter` write time — never silently drop; warn user
- PITFALL D-05: `addFilter` REPLACES existing filter on same column — test `region=EAST` then `region=WEST` yields exactly one filter
- PITFALL C-02: Use `useFilterStore(state => state.filters[tableId] ?? [])` selector — NOT `state.filters` — to prevent O(N) re-renders across tables
- PITFALL C-04: Store shape MUST be `Record<number, ActiveFilter[]>` keyed by `tableId` from day one — flat array is an unacceptable shortcut (retrofit cost is very high)
- PITFALL S-01: Filter state lives in `useFilterStore` ONLY — no `useState` shadow copies in chart components
- PITFALL S-02: Use `filterVersion: number` counter (increments on every add/remove/clear) as a primitive dep for `useEffect` — prevents the "clear is a no-op" bug where an empty array reference appears stable
- PITFALL S-03: New filter store spec file MUST run under the same `vitest.config.ts` as `src/test/setup.ts` so the Zustand store-reset shim covers it — add a canary test confirming store is empty at the start of each test
- AP-1: Filter state NEVER lives on a chart component — only in `useFilterStore`
- AP-3: EVERY user-clicked value flowing into SQL goes through `escapeKineticaStringLiteral` — no exceptions
- AP-4: Store filter state as `Record<number, ActiveFilter[]>` from day one — NOT a flat array

### Phase 10: Existing-Chart Drill-Down
**Goal**: Users can click any element on a bar, line, pie, scatter, or table chart and have that click add an equality filter to the dashboard's shared filter store — causing every other chart on the same table to re-query with the updated WHERE clause — with visual confirmation on both the clicked element and the filter bar.
**Depends on**: Phase 9 (filter store + SQL utilities exist)
**Requirements**: DRILL-01, DRILL-02, DRILL-03, DRILL-04
**Success Criteria** (what must be TRUE):
  1. Clicking a bar segment (or pie slice, line point, scatter point, or table row) on any aggregated chart adds a visible filter chip to the filter bar and triggers a re-fetch on every other chart sharing the same table
  2. The clicked chart element shows a "selected" highlight state (e.g., dimmed peers, bordered active segment) that persists until the filter is cleared
  3. Each active filter chip has an "×" dismiss button that removes only that filter and triggers a re-fetch; a "Clear all" button removes every filter for that table
  4. Geometry-typed columns (WKT, WKB, Kinetica geometry) and large-text columns are absent from the drill-down column picker in the chart config panel — only low-cardinality-safe column types are selectable
  5. A toast notification appears confirming the filter that was added (format: `column = 'value'`)

**Plans:** 4/4 plans complete

**Canonical references for planning:**
- Per-chart-type click contracts: ARCHITECTURE.md section 6 (table mapping bar/line/pie/scatter/table click events to `onDrillDown` payload)
- Geometry/large-text column exclusion from drill-down picker (PITFALL D-01)
- Deduplicate identical filter adds: if `{column, value}` already exists, `addFilter` is a no-op (EC-3 from FEATURES.md)
- AbortController on `AggregatedWidgetRenderer` SQL fetch (wired here alongside filter subscription)
- `runSql` gains `signal` param for AbortController support (one-line change to `src/api/client.ts`)
- Stale-data contract: on filter change, clear `data` to `null` before new fetch — show loading state, not stale data (PITFALL C-03)
- AP-1: Filter state lives in `useFilterStore` only — `WidgetRenderer` reads via selector, never props
- AP-3: `escapeKineticaStringLiteral` called on every value that flows from chart click into SQL
- AP-4: `tableId` stored in `widget.config.tableId` at config-save time — renderers read it directly, no runtime lookup

### Phase 11: Map Chart
**Goal**: Users can add a map chart widget to a dashboard, configure its spatial column mode and WMS render mode, see Kinetica WMS tiles rendered on an OpenLayers basemap, and have the map tiles automatically invalidate and refetch when any filter for the map's table changes.
**Depends on**: Phase 10 (filter store + drill-down pipeline proven on existing chart types)
**Requirements**: MAP-01, MAP-02, MAP-03, MAP-04, FILT-04
**Success Criteria** (what must be TRUE):
  1. A map chart can be added to a dashboard and configured with lat/lon pair columns, a WKT geometry column, or a Kinetica native WKB geometry column — the map renders visible Kinetica WMS tiles in the correct geographic position overlaid on the basemap
  2. All four render modes (raster, heatmap, classbreak, contour) are selectable at config time; switching render mode updates the tile display without remounting the map or losing the current pan/zoom position
  3. When a filter is active for the map's table (applied from any chart on that table), the map's WMS tiles immediately invalidate and refetch reflecting the filtered dataset — no stale tiles remain visible
  4. The map component cleans up completely on unmount (no memory leak, no duplicate tile requests, no stale DOM listeners) — verified by navigating away from a dashboard with a map and back
  5. After a filter changes, no browser-cached WMS tile from the previous filter state is served (`Cache-Control: no-store` on `/api/wms` proxy responses confirmed in Network tab)

### Phase 12: Dashboard Layers Panel
**Goal**: Users can manage a dashboard-scope collection of `KineticaWms` layers via a new "Layers" toolbar modal — adding, configuring (spatial mode, render mode, render-mode params, classbreak builder, opacity), reordering, duplicating, and removing layers — and each map widget on the dashboard renders any chosen subset of those layers as N stacked OpenLayers ImageWMS layers, with per-layer filter subscriptions, persisted in a new SQLite `dashboard_layers` table, while Phase 11 single-WMS map widgets become inert with a reconfigure overlay (hard cutover).
**Depends on**: Phase 11 (map widget pattern, OL ImageWMS lifecycle, WMS URL builder, capabilities store)
**Requirements**: LAYER-01-backend-schema, LAYER-02-backend-crud, LAYER-03-form-extraction, LAYER-04-bbox-deletion, LAYER-05-frontend-client, LAYER-06-frontend-store, LAYER-07-modal-shell, LAYER-08-modal-interactions, LAYER-09-css-tokens, LAYER-10-renderer-n-stack, LAYER-11-config-shrink, LAYER-12-old-config-cutover, LAYER-13-integration-verify
**Success Criteria** (what must be TRUE):
  1. Layer CRUD via the modal works end-to-end: create, edit (auto-save 300ms debounce), reorder via drag, duplicate, delete with inline confirm, missing-table badge — all backed by the new `dashboard_layers` SQLite table and `/api/dashboards/:id/layers[/:layerId|/reorder]` Express routes
  2. A map widget renders N stacked ImageWMS layers (one per included dashboard layer), ordered by `dashboard_layers.position`; the layer-inclusion picker (multi-select on `widget.config.includedLayerIds`) toggles which layers a widget shows; multiple map widgets on the same dashboard render the same layer order independently
  3. Per-layer filter subscription preserves M-01/M-02 locks: applying a drill-down filter to table T's chart causes only the layer(s) bound to T to refetch tiles via `imageWmsSource.updateParams({ QUERY, _v: filterVersion })`; unrelated layers do not need a content refetch; the OL Map instance is never disposed (zoom/pan retained)
  4. Hard cutover for Phase 11 map widgets: any widget with the old single-WMS config shape (`spatialMode` set + `includedLayerIds` undefined) renders the `.widget-map-reconfigure` overlay with the verbatim UI-SPEC copy; no auto-migration; `bboxHelper.ts` + zoom-to-data button deleted as dead code
  5. Missing-table state: when a layer's `table_id` is no longer in the dashboard's `dashboard_tables` join, the layer survives (no auto-delete), the layer row shows the red `Table removed — reconfigure` badge, and map widgets skip rendering that layer (no WMS request fired)
