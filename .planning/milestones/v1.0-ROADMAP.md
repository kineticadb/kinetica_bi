# Roadmap: Kinetica BI

## Overview

Milestone v1.0 — Authentication & Per-User Access — replaces the shared admin Kinetica credentials with per-user passthrough. Three phases ship the milestone end-to-end: Phase 1 lays the keystone (encrypted server-side session store carrying the user's Kinetica password between requests), Phase 2 routes every Kinetica call through the user's credentials (the milestone's headline behavior), and Phase 3 closes the loop with mid-session re-login UX and removal of the admin env vars.

Each phase is independently shippable: after Phase 1 nothing user-visible changes but `req.user.creds` is available; after Phase 2 the milestone goal is functionally met (Kinetica permissions enforced per user); after Phase 3 the env-var fallback is gone and auth-failure UX is clean.

## Phase Details

### Phase 1: Encrypted server-side session store
**Goal**: After login, the server can decrypt the user's Kinetica password on every authenticated request without changing any user-visible behavior; the cookie carries no credential material.
**Depends on**: Nothing (first phase)
**Requirements**: SESS-01, SESS-02, SESS-03, SESS-04, SESS-05
**Success Criteria** (what must be TRUE):
  1. After login, querying the `sessions` table in `kinetica.db` shows a row with `username`, `ciphertext`, `iv`, `auth_tag`, and `expires_at` — the password is NOT recoverable from the cookie alone.
  2. Decoding the JWT cookie payload (e.g., `jwt.io` or `cut -d. -f2 | base64 -d`) shows only `{ sub, sid, ... }` and contains no plaintext password or anything reversible to one.
  3. Hitting `POST /api/auth/logout` removes the corresponding `sessions` row immediately (verified via `sqlite3 kinetica.db "SELECT * FROM sessions WHERE sid = ?"` returning empty), and replaying the old cookie afterwards returns 401.
  4. `GET /api/auth/me` returns 401 (not 200) when the session row has been deleted out-of-band, even though the cookie is still cryptographically valid.
  5. After 8 hours, expired session rows are cleaned up by a GC sweep — the `sessions` table never grows past the count of active (non-expired) sessions.

### Phase 2: Per-user credential passthrough on every Kinetica call
**Goal**: Every downstream Kinetica request authenticates as the BI user who initiated it; Kinetica's per-user permissions become the only authorization boundary the app respects.
**Depends on**: Phase 1
**Requirements**: CRED-01, CRED-02, CRED-03, CRED-04, CRED-05, CRED-06, OBS-01
**Success Criteria** (what must be TRUE):
  1. A user with restricted Kinetica permissions logs in and sees only the schemas, tables, and columns that user is granted — admin-only schemas/tables disappear from the discovery UI.
  2. A user without SELECT permission on table X who runs a SQL query targeting X via `POST /api/sql` gets back the Kinetica permission error (not silently elevated admin results).
  3. `git grep -n "kineticaUser\|kineticaPassword\|Buffer\.from(\`\${" kinetica_bi/server/src/index.ts` returns zero matches — every Kinetica call site now goes through `kineticaCall`.
  4. Every Kinetica call (SQL proxy, schemas/tables/columns, materialize, WMS) emits one server log line containing `username`, route/operation, and outcome (`success` / `auth-fail` / `upstream-error`) — no credentials, no full SQL bodies.
  5. View materialization, schema/table/column discovery, and the WMS proxy continue to work for an admin-equivalent user — no functional regression on existing flows.

### Phase 3: Auth failure UX + admin credential removal
**Goal**: Mid-session Kinetica auth failures return the user cleanly to the login screen; permission failures (403) stay inline; the shared admin env vars are gone everywhere.
**Depends on**: Phase 2
**Requirements**: ADMN-01, ADMN-02, ADMN-03, ADMN-04, UX-01, UX-02, UX-03
**Success Criteria** (what must be TRUE):
  1. Rotating a logged-in user's Kinetica password externally — on the next API call the BI app drops the user back to the login screen with a "your session has ended, please sign in again" message (not a stack trace, not a stuck spinner, not a raw 401 toast).
  2. A logged-in user clicking on a widget backed by a table they lack SELECT permission on sees an inline permission error on that widget — they are NOT logged out and can continue using other parts of the dashboard.
  3. Inspecting network responses: mid-session auth failure returns HTTP 401 with body `{ error: ..., code: "REAUTH_REQUIRED" }`; permission denial returns HTTP 403 (no `REAUTH_REQUIRED` code) — the frontend dispatches on the code, not just status.
  4. Starting the server with `unset KINETICA_USERNAME KINETICA_PASSWORD` succeeds — every authenticated route still serves the logged-in user's data with no "Missing KINETICA_USERNAME..." 500s.
  5. `git grep -rn "KINETICA_USERNAME\|KINETICA_PASSWORD"` across the entire repo (including `.env.example`, deployment docs, any sibling scripts) returns zero matches outside of intentional historical references (e.g., changelog).
