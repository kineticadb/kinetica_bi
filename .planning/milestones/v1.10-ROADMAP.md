## v1.10 Per-Dashboard View Permissions

**Goal:** Layer per-dashboard VIEW access control on top of the global `dashboards:view` permission — analysts see/open only the dashboards they have been granted (by user and/or role), admin + designer bypass to see/open all, newly created dashboards are private-by-default, enforced server-authoritatively at both list and open. Extends the v1.8 RBAC system; intentionally revises the v1.8 "shared workspace — no dashboard ownership" decision. App-level visibility layer only — Kinetica per-user credentials remain the data-access authority.

### Phases

- [x] **Phase 55: Access Model & Server Enforcement** - Grant schema + 17th permission + view resolver + server-authoritative list-filter, open-gating, grant CRUD, and audit (completed 2026-06-09)
- [x] **Phase 56: Access-Management UI & List/Open UX** - Access panel (user + role grants), `manage_access` UI gating, filtered list view, and "no access" direct-nav state (completed 2026-06-09)
- [x] **Phase 57: Verification & Live UAT** - Live operator walk-through of grant/revoke + analyst restriction + bypass, automated gates green (completed 2026-06-10)

### Phase Details

### Phase 55: Access Model & Server Enforcement
**Goal**: Per-dashboard view access is fully modeled and enforced server-side — the server is the single authority for which dashboards a user can list, open, and load data for.
**Depends on**: Nothing new (builds on the shipped v1.8 RBAC system — `permissions.ts` catalog, `rbac_seed_history`, `getEffectivePermissions`, `requirePermission`, `emitRbacAudit`, and the existing `dashboards` table).
**Requirements**: ACCESS-V110-01, ACCESS-V110-02, ACCESS-V110-03, ACCESS-V110-04, ENFORCE-V110-01, ENFORCE-V110-02, ENFORCE-V110-03, ENFORCE-V110-04
**Success Criteria** (what must be TRUE):
  1. A new `dashboards:manage_access` permission appears in the catalog as the 17th entry, is default-mapped to `admin` and `designer`, and seeds exactly once via `rbac_seed_history` (an operator who removes the default mapping still has it removed after a restart; the new permission is not re-seeded).
  2. A new app-local grant table persists a dashboard's view-access to specific users (lowercased username) and/or roles, keyed by dashboard + grantee; deleting a dashboard cascades away its grants.
  3. A server resolver (`canViewDashboard`) returns true for `admin`/`designer` (bypass), for a matching direct user grant, or for a grant held via ANY of the user's roles (union semantics mirroring `getEffectivePermissions`); a freshly created dashboard with no grants resolves viewable only for bypass roles.
  4. `GET /api/dashboards` returns only the dashboards the requester may view (bypass receives all; everyone else receives only granted ones) — filtered server-side, not client-side; and a non-permitted user receives 403/404 on `GET /api/dashboards/:id` and its scoped data routes (widgets, tables, layers, dynamic-views, views).
  5. Grant list/add/remove routes are gated by `dashboards:manage_access`, and every add/remove is recorded via the existing dual-sink (`rbac_audit` row + OBS-1 log line) consistent with v1.8 mutation auditing.
  6. New enforcement is covered by supertests; server `tsc` stays clean and the server vitest set-based gate holds (failing files ⊆ the TD-V16-TEST-ISOLATION known-flaky list — never a fixed pass-count).
**Plans**: 2 plans
- [ ] 55-01-PLAN.md — Access model: 17th permission (dashboards:manage_access) + dashboard_access_grants table + canViewDashboard resolver & grant helpers (Wave 1)
- [ ] 55-02-PLAN.md — Server enforcement: list filter + open-gating (404) + grant CRUD routes + dual-sink audit (Wave 2, depends on 55-01)

### Phase 56: Access-Management UI & List/Open UX
**Goal**: A `manage_access` user can view and edit a dashboard's grants from the UI, and the list/open experience reflects per-dashboard access for every persona.
**Depends on**: Phase 55 (grant API, filtered list endpoint, and open-gating must exist and be server-authoritative before the UI consumes them).
**Requirements**: GRANTUI-V110-01, GRANTUI-V110-02, GRANTUI-V110-03, LISTUX-V110-01, LISTUX-V110-02, LISTUX-V110-03
**Success Criteria** (what must be TRUE):
  1. A user with `dashboards:manage_access` can open an access panel for a dashboard that lists its current user grants and role grants.
  2. From that panel the user can add a grant (choosing a user or a role) and remove an existing grant, with changes persisted through the grant API and reflected immediately.
  3. The access-management entry point is absent from the DOM (hide-don't-disable, mirroring v1.8) when the user lacks `dashboards:manage_access` — the server remains the authority; UI gating is UX only.
  4. The dashboard list shows only dashboards the user may view (driven by the filtered endpoint): an analyst no longer sees ungranted dashboards, while admin and designer continue to see and open every dashboard with no regression to the existing design/governance workflow.
  5. Navigating directly to a non-permitted dashboard (stale URL / direct nav) shows a clear "you don't have access" state rather than a broken or empty dashboard.
  6. New UI is covered by vitest specs; frontend vitest stays at 100% green and web `tsc` stays clean.
**Plans**: 2 plans
- [ ] 56-01-PLAN.md — Permission constant + grant CRUD client fns + DashboardAccessModal (list/add/remove user & role grants) (Wave 1)
- [ ] 56-02-PLAN.md — Wire modal into list row (manage_access-gated), friendly empty state, inline no-access 404 panel (Wave 2, depends on 56-01)

### Phase 57: Verification & Live UAT
**Goal**: The end-to-end per-dashboard view-permission feature is proven correct against the deployed system across all personas, with all automated gates green.
**Depends on**: Phase 55, Phase 56.
**Requirements**: VERIFY-V110-01
**Success Criteria** (what must be TRUE):
  1. In a live operator walk-through, an analyst sees and can open ONLY granted dashboards, enforced on both the list view and direct navigation (the "no access" state appears for an ungranted dashboard reached by URL).
  2. A `manage_access` user grants and then revokes both a user grant and a role grant, and the effect on the analyst's visibility is immediate (next list/open reflects the change).
  3. Admin and designer users are unaffected — they continue to see and open all dashboards (governance + design workflow unchanged).
  4. Automated gates are green: frontend vitest 100%, web + server `tsc` clean, and the server vitest set-based known-flaky gate holds (failing files ⊆ TD-V16-TEST-ISOLATION list).
**Plans**: 3 plans
