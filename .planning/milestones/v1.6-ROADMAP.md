### 🚧 v1.6 Dynamic Views (Phases 32-36)

**Milestone Goal:** Operators define dashboard-scoped "dynamic views" — saved SQL templates that re-materialize on top of the existing filter view whenever filters change, guarded by a max-records threshold. Visualizations can use a dynamic view as their data source. When the underlying filtered source exceeds the threshold (or no filter is applied), the dynamic view is dropped and dependent widgets show an "over threshold" empty state.

**Locked decisions (informed lightweight planning, 2026-05-14):**
- Template token: `{view}` — substituted with the source table's current materialized filter-view name at materialize time.
- No-filter behavior: treat as over-threshold → dynamic view dropped, dependents show empty state. Threshold-gate is the safety story; running a dynamic view against the unfiltered source would defeat it.
- Columns persisted in DB on Save (refreshed on SQL edit) so ChartConfigPanel pickers work without round-tripping.
- Dashboard-scoped; multiple dynamic views per dashboard; lifecycle reset on logout / dashboard switch (mirrors v1.3 / v1.5).

### Phase 32: dynamic-view-foundation
**Goal**: Server-side foundation — `dashboard_dynamic_views` SQLite table; pure SQL helpers (template substitution + row-count check); three new endpoints (`POST /api/dynamic-view/preview`, `POST /api/dynamic-view/materialize`, `DELETE /api/dynamic-view/:id`); supertest coverage in both auth modes; full v1.3 backward compat (no impact on filter-view endpoints).
**Depends on**: Nothing (first v1.6 phase; pure additive server work)
**Requirements**: DV-V16-01, DV-V16-02, DV-V16-03, DV-V16-04, DV-V16-05
**Plans:** 3/3 plans complete
Plans:
- [ ] 32-01-db-schema-and-helpers-PLAN.md — Wave 1. dashboard_dynamic_views table + idempotent migration + pure helpers (substituteViewToken, buildDynamicViewName) + extracted createOrReplaceMaterialized shared helper. Closes DV-V16-01 (schema) + DV-V16-02 (helper).
- [ ] 32-02-crud-endpoints-PLAN.md — Wave 2 (depends on 01). GET/POST /api/dashboards/:dashboardId/dynamic-views + PUT /api/dynamic-views/:id with {view} validation + automatic columns_json clear on template_sql change. Closes DV-V16-01 (CRUD round-out).
- [ ] 32-03-preview-materialize-delete-PLAN.md — Wave 2 (depends on 01). POST /api/dynamic-view/preview + materialize (no-filter / over-threshold / TM-SMc-1078 retry via shared helper) + DELETE /api/dynamic-view/:id. Closes DV-V16-03, DV-V16-04, DV-V16-05.
**Success Criteria** (what must be TRUE):
  1. New `dashboard_dynamic_views` table exists with columns `id, dashboard_id, source_table_id, name, template_sql, max_records, columns_json, created_at, updated_at`. Idempotent PRAGMA-guarded migration mirrors the v1.4 Phase 19 pattern.
  2. Pure module `kinetica_bi/server/src/lib/dynamicViewSql.ts` exports `substituteViewToken(template, viewName)` — replaces `{view}` (case-insensitive, whitespace-tolerant) with the supplied identifier; throws if `{view}` is absent (configuration error).
  3. `POST /api/dynamic-view/preview` accepts `{ template_sql, source_view_name, sample_limit }`. Runs `SELECT * FROM ({template_sql_substituted}) LIMIT N` against Kinetica; returns `{ rows, columns }` for the operator's discovery flow. Does NOT create a permanent view.
  4. `POST /api/dynamic-view/materialize` accepts `{ dynamic_view_id }`. Looks up the row, computes the source filter-view name (via existing `buildFilterViewName`), runs a `SELECT COUNT(*) FROM <source_view>` row-count check, then either: (a) below threshold → `CREATE OR REPLACE MATERIALIZED VIEW <dynamic_view_name> AS (<substituted_sql>) USING TABLE PROPERTIES (TTL = 5)`; or (b) at/above threshold → `DROP TABLE IF EXISTS <dynamic_view_name>` and return `{ status: "over_threshold" }`. Re-uses the TM/SMc:1078 race-recovery retry from Phase 30.
  5. `DELETE /api/dynamic-view/:id` drops the materialized view + deletes the row.
  6. Supertest coverage in both `AUTH_MODE=password` and `AUTH_MODE=oidc` blocks: preview path (column extraction), materialize-below-threshold (200 + viewName), materialize-over-threshold (200 + `over_threshold` status + DROP fired), bare unsubstituted-token (400), 501 / WKB-style errors propagated cleanly.
