# Requirements: Kinetica BI — v1.3 Unified Dashboard Filtering

**Defined:** 2026-05-06
**Core Value:** Click-through data exploration — users drill into chart elements and the entire dashboard filters to that slice of data, enabling fast iterative analysis without writing SQL.

**Milestone goal:** Replace v1.2's broken WMS-QUERY filter and client-side WHERE-injection path with a single server-side primitive — a transient Kinetica materialized view per `(user, session, dashboard, table)` — that every chart, records-table, and map widget queries when filters are active. Closes TD-V12-01 (top v1.3 driver) and TD-V12-04.

**Architectural references:** `.planning/research/SUMMARY.md` (commit `e68080f`); PROJECT.md "Current Milestone: v1.3" block.

## v1.3 Requirements

### P1 Architectural Spikes (Phase 1 gates — must pass before code lands)

These four spikes verify Kinetica-deployment-specific behavior that the rest of v1.3 depends on. Findings drive Phase 1 lock decisions.

- [x] **SPIKE-V13-01**: Operator verifies that Kinetica WMS resolves `LAYERS=<materialized_view_name>` to valid tiles against the deployed instance. **P1 architectural gate** — if SPIKE-V13-01 fails, MAP-V13-* requirements are deferred to a post-v1.3 follow-up; charts ship as planned.
- [x] **SPIKE-V13-02**: Operator verifies per-user Kinetica credentials carry sufficient permission to execute `CREATE OR REPLACE MATERIALIZED VIEW` and `DROP TABLE IF EXISTS`. **P1 gate** — if denied, Phase 1 must deliver a service-account DDL path before consumer phases are buildable.
- [x] **SPIKE-V13-03**: Operator captures the exact Kinetica error message/code returned when querying a materialized view that has been dropped (TTL expiry or explicit DROP). Needed to build the `isViewNotFoundError()` reactive recovery branch in LIFE-V13-02.
- [x] **SPIKE-V13-04**: Operator verifies whether `LAYERS=<view_name>` resolves in the user's default schema or requires schema-qualified view names. Determines whether `POST /api/filter/materialize` returns a fully-qualified view name.

### Backend Materialize Endpoint

The new server-side primitive. Net-new endpoint — does not extend the pre-v1.0 `/api/views/:id/materialize` route (which is for persisted, dashboard-scoped views with SQLite-backed filter clauses).

- [x] **VIEW-V13-01**: User-initiated filter activity calls `POST /api/filter/materialize` with `(dashboardId, tableId, filters[])`; server fires `CREATE OR REPLACE MATERIALIZED VIEW <name> AS SELECT * FROM <table> WHERE <clause> USING TABLE PROPERTIES (TTL = 5)` via `kineticaSql(req, ...)`; returns `{ viewName: string, expiresAt: number }`.
- [x] **VIEW-V13-02**: User clearing all filters (or explicit cleanup on dashboard-switch / logout) calls `DELETE /api/filter/materialize` with `(dashboardId, tableId)` — server fires `DROP TABLE IF EXISTS <viewName>`; fire-and-forget semantics (client does not block on response).
- [x] **VIEW-V13-03**: View-name builder is deterministic: `_kbi_filt_u<userId>_d<dashId>_t<tableId>_s<sessionShort>` (sessionShort = first 8 hex chars of sessionId). OIDC-userId characters sanitized to Kinetica naming constraints (max 200 chars; underscore-prefix allowed; non-alphanumeric replaced with `_`).
- [x] **VIEW-V13-04**: Server is stateless re views — no SQLite tracking; no in-memory map of active views; Kinetica's sliding 5-min TTL is the sole authoritative cleanup mechanism.
- [x] **VIEW-V13-05**: `KineticaPermissionError` (DDL denied) surfaces via existing typed-error middleware as 403 with `code: "DDL_DENIED"` (or equivalent); client shows actionable toast "Filtering not enabled for your account — contact your administrator." (One-time per session.)
- [x] **VIEW-V13-06**: Server-side WHERE clause builder (extracted from the deleted v1.2 client-side `buildWhereClause`/`escapeKineticaStringLiteral`/`buildEqualityFilter`) — same SQL-safe escape semantics, lives server-side now, accepts the same `ActiveFilter[]` shape sent by the client.
- [x] **VIEW-V13-07**: Supertest coverage for `POST` and `DELETE` endpoints — asserts on DDL SQL string shape, view-name composition, empty-filters → DROP path, AUTH_MODE password and oidc both wire.

### Client View State Store

A new Zustand slice paired with the existing `useFilterStore` (which stays unchanged for chip state).

- [x] **VSTORE-V13-01**: New `useFilterViewStore` Zustand slice with shape `Record<tableId, { viewName: string, expiresAt: number, materializing: boolean, materializeVersion: number }>` and actions `setView`, `clearView`, `markMaterializing`, `bumpMaterializeVersion`, `reset`. Reference-stable per-table updates (only mutated entries get new references) for selector-driven re-renders.
- [x] **VSTORE-V13-02**: Materialize call is dispatched from `AggregatedWidgetRenderer` ONLY (single trigger point per dashboard-table); 300ms debounce; dedicated `materializeAbortRef` separate from chart-query `AbortController`; `setView()` is called only after server confirms 200 (no optimistic updates that could leave widgets querying a non-existent view).
- [x] **VSTORE-V13-03**: `useFilterStore` (existing v1.2 slice) is unchanged — chip state, drill-down dispatch, filter intent, 10-cap, `filterVersion`, dedupe/replace semantics all stay as-is. `useFilterStore` drives WHEN to materialize; `useFilterViewStore` drives WHAT NAME to put in `FROM` / `LAYERS`.
- [x] **VSTORE-V13-04**: New client API helpers (`materializeFilter(args, signal?)`, `dropFilterView(args)`) added to `kinetica_bi/src/lib/client.ts` following existing `apiFetch` patterns; `signal?` threaded through to enable abort on rapid filter changes.

### Chart Filtering (FROM-swap)

Replaces v1.2's `injectWhereClause` path with a `FROM <table>` → `FROM <view>` substitution at SQL execution time.

- [x] **FILT-V13-01**: User clicks any chart element on bar/line/pie/scatter/table widgets → debounced materialize → `AggregatedWidgetRenderer` substitutes `FROM <table>` with `FROM <view>` in the widget's SQL query (when `useFilterViewStore.views[tableId]?.viewName` is non-null) and re-runs.
- [x] **FILT-V13-02**: `RecordsTableRenderer` (second SQL consumer that short-circuits at `WidgetRenderer.tsx:192` and bypasses `AggregatedWidgetRenderer`) wired with the same FROM-swap pattern — subscribes to `useFilterViewStore.views[tableId]` and rewrites its SQL accordingly.
- [x] **FILT-V13-03**: When `useFilterStore.filters[tableId]` is empty (no active filters), widgets query the raw `<table>` with no materialize round-trip. Zero overhead on cold dashboard loads.
- [x] **FILT-V13-04**: User sees a per-widget "filtering..." indicator during the materialize phase (badge in widget card header, NOT a full overlay); stale chart data remains visible underneath; existing `loading` state continues to cover the chart-query phase. Two visual phases: (a) `materializing` (new), (b) `loading` (existing).
- [x] **FILT-V13-05**: Dead-code deletion (atomic with FROM-swap landing — same phase): `injectWhereClause`, `buildWhereClause`, `escapeKineticaStringLiteral`, `buildEqualityFilter` removed from `filterStore.ts`; corresponding `filterStore.spec.ts` test blocks deleted; `tsc --noEmit` passes after removal with no orphan callers.

### Map Filtering (LAYERS-swap)

Replaces v1.2's broken `QUERY` param approach with a `LAYERS=<view_name>` swap. Closes TD-V12-01.

- [x] **MAP-V13-01**: When filters are active for a table, map layers rendering that table use `LAYERS=<view_name>` instead of `LAYERS=<table>` in WMS GetMap requests (gated on SPIKE-V13-01 passing).
- [x] **MAP-V13-02**: When filters are NOT active for a table, map layers fall back to `LAYERS=<table>` (raw, unfiltered).
- [x] **MAP-V13-03**: `wmsUrlBuilder.ts` `QUERY` / `FILTER_PARAM` block fully removed; `_v` cache-buster RENAMED to `_mv` ("materialize version") and RETAINED — sourced from `useFilterViewStore.materializeVersion[tableId]`. Required because the same view name gets `CREATE OR REPLACE`'d with new content on filter change; OL `ImageWMS` caches by URL, so cache-bust is still mandatory.
- [x] **MAP-V13-04**: `MapChartRenderer` Effect 3 dependency array changes from `[filterVersion, includedLayers, tables]` to a stable `viewsKey` string derived from `useFilterViewStore`; Effect 1 (Map create + ResizeObserver) and Effect 2 (per-layer source attach) unchanged. v1.2 PITFALL locks (ResizeObserver dimension propagation, blob lifecycle / data-URL placeholder, mapRef guard, XHR+arraybuffer+base64 imageLoadFunction) preserved verbatim with explicit lock comments per V13-P-06.
- [x] **MAP-V13-05**: Map widgets and `RecordsTableRenderer` are PURE CONSUMERS of `useFilterViewStore` — they never trigger `POST /api/filter/materialize` themselves (prevents 2N redundant DDL when chart + map share a table). Only `AggregatedWidgetRenderer` is the materialize trigger.
- [x] **MAP-V13-06**: `wmsUrlBuilder.spec.ts` FILT-04 test block (lines 470-492) explicitly deleted in cleanup phase; `_v` test cases updated to `_mv`; new tests assert on `LAYERS=<view>` substitution when filter active.

### Lifecycle & Recovery

TTL expiry handling, reset triggers, and orphan-view cleanup.

- [x] **LIFE-V13-01**: Proactive TTL expiry recovery — client checks `Date.now() >= useFilterViewStore.views[tableId].expiresAt` before each chart query; if expired, clears the stored view and re-materializes silently before the chart query runs. No user-visible error.
- [x] **LIFE-V13-02**: Reactive TTL expiry recovery — `.catch()` on chart query detects "view not found" / "table not found" Kinetica error (per SPIKE-V13-03) → clears view from `useFilterViewStore` → re-materializes → retries the chart query. No toast, no error UI.
- [x] **LIFE-V13-03**: Logout reset wiring extended — existing `useFilterStore.reset()` hook in `App.tsx` (`useEffect([status])`) extended to also call `useFilterViewStore.reset()` AND fire-and-forget `DELETE /api/filter/materialize` for each active view.
- [x] **LIFE-V13-04**: Dashboard-switch reset wiring extended — existing `DashboardOpen` `useEffect([dashboard.id])` cleanup extended to also call `useFilterViewStore.reset()` AND fire-and-forget DROP for each active view.
- [x] **LIFE-V13-05**: Page-refresh / tab-close: no explicit client cleanup needed; Kinetica TTL is the sole cleanup mechanism for orphaned views (5-min sliding TTL ensures auto-drop of idle views).

## Out of Scope

Explicitly excluded from v1.3.

| Feature | Reason |
|---------|--------|
| Shareable filter URLs | Filter state is tied to `sessionId` — view name includes session component |
| Filter state persistence across page refresh | 5-min sliding TTL covers active users; F5 reset is acceptable cost |
| Undo/Redo for filter changes | Filter bar `×` dismiss + Clear All cover most flows |
| Cross-dashboard filter inheritance | `useFilterStore.reset()` on dashboard switch is locked v1.2 design decision |
| Persistent filter snapshots / saved filter sets | Overlaps with pre-v1.0 persisted views workflow |
| Filter expiry countdown / toast / banner | Silent re-materialize is the correct handling |
| Materialize progress bar | Kinetica DDL is synchronous; no incremental progress signal |
| View warm-up / pre-materialize on dashboard load | Predicting filters requires ML/query history; prohibitively expensive |
