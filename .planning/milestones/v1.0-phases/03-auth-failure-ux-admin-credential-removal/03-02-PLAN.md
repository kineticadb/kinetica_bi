<!-- Express async error forwarding —- the executor MUST handle this correctly. -->

Express 4 does NOT auto-forward thrown errors from `async` route handlers to error middleware. Two compatible options:

Option A (RECOMMENDED — minimal dep, zero behavior change): wrap each async route handler in a tiny `asyncHandler` helper:
```ts
const asyncHandler =
  <T extends Request = Request>(fn: (req: T, res: Response, next: NextFunction) => Promise<unknown>) =>
  (req: T, res: Response, next: NextFunction) => {
    Promise.resolve(fn(req, res, next)).catch(next);
  };
```
Mount as `app.get("/api/...", requireConfig, asyncHandler(async (req, res) => { ... }))`. Throws inside the async fn → next(err) → middleware.

Option B: install `express-async-errors` (one-liner side-effect import at top of index.ts). Adds ~10KB to the dep tree. Both are acceptable; Option A keeps zero new deps.

The plan picks Option A (no new dep, file-local helper, easy to grep/audit).

For `app.use("/api", requireAuth)` (line 122) Phase 1 already returns 401 directly without throw — leave alone. requireAuth is NOT an async handler in the throw sense.

Existing route signatures (current state — Phase 2):
```typescript
app.post("/api/sql", requireConfig, async (req, res) => { ... try { ... } catch (error) { ... return res.status(502)... } })
app.get("/api/kinetica/schemas", requireConfig, async (req, res) => { ... try { ... } catch { ... } })
app.get("/api/kinetica/schemas/:schema/tables", ...)
app.get("/api/kinetica/schemas/:schema/tables/:table/columns", ...)
app.get("/api/wms", requireConfig, async (req, res) => { ... try { ... } catch { ... } })
app.post("/api/views/:id/materialize", requireConfig, async (req, res) => { ... try { ... updateViewStatus(id,"created"); } catch (err) { updateViewStatus(id, "error", ...); return res.status(502)... } })
```

Materialize's MUST-PRESERVE side effect (current index.ts:271-285):
```typescript
try {
  await kineticaSqlHelper(req as AuthedRequest, ddl, { ... });
  const updated = updateViewStatus(id, "created");
  return res.json({ view: updated, ddl });
} catch (error) {
  // PRESERVE: persist view status="error" with the error message before forwarding
  if (error instanceof KineticaAuthError || ... ) {
    const updated = updateViewStatus(id, "error", error.message);
    // PHASE 3 CHANGE: was `return res.status(502).json({ error: error.message, view: updated });`
    // becomes `return next(error);` — middleware sends the 401/403/502 response
    return next(error);
  }
  // Defensive: unexpected non-typed error
  updateViewStatus(id, "error", "Failed to materialize view");
  return next(error);
}
```
Note: the BI client previously received `{ error, view }` from the materialize 502 response. Phase 3's middleware does NOT include the `view` object (the middleware only knows about errors, not domain objects). The frontend should refetch view status separately if it needs the persisted error_message — Plan 03-04's `materializeView()` helper can read `view: undefined` and rely on a follow-up `listViews()`. Existing routes.materialize.spec.ts tests `expect(res.body).toHaveProperty("error")` — that still passes; tests asserting `res.body.view` (none currently do — verified) are unaffected.
