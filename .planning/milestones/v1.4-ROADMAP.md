### Phase 13: spikes-and-endpoint
**Goal**: Architectural unknowns resolved and the server-side materialize primitive is live and tested
**Depends on**: Nothing (first v1.3 phase)
**Requirements**: SPIKE-V13-01, SPIKE-V13-02, SPIKE-V13-03, SPIKE-V13-04, VIEW-V13-01, VIEW-V13-02, VIEW-V13-03, VIEW-V13-04, VIEW-V13-05, VIEW-V13-06, VIEW-V13-07
**Success Criteria** (what must be TRUE):
  1. Operator has recorded spike findings for S1 (WMS LAYERS=view), S2 (DDL permission), S3 (error message format for expired view), and S4 (schema qualification) — each with a concrete pass/fail and its downstream consequence for the build
  2. `POST /api/filter/materialize` with non-empty filters issues `CREATE OR REPLACE MATERIALIZED VIEW _kbi_filt_u<...>_d<...>_t<...>_s<...> AS (SELECT * FROM <table> WHERE <clause>) USING TABLE PROPERTIES (TTL = 5)` via `kineticaSql` and returns `{ viewName, expiresAt }`
  3. `POST /api/filter/materialize` with empty filters issues `DROP TABLE IF EXISTS <viewName>` and returns `{ dropped: true }`; client can call it fire-and-forget on clear/logout/switch
  4. OIDC usernames with special characters (dots, at-signs, hyphens) are sanitized to Kinetica-safe alphanumeric+underscore before interpolation into the view name
  5. Supertest coverage passes for both `AUTH_MODE=password` and `AUTH_MODE=oidc` session contexts, asserts on DDL SQL string shape, view-name format, and 403 response when DDL permission is denied

### Phase 15: chart-filtering
**Goal**: Every chart and records-table widget queries filtered data via `FROM <view>` swap when filters are active, dead WHERE-injection code is gone, and all lifecycle reset hooks are wired
**Depends on**: Phase 14
**Requirements**: FILT-V13-01, FILT-V13-02, FILT-V13-03, FILT-V13-04, FILT-V13-05, LIFE-V13-01, LIFE-V13-02, LIFE-V13-03, LIFE-V13-04, LIFE-V13-05
**Success Criteria** (what must be TRUE):
  1. User clicks a bar/line/pie/scatter/table chart element → debounce fires → all widgets on the same table re-render using `FROM <view_name>` (not `FROM <raw_table>` with a WHERE clause); a per-widget "filtering..." badge appears during the materialize phase and disappears once chart data loads; existing chart data remains visible underneath during both phases
  2. `RecordsTableRenderer` (the second SQL consumer that bypasses `AggregatedWidgetRenderer`) also uses `FROM <view_name>` when a filter is active — row count in the records table narrows to match the filtered dataset
  3. When no filters are active (`useFilterStore.filters[tableId]` is empty), widgets query the raw table with zero materialize overhead; cold dashboard loads incur no additional round-trips
  4. After 5+ minutes idle with an active filter, the next chart interaction triggers silent re-materialize with no error state shown to the user (proactive `expiresAt` check clears stale view; reactive "not found" catch re-materializes then retries)
  5. User clicks logout or switches dashboards → `useFilterViewStore.reset()` fires alongside the existing `useFilterStore.reset()`, and a fire-and-forget `DROP TABLE IF EXISTS` is sent for each active view
  6. `tsc --noEmit` passes with zero errors after deletion of `injectWhereClause`, `buildWhereClause`, `escapeKineticaStringLiteral`, and `buildEqualityFilter` from `filterStore.ts`; `filterStore.spec.ts` test blocks for those functions are removed; full vitest suite is green

**Success Criteria** (what must be TRUE):

  4. A layer with `info_template` configured renders each record using that HTML string; a layer without a template renders a plain key-value table of the selected columns — both rendering modes are visible in the same popup when switching between a templated and an untemplated layer
