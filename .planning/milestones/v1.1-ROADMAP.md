### Phase 4: Schema + SessionStore Foundation

**Goal**: The session schema can hold both password and OIDC credentials without ambiguity; all downstream code compiles against the new types.

**Depends on**: Nothing (foundation for all v1.1 work)

**Requirements**: MODE-02, MODE-03, MODE-06

**Success Criteria** (what must be TRUE):
  1. `PRAGMA table_info(sessions)` shows a `credential_type TEXT NOT NULL DEFAULT 'password'` column; existing password-mode rows are unaffected (default value applied automatically).
  2. `SessionRow` type in `sessionStore.ts` has a `secret` field (renamed from `password`) and a `credentialType: "password" | "oidc"` field; `createSession` accepts a fourth `credentialType` param defaulting to `"password"`.
  3. The `id_token` encrypted column (`id_token_ciphertext`, `id_token_iv`, `id_token_auth_tag`) exists in the sessions DDL and `createSession` accepts it as an optional param.
  4. All existing tests pass without modification — password-mode behavior is unchanged.
  5. TypeScript compilation succeeds with zero errors against the new `AuthedRequest` shape (which now carries `credentialType` at top level alongside `creds`).

### Phase 5: OIDC Module + Routes

**Goal**: In `AUTH_MODE=oidc`, a user can complete the full OIDC Authorization Code flow end-to-end; the backend creates a valid session row with credential_type='oidc'; the entire flow is testable via curl without any frontend changes.

**Depends on**: Phase 4 (needs `createSession` with `credentialType` param; needs `credential_type` column in schema)

**Requirements**: OIDC-02, OIDC-03, OIDC-04, OIDC-05, OIDC-06, OIDC-07, OIDC-08, MODE-01

**Success Criteria** (what must be TRUE):
  1. `curl -i http://localhost:4000/api/auth/oidc/start` (with `AUTH_MODE=oidc`) returns `HTTP/1.1 302` with a `Location` header pointing to the configured IdP's `authorization_endpoint`; an `oidc_state` httpOnly cookie is set.
  2. `curl -i http://localhost:4000/api/auth/oidc/callback?error=access_denied&state=<any>` returns a redirect to the login page with a non-leaking user-visible error message — never a 500 or blank response.
  3. `curl -i http://localhost:4000/api/auth/login` with `AUTH_MODE=oidc` returns `HTTP/1.1 405` (or `400` per ARCHITECTURE.md pattern) — the password login route is disabled.
  4. `curl http://localhost:4000/api/auth/config` returns `{"authMode":"oidc"}` (or `"password"`) with no authentication required.
  5. After a successful end-to-end OIDC callback (state validated, code exchanged, id_token verified, username extracted), the sessions table contains a row with `credential_type='oidc'` and the access token encrypted in `ciphertext`; `id_token_ciphertext` is also populated.
  6. Server startup with `AUTH_MODE=oidc` and an unreachable or misconfigured `AUTH_OIDC_ISSUER_URL` causes the process to exit non-zero with a clear error log — it never boots into a broken state.

**Open questions — resolve at Phase 5 planning kickoff (spike before writing code)**:
  - **`openid-client` v5 vs v6**: Run `npm show openid-client version` from `kinetica_bi/server/` at planning time to confirm v5 is still current stable. STACK.md recommends v5; v6 was a WIP rewrite as of mid-2025.
  - **Opaque vs JWT access token format**: Confirm with team's IdP owner whether the IdP issues JWT or opaque access tokens. PITFALLS.md T-05 and T-02 depend on this. If opaque: the BI app can still store it, but PITFALLS.md T-05 warning log must fire and Kinetica trust config must be verified separately.
  - **Dev vs prod redirect URL**: `AUTH_OIDC_REDIRECT_URI` must differ between dev (`:5173` or `:4000` proxy) and prod. Confirm the exact callback URL registered at the IdP before writing the start route. PITFALLS.md O-03.
  - **Kinetica claim-to-username mapping**: Confirm which OIDC claim (`preferred_username`, `sub`, `email`) maps to the Kinetica account name in the target deployment. Required before `AUTH_OIDC_USERNAME_CLAIM` default can be validated. This is a deploy-time prereq (PITFALLS.md T-03, T-04).

### Phase 6: requireAuth + Helper Credential Branch

**Goal**: Every Kinetica API call made from an OIDC session sends `Authorization: Bearer <token>`; every call from a password session continues to send `Authorization: Basic <b64>`; the existing 401-REAUTH chain fires correctly when the bearer token expires; the audit log records `auth_mode` per call.

**Depends on**: Phase 4 (needs `credentialType` on `SessionRow` + `AuthedRequest`), Phase 5 (needs OIDC sessions to exist before the helper branch is meaningful)

**Requirements**: MODE-04, UX-04, UX-05, UX-07, OBS-02

**Success Criteria** (what must be TRUE):
  1. `git grep 'Authorization.*Basic' kinetica_bi/server/src/kinetica.ts` returns exactly one site — inside `buildAuthHeader`, behind a `credentialType === 'password'` branch — and a `Bearer` branch exists beside it.
  2. A curl request using an OIDC session cookie to `GET /api/dashboards` reaches Kinetica with `Authorization: Bearer <token>`; a request using a password session cookie sends `Authorization: Basic <b64>`. (Verify via server-side audit log, not Kinetica response.)
  3. When the stored access token's `exp` claim is in the past, `requireAuth` (or `getSession`) returns null → the response is `401 { code: "REAUTH_REQUIRED" }` — the expired token is never forwarded to Kinetica.
  4. `POST /api/auth/logout` destroys the session row and clears the `kbi_session` cookie identically in both auth modes; the user remains logged in at the IdP (no `end_session_endpoint` call).
  5. Every Kinetica-call audit log line includes `"auth_mode":"oidc"` or `"auth_mode":"password"` as a top-level JSON field.

Plans:

### Phase 7: Frontend AUTH_MODE Awareness

**Goal**: The browser renders the correct login UI for the configured auth mode without requiring a rebuild; after OIDC re-auth the user lands back on the page they left; `/api/auth/me` exposes `authMode` to the frontend.

**Depends on**: Phase 5 (`/api/auth/config` route must exist), Phase 6 (full OIDC session flow must work end-to-end before frontend wiring is meaningful)

**Requirements**: OIDC-01, UX-06, UX-08

**Success Criteria** (what must be TRUE):
  1. With `AUTH_MODE=oidc` and the app loaded in a browser, the `LoginPage` shows a "Sign in with SSO" button and no username/password form; with `AUTH_MODE=password` it shows the existing form — without rebuilding the frontend.
  2. `GET /api/auth/me` response JSON includes `"authMode":"oidc"` (or `"password"`) as a top-level field.
  3. A user who is redirected to the IdP mid-session (token expiry → REAUTH → OIDC start) and completes re-auth lands back on the same page they were on before the redirect — confirmed by checking `window.location.pathname` after callback redirect.
  4. The `LoginPage` session-expired banner ("Your session has ended. Please sign in again.") renders correctly in OIDC mode when `reason === "session-expired"`.
  5. `GET /api/auth/config` response includes `Cache-Control: no-store` header so the browser never serves a stale auth mode.

### Phase 8: Boot Wipe + Hardening + Runbook

**Goal**: Changing `AUTH_MODE` between deployments wipes stale sessions atomically; the server refuses to start with missing OIDC config; operators have a clear, actionable runbook for Kinetica OIDC trust configuration.

**Depends on**: Phase 4 (needs `credential_type` column to detect contradicting sessions), Phase 5 (`validateOidcEnv` is already defined in `oidc.ts`), Phases 6+7 complete (hardening phase runs last)

**Requirements**: MODE-05, OPS-01

**Success Criteria** (what must be TRUE):
  1. Starting the server with `AUTH_MODE=oidc` after a previous run in `AUTH_MODE=password` (or vice versa) causes all sessions with the contradicting `credential_type` to be deleted in a single SQLite transaction before `app.listen()` is called — confirmed by checking the sessions table count before and after restart.
  2. Starting the server with `AUTH_MODE=oidc` and `AUTH_OIDC_ISSUER_URL` unset (or pointing to an unreachable endpoint) causes the process to exit with a non-zero code and a log message naming the missing/invalid variable — it never starts serving requests.
  3. `cat kinetica_bi/server/DEPLOY-RUNBOOK.md` (or the Phase 1 runbook extended with a v1.1 section) contains a "Kinetica OIDC Trust Configuration" section covering: IdP issuer URL, expected audience (`AUTH_OIDC_CLIENT_ID`), JWKS URL, claim-to-Kinetica-username mapping, and an explicit note that this is a DBA task on the Kinetica server — separate from the BI app's `AUTH_OIDC_*` env vars.
  4. The runbook section explicitly calls out PITFALLS O-04 / I-06: "If users can log in but every dashboard call fails with re-auth loop, check Kinetica's OIDC trust configuration first."
  5. Server startup in `AUTH_MODE=oidc` logs a structured line: `"[boot] OIDC mode active. Kinetica must be configured to trust tokens from <issuer> with audience <client_id>."` — visible without reading the runbook.
