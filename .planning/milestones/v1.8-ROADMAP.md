## Phase Details

### Phase 46: RBAC Schema + Data Layer
**Goal**: The SQLite role registry and all data-access primitives exist and are idempotently seeded — every downstream phase can read and write roles, permissions, and user assignments without performing any DB migrations of their own.
**Depends on**: Nothing (foundation gate for all v1.8 phases)
**Requirements**: SCHEMA-V18-01, SCHEMA-V18-02, SCHEMA-V18-03
**Success Criteria** (what must be TRUE):
  1. A server restart against an existing v1.7 database completes without error — the `roles`, `role_permissions`, `user_roles` tables are created idempotently (CREATE TABLE IF NOT EXISTS) and all four built-in roles plus 15-permission catalog entries are present after restart (INSERT OR IGNORE; no duplicate rows on second restart).
  2. `getEffectivePermissions("admin")` returns all 15 permissions regardless of DB state — the bootstrap admin short-circuit fires before any DB lookup.
  3. `getEffectivePermissions` for a username with zero `user_roles` rows returns exactly the current analyst role's permission set (default-analyst fallback; no lockout on first deploy).
  4. When `AUTH_MODE=oidc` and `APP_ADMIN_USERNAME` is unset or at default `"admin"`, the server boot log contains a structured warning entry citing the OIDC IdP-claim mismatch risk.
  5. `db.rbacMigration.spec.ts` confirms idempotent migration on both a fresh database and a database that already has the v1.7 schema — both pass without errors or duplicate rows.
**Plans**: 3 plans (3 waves — strict foundation dependency chain)
- [ ] 46-01-PLAN.md — Canonical PERMISSIONS catalog (15) + DEFAULT_ROLE_MAPPINGS constants (wave 1)
- [ ] 46-02-PLAN.md — RBAC tables in SCHEMA_DDL + idempotent seedRbac() + migration spec (wave 2)
- [ ] 46-03-PLAN.md — getEffectivePermissions data layer + bootstrap admin + OIDC boot warning (wave 3)

### Phase 47: Server Middleware + Route Guards
**Goal**: Every mutating route is permission-gated server-side and the existing supertest suite continues passing at the pre-v1.8 baseline — server enforcement is the authority before any frontend work ships.
**Depends on**: Phase 46 (rbacDb.ts and seed data must exist before middleware can call getEffectivePermissions)
**Requirements**: GUARD-V18-01, GUARD-V18-02, GUARD-V18-03, GUARD-V18-04, GUARD-V18-05
**Success Criteria** (what must be TRUE):
  1. An unauthenticated or permission-lacking request to any config-mutation route (dashboards CRUD, widgets CRUD + config PATCH, tables association, views CRUD, dynamic-views CRUD, dashboard-layers CRUD + reorder) receives a 403 with `code: "PERMISSION_DENIED"` — mirroring the existing `REAUTH_REQUIRED` pattern.
  2. All analyst interaction routes (`POST/DELETE /api/filter/materialize`, `POST /api/info/query`, `GET /api/top-values`, column-stats, quantile, `POST /api/dynamic-view/materialize`, `POST /api/dynamic-view/:id/drop`, `/api/wms`, read-path SQL) remain reachable with `requireAuth` only — a valid analyst session can reach all of them without a 403.
  3. RBAC management routes (list users, assign/revoke roles, role CRUD, mapping edits) are gated on the correct permissions from the catalog (`users:view`, `users:assign_roles`, `roles:view`, `roles:manage_permissions`, `roles:create_custom`, `roles:delete_custom`) and return 403 for callers without those permissions.
  4. The existing server vitest suite passes at the pre-v1.8 baseline (582/689) with no new failures introduced — `createAdminSession(db)` seeds a session AND grants admin permissions, allowing all existing route tests to reach their handlers as before.
  5. A comment block at the analyst-passthrough route registrations in `packages/server/src/index.ts` documents the boundary — the analyst-passthrough classification is visible in code to future contributors.
**Plans**: 3 plans (3 waves — strict dependency chain: helper migration → factory → route wiring)
- [ ] 47-01-PLAN.md — createAdminSession() helper + 21-spec migration + datasets:manage catalog addition + seed-history upgrade-path spec (wave 1, GUARD-V18-05)
- [ ] 47-02-PLAN.md — requirePermission factory (rbac.ts) + routes.rbac.spec.ts (wave 2, GUARD-V18-01)
- [ ] 47-03-PLAN.md — wire guards on 22 mutation routes + passthrough boundary comment + known_users table/upserts + 7 management routes (wave 3, GUARD-V18-02/03/04)

### Phase 48: /me Extension + Frontend Store + UI Gating
**Goal**: The application is usable as a non-admin role — every UI surface that requires a permission either hides/disables correctly for users who lack it, or remains fully accessible for users who have it, with server enforcement already live and authoritative.
**Depends on**: Phase 47 (server enforcement must be live before frontend gating ships; permission strings must be canonical before frontend imports them)
**Requirements**: GATE-V18-01, GATE-V18-02, GATE-V18-03, GATE-V18-04, GATE-V18-05
**Success Criteria** (what must be TRUE):
  1. `GET /api/auth/me` returns `roles: string[]` and `permissions: string[]` alongside existing fields; `useAuthStore.user` carries those arrays and `hasPermission(perm)` returns the correct boolean without a new store or additional fetch call.
  2. A user with only analyst permissions sees the DashboardsPage with no New Dashboard, no Edit, no Delete, no Map Layers, and no Dynamic Views buttons — all five buttons are hidden (not disabled), with no console errors.
  3. A user without `dashboards:edit` cannot add, delete, or reorder widgets via the grid — the add-widget control is hidden and drag/resize interactions are inert.
  4. A user without `widgets:configure` sees ChartConfigPanel in read-only mode — the save/apply controls are hidden and no configuration changes can be submitted.
  5. The Sidebar nav items "User Management" and "Roles" are hidden for users lacking `users:view` and `roles:view` respectively; they remain visible and functional for users who hold those permissions.

### Phase 49: Users Management UI
**Goal**: An admin or user admin can see all known usernames with their current roles and assign or revoke roles — including bulk assignment — with the system protecting against the last admin being removed.
**Depends on**: Phase 48 (Sidebar nav "User Management" link and `hasPermission` selector must exist; RBAC management API routes from Phase 47 must be live)
**Requirements**: USERS-V18-01, USERS-V18-02, USERS-V18-03, USERS-V18-04, SAFE-V18-01
**Success Criteria** (what must be TRUE):
  1. The Users page lists all known usernames (sourced from session history plus existing role assignments) with each user's currently assigned roles displayed as chips — the list is visible to any user with `users:view`.
  2. A user admin can assign a role to a user and immediately see the updated chip list; revoking a role removes its chip; a user may hold multiple roles simultaneously and all are shown.
  3. Bulk role assignment works — selecting multiple users and applying a role assigns it to all selected users in one action; already-assigned users are not duplicated.
  4. Attempting to revoke the last admin role from the last non-bootstrap admin user returns a clear 400 error from the server; the UI surfaces the error message and does not apply the change.
  5. An admin who logs in while unassigned users exist sees an onboarding banner ("N users are currently on the default analyst role") with a link to the User Management page; the banner disappears once all users have explicit role assignments.
**Plans**: 3 plans (3 waves — server foundation → page component → app-shell integration)

### Phase 50: Roles Management UI + Custom Roles + Audit
**Goal**: An admin or user admin can view and edit role-to-permission mappings, create and delete custom roles, with escalation guards preventing privilege escalation and all mutations recorded in the audit log.
**Depends on**: Phase 49 (role management is more complex than user management and benefits from the management API layer being stable; escalation guard logic depends on the assign/revoke API shape established in Phase 49)
**Requirements**: ROLES-V18-01, ROLES-V18-02, ROLES-V18-03, ROLES-V18-04, SAFE-V18-02, AUDIT-V18-01
**Success Criteria** (what must be TRUE):
  1. The Roles page shows a role × permission matrix — rows are built-in and custom roles, columns are the 15-item permission catalog — with checkboxes reflecting current mappings; the page is visible to any user with `roles:view`.
  2. A user admin can edit permission mappings for any role including built-ins; editing a built-in role displays a warning ("affects all users with this role"); saving the change takes effect on the next request by any user holding that role.
  3. A user admin can create a custom role by selecting any subset of the 15 permissions; the new role appears in the matrix and is immediately assignable on the Users page.
  4. A custom role can be deleted only when no users currently hold it; attempting to delete a role with active holders returns a clear error; built-in roles cannot be deleted or renamed.
  5. A user admin (non-admin) cannot assign the admin role to any user, cannot edit the admin role's permission mappings, and cannot grant a custom role permissions outside their own effective permission set — the server rejects all three attempts with a 403.
  6. Every role assignment, revocation, and permission mapping change emits a structured audit-log entry (extending the existing OBS-01 JSON log) that includes actor username, target (user or role), and before/after state — entries are visible in the server log immediately after the action.
**Plans**: 3 plans (3 waves — server authority → RolesPage component → app wiring + UsersPage retrofit)
- [ ] 50-01-PLAN.md — rbac_audit table + emitRbacAudit + 3 escalation guards + held-role delete block + slug validation + audit in 5 handlers + createUserAdminSession (wave 1, SAFE-V18-02/AUDIT-V18-01/ROLES-V18-03/04 server)
- [ ] 50-02-PLAN.md — RolesPage two-pane matrix editor + draft/Save + inline custom-role create/delete + holders_count + client wrappers + SAFE-V18-02 UI mirrors (wave 2, ROLES-V18-01/02/03/04 UI)
- [ ] 50-03-PLAN.md — App.tsx 'roles' Page wiring + OIDC ReturnTo + UsersPage admin-role filter for non-admin editors (wave 3, ROLES-V18-01 reachability / SAFE-V18-02 Users-page mirror)
