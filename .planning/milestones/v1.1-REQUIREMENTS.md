# Requirements: Kinetica BI

**Defined:** 2026-04-30
**Core Value:** Click-through data exploration over Kinetica-backed dashboards.
**Milestone:** v1.1 — OIDC SSO Support

## v1.1 Requirements

Requirements for the OIDC SSO Support milestone. Adds Generic OIDC as an alternative authentication path alongside the existing v1.0 Kinetica password flow. A single deployment is configured for one mode or the other via `AUTH_MODE`; both modes converge on the same AES-256-GCM encrypted session store.

### OIDC Flow

The Authorization Code flow against any OIDC-compliant IdP. All requirements assume `AUTH_MODE=oidc`.

- [x] **OIDC-01**: When `AUTH_MODE=oidc`, the LoginPage displays a "Sign in with SSO" button instead of the username/password form. Clicking it issues `GET /api/auth/oidc/start`.
- [x] **OIDC-02**: `GET /api/auth/oidc/start` builds the IdP authorization URL from the discovered `authorization_endpoint`, generates a cryptographically random `state`, persists it in a short-lived httpOnly cookie, and 302-redirects the user to the IdP.
- [x] **OIDC-03**: At server startup, the OIDC discovery document is fetched from `${AUTH_OIDC_ISSUER_URL}/.well-known/openid-configuration` and cached in process memory. If discovery fails (network error, malformed document, missing required endpoints), the server logs a clear error and exits fail-fast — never boots into a broken state.
- [x] **OIDC-04**: On callback, the returned `state` parameter must match the value persisted by `/api/auth/oidc/start`. Mismatch → callback rejected with a user-visible error; never proceed with code exchange.
- [x] **OIDC-05**: `GET /api/auth/oidc/callback` exchanges the authorization `code` for tokens at the IdP's `token_endpoint`, using `AUTH_OIDC_CLIENT_ID`, `AUTH_OIDC_CLIENT_SECRET`, and `AUTH_OIDC_REDIRECT_URI`.
- [x] **OIDC-06**: The returned `id_token` JWT signature is verified against the IdP's JWKS (fetched from the discovered `jwks_uri`). Audience must equal `AUTH_OIDC_CLIENT_ID`; issuer must equal `AUTH_OIDC_ISSUER_URL`; `exp` checked. Verification failure → callback rejected.
- [x] **OIDC-07**: The username is extracted from the verified ID token claims using the env var `AUTH_OIDC_USERNAME_CLAIM` (default `preferred_username`). Optional `AUTH_OIDC_USERNAME_REGEX` applies a transform. If the configured claim is missing or the regex produces an empty string, callback returns a user-visible error — never silently stores an empty username.
- [x] **OIDC-08**: Callback errors (IdP `?error=…`, state mismatch, code-exchange failure, ID token verification failure, missing claim) redirect the user to LoginPage with a short, non-leaking error message. Never a 500, blank page, or stack trace.

### Auth Mode Plumbing

The `AUTH_MODE` server-side switch and the session store / helper changes that support both modes.

- [x] **MODE-01**: An `AUTH_MODE` env var (`password` | `oidc`) gates which auth routes are mounted. In OIDC mode, `POST /api/auth/login` is not mounted (or returns 405). In password mode, `/api/auth/oidc/start` and `/api/auth/oidc/callback` are not mounted.
- [x] **MODE-02**: The `sessions` table is extended with a `credential_type TEXT NOT NULL DEFAULT 'password'` column. Existing v1.0 password rows are unaffected (default value handles the migration).
- [x] **MODE-03**: When `AUTH_MODE=oidc`, the access token is stored in the session row's encrypted `ciphertext` column (replacing where the password lived in v1.0). Encryption key remains `SESSION_ENCRYPTION_KEY`; AES-256-GCM unchanged.
- [x] **MODE-04**: The `kineticaSql` / `kineticaWms` helpers branch on `req.user.credentialType`: emit `Authorization: Bearer <token>` in OIDC mode, `Authorization: Basic <base64(user:pass)>` in password mode. The helper public API does not change beyond accepting the discriminated `req.user.creds` shape.
- [x] **MODE-05**: At server startup, if the persisted last-known `AUTH_MODE` differs from the current value, the entire `sessions` table is wiped in a single SQLite transaction. Mirrors v1.0's `AUTH_SECRET` rotation pattern. The `kbi_session` cookie's `v: 1` field is NOT bumped — the credential discriminant lives in the session row, not the JWT payload.
- [x] **MODE-06**: The `id_token` is also stored encrypted in the session row (separate column) alongside the access token. Enables future surfacing of user claims (email, display name) without a UserInfo round-trip. (Differentiator D-2.)

### User Experience

User-visible behavior — most reuses v1.0's existing chain unchanged. Extends v1.0 UX-01..03.

- [x] **UX-04**: BI session TTL stays at 8 hours regardless of IdP token expiry. If the IdP issues 1-hour access tokens, the user re-authenticates roughly hourly via the existing 401-REAUTH flow without losing their BI session expiration semantics.
- [x] **UX-05**: When the IdP-issued access token expires mid-session, the next Kinetica call returns 401 → `KineticaAuthError` → existing v1.0 Phase 3 middleware emits `code: "REAUTH_REQUIRED"` → frontend's UNAUTHORIZED_EVENT fires → in OIDC mode, the user is redirected to `/api/auth/oidc/start` instead of seeing a password form. No new error chain — the v1.0 chain handles it.
- [x] **UX-06**: After a successful OIDC callback completes a fresh session, the user lands back at the page they were on when the re-auth was triggered (not a generic dashboard). Implementation may use `sessionStorage` to remember the pre-redirect path.
- [x] **UX-07**: Local logout (`POST /api/auth/logout`) destroys the BI session row and clears the cookie identically to v1.0. The user remains logged in at the IdP — single sign-on across the broader org is preserved. No RP-initiated logout to the IdP's `end_session_endpoint`.
- [x] **UX-08**: `GET /api/auth/me` includes `authMode` in its response so the frontend can conditionally render mode-specific UX (e.g., the SSO button vs. the password form, the post-logout messaging) without hard-coding the mode at build time. (Differentiator D-3.)

### Observability

Extends v1.0 OBS-01.

- [x] **OBS-02**: The per-Kinetica-call audit log JSON line includes a new `auth_mode: "password" | "oidc"` field. Distinguishes traffic in deployments that have migrated between modes. (Differentiator D-4.)

### Operations / Deploy

- [x] **OPS-01**: Phase 1's `DEPLOY-RUNBOOK.md` is extended (or a new section appended) documenting the Kinetica server's OIDC trust configuration prereqs: issuer URL, expected audience, JWKS URL, claim-to-Kinetica-username mapping. The runbook makes clear that this is a DBA task on the Kinetica server itself, separate from the BI app's `AUTH_OIDC_*` env vars. Not optional — Kinetica trust misconfiguration is the #1 documented v1.1 deployment failure mode (PITFALLS O-04, I-06).

## Out of Scope

Explicitly excluded for v1.1. Documented to prevent scope creep.

| Feature | Reason |
|---------|--------|
| Dual-auth mode (password AND OIDC active simultaneously per deployment) | Doubles login surface area; mutually-exclusive `AUTH_MODE` is the locked architectural decision. Migration handled by switchover, not coexistence. |
| Account linking (existing password user → new OIDC user identity) | Only meaningful in dual-auth mode; rejected by AF-3. Username mapping is a Kinetica admin task at deploy time. |
| Storing the access token in the JWT cookie (stateless OIDC) | Cookie size limits + every-request overhead. Encrypted session-row storage is the v1.0 architecture and remains the right choice. |
| IdP discovery / selection UI ("Which IdP do you use?") | Single-IdP-per-deployment is the v1.1 model. No tenant-selectable IdP. |
| "Last used IdP" persistence | Single-IdP per deployment — nothing to remember. |
| Surfacing raw OIDC error codes to the user | `access_denied`, `invalid_request`, etc. are unhelpful to end users and may leak config details. Map to friendly messages; log raw error server-side. |
| Allowing users to switch between password and SSO mid-session | Mutually exclusive `AUTH_MODE` makes this impossible by design. Each mode's inactive routes return 405. |
