# Requirements: Kinetica BI

**Defined:** 2026-04-27
**Core Value:** Click-through data exploration over Kinetica-backed dashboards.
**Milestone:** v1.0 — Authentication & Per-User Access

## v1.0 Requirements

Requirements for the Authentication & Per-User Access milestone. Each maps to roadmap phases.

### Session Storage

- [x] **SESS-01**: Server persists the BI user's Kinetica password between requests, encrypted at rest with AES-256-GCM
- [x] **SESS-02**: Session cookie carries an opaque session id only — no plaintext credentials in the cookie payload
- [x] **SESS-03**: Logout destroys the server-side session row (not just the cookie)
- [x] **SESS-04**: Session TTL is 8 hours — no extension, no sliding window in this milestone
- [x] **SESS-05**: Expired session rows are cleaned up (no unbounded growth of the sessions table)

### Credential Passthrough

- [x] **CRED-01**: Every Kinetica/gpudb API call routes through a single helper that uses the authenticated user's credentials
- [x] **CRED-02**: SQL proxy (`POST /api/sql`) uses the user's Kinetica credentials
- [x] **CRED-03**: Schema/table/column discovery (`GET /api/kinetica/schemas`, `…/tables`, `…/columns`) uses the user's Kinetica credentials
- [x] **CRED-04**: View materialization (`POST /api/views/:id/materialize`) uses the user's Kinetica credentials
- [x] **CRED-05**: WMS proxy (`GET /api/wms`) uses the user's Kinetica credentials
- [x] **CRED-06**: A user with restricted Kinetica permissions sees only the schemas, tables, and rows that user is granted

### Admin Credential Removal

- [x] **ADMN-01**: `KINETICA_USERNAME` and `KINETICA_PASSWORD` env vars are removed from the server entirely
- [x] **ADMN-02**: `requireConfig` middleware is narrowed to whatever Kinetica config is still required (e.g., `KINETICA_URL` only) or removed in favor of boot-time validation
- [x] **ADMN-03**: `.env.example` is updated to reflect the new contract (no admin creds; `AUTH_SECRET` and any new encryption-key variable documented)
- [x] **ADMN-04**: Server boots and operates with `KINETICA_USERNAME`/`KINETICA_PASSWORD` unset

### Auth Failure UX

- [x] **UX-01**: When a downstream Kinetica call fails authentication mid-session, the BI app drops the user back to the login screen with a "your session has ended, please sign in again" message
- [x] **UX-02**: When Kinetica returns a 403 (authorization denied for a specific table/operation), the BI app surfaces the error inline on the affected widget — the user is NOT logged out
- [x] **UX-03**: The BI server distinguishes "your session is dead" (returns 401 with `code: "REAUTH_REQUIRED"`) from "you don't have permission for this resource" (returns 403) so the frontend can dispatch correctly

### Observability

- [x] **OBS-01**: Every Kinetica call emits a server log line capturing username, route/operation, and outcome (success / auth-fail / upstream-error) — no credentials, no full SQL bodies that may contain PII

## Out of Scope

Explicitly excluded for v1.0. Documented to prevent scope creep.

| Feature | Reason |
|---------|--------|
| Storing credentials anywhere on the client (localStorage, sessionStorage, Zustand persist) | Anti-feature — credentials live only on the server, encrypted |
| Admin-credential fallback when user creds fail | Defeats the milestone goal — every call must use the user's creds, no escape hatch |
| Echoing credentials back to the client (in `/api/auth/me` or anywhere else) | Server holds them; client never receives them in any form |
| Cross-user response cache | Risks leaking one user's data to another with different Kinetica permissions |
| "Acting as" / impersonation for admins | Out of milestone scope; if needed, separate phase with explicit permission model |
| Real-time streaming / auto-refresh | Pre-existing exclusion; complexity not justified for v1 |
| Mobile app | Web-first |
| Custom SQL editor | Structured query builder is sufficient |
| Export / download functionality | Defer to v2 |
