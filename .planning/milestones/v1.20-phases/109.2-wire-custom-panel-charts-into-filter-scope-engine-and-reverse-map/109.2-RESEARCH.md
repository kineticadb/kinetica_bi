# Phase 109.2: Wire Custom-Panel Charts into Filter-Scope Engine and Reverse-Map - Research

**Researched:** 2026-07-10
**Domain:** v1.18/v1.20 filter-combination engine internals (React + Zustand, no new libs)
**Confidence:** HIGH (all findings verified by direct source read + git history; no external/Context7 lookups needed — this is 100% in-repo architecture research)

## Summary

The bug is real but narrower — and in one place, worse — than the roadmap's framing suggests. `NON_TRIGGER_TYPES` in `useCombinationOrchestrator.ts` and its hand-mirrored twin in `useReverseFilterMap.ts` both list `"calendar"`, `"timeline"`, `"numericline"`, which skips these three widget types entirely out of the STEP-A enumeration loop that mints a `vizToHash` binding. Because Timeline/NumericLine renderers are pure **consumers** of `filterCombinationStore.vizToHash` (they never write it), the practical effect today is that Timeline and NumericLine **always read the fully unfiltered base table** — not "unscoped" (all filters), but zero filters, always, regardless of any active dashboard filter. Calendar is worse: its `respondToFilters` read path subscribes to `useFilterViewStore.views[tableId]` / `.dvViews[dynamicViewId]`, a table-path store that **nothing has written to since Phase 91** (`AggregatedWidgetRenderer`'s Effect 1 — the only writer — was deleted in Phase 91/94; `FilteringBadge.tsx`'s own Phase-96-01 comment independently documents this exact same dead-store fact). So Calendar's `respondToFilters: true` path is provably dead code today: `fvViewName` never resolves, and after the calendar's own click handler calls `markMaterializing` on that same dead store it gets **permanently stuck** (suspend gate never lifts). `respondToFilters: false` (the default) at least deterministically reads the unfiltered base table — which is why "Calendar doesn't apply its configured filter scope at all" is the accurate description for Calendar specifically.

The good news: the two "is this a filter SOURCE" vs "is this a scope-bound CONSUMER" concepts the roadmap worried about conflating are **already fully separate, orthogonal sets** in this codebase. `FILTER_PRODUCING_TYPES` (`filterSourceTypes.ts`) is the filter-SOURCE set and **already includes** `"calendar"`, `"timeline"`, `"numericline"` (has for phases) — completely independent of `NON_TRIGGER_TYPES`/`isTriggerType`, which governs something else entirely: "does this widget need its own scoped materialized-view entry (a `vizToHash` binding) in the combination engine." `"bar"`/`"pie"`/`"table"` are simultaneously filter sources (`FILTER_PRODUCING_TYPES`) AND trigger/scope-bound types (`isTriggerType`) today with zero conflict — that's the existing, working precedent. **There is no real risk of "becoming a filter source"** by editing `NON_TRIGGER_TYPES` — that risk doesn't exist in this codebase's actual design. The minimal-risk fix for Timeline/NumericLine is a 2-line-per-file edit (remove 3 strings from 2 `Set` literals) with **zero renderer code changes** — their existing `vizToHash` read paths (already written and already unit-tested against a *mocked* combo store) will "just work" the moment the orchestrator starts populating their bindings.

Calendar is the real work in this phase: it needs a full read-path swap (mirror Timeline's `vizToHash`-based FROM-target resolution, including the dv branch which must mirror `WidgetRenderer.tsx`'s `AggregatedWidgetRenderer` dv branch, since Timeline/NumericLine have no dv picker to copy from), **deletion of `respondToFilters`** end-to-end (type, default, checkbox, renderer gate, dead `filterViewStore` reads), and — the subtle part — a **read-time coalesce function** that must be applied consistently at every site that currently reads `w.config.filterSelection` raw for a calendar widget (the orchestrator's table loop, the orchestrator's dv loop, and `useReverseFilterMap.ts`'s `enumerateVizDescriptors`), plus, to avoid a known bug class this project has hit before ("badges reading a legacy store go stale"), the on-card `WidgetFilterBadge`'s `cfg` source in `WidgetCard.tsx`.

**Primary recommendation:** (1) Remove `"calendar"`, `"timeline"`, `"numericline"` from `NON_TRIGGER_TYPES` in both `useCombinationOrchestrator.ts` and `useReverseFilterMap.ts` (keep them as two independently-edited literal `Set`s — this is the established, already-precedented pattern; do NOT extract a shared constant module in this phase). (2) Add one new pure helper, `coalesceCalendarFilterSelection`, and thread it through the 4 read sites that touch calendar's `config.filterSelection`. (3) Swap `CalendarRenderer.tsx`'s FROM-resolution to the `vizToHash` pattern (mirror `TimelineRenderer.tsx`'s table-path exactly; mirror `WidgetRenderer.tsx`'s `AggregatedWidgetRenderer` dv-branch for the dv path). (4) Delete `respondToFilters` from `CalendarConfig`, `DEFAULT_CALENDAR_CONFIG`, `CalendarConfigPanel.tsx`'s checkbox UI, and `CalendarRenderer.tsx`'s gating logic + dead `filterViewStore` imports/reads.

### Pattern 1: `isTriggerType` is "needs a scope-bound vizToHash entry," NOT "is a filter source"
**What:** `useCombinationOrchestrator.ts`'s `NON_TRIGGER_TYPES` (lines 70-81) gates 4 things, ALL currently already-generic and requiring **zero further changes** once the 3 strings are removed:
1. `widgetsKey` memo (line 119-131) — the Effect-dependency stability key for table-bound trigger widgets.
2. `dvWidgetsKey` memo (line 146-154) — same, for dv-bound trigger widgets.
3. STEP A table loop (line 208-241) — builds `byTable` hash-map entries (drives materialize dispatch) AND sets `vizKeyToHash.set('w:<id>', hash)` (the actual binding Timeline/NumericLine/Calendar need to read).
4. STEP A dv loop (line 283-312) — same, for dv-bound widgets.

STEP B (ceiling), STEP C (desired-set build), STEP D (dispatch/dedup), and STEP E (vizToHash sync + ref-count) are **entirely generic** already — none of them special-case widget type; they operate purely on the `byTable`/`byDv` maps and `vizKeyToHash` built by STEP A. STEP E's "which vizKeys left the dashboard" tracking (`currentVizKeys`, line 600-608) is **already unconditional over ALL widgets/layers regardless of trigger type** — so release-on-removal for calendar/timeline/numericline already works correctly today (they're just never *acquired* in the first place).

**Why this is the exact right/only edit:** `FILTER_PRODUCING_TYPES` (`components/charts/filterSourceTypes.ts`, lines 18-28) is a **completely separate, unrelated `Set`** that already lists `"bar"`, `"line"`, `"pie"`, `"scatter"`, `"table"`, `"datafilter"`, **`"calendar"`, `"timeline"`, `"numericline"`** — i.e., these three widgets are *already* filter sources today (used by `FilterSelectionPanel` to build its source-widget checklist) and coexist fine with `"bar"`/`"pie"`/`"table"` being BOTH sources AND trigger-types simultaneously. There is no mechanism anywhere in the codebase that treats "in `isTriggerType`" as "is a source" — that would require checking `FILTER_PRODUCING_TYPES`, which nothing conditions on `isTriggerType`. **Removing these 3 types from `NON_TRIGGER_TYPES` cannot make them "become sources"** — they already are, unconditionally, today, and that's correct/desired/unaffected.

**When to use:** This is the whole engine-side fix. Apply verbatim — no new `SCOPE_BOUND_TYPES` set, no reclassification scheme. The existing `isTriggerType`/`NON_TRIGGER_TYPES` concept is already exactly "scope-bound combo-store consumer," it's just missing 3 entries.

### Pattern 2: The calendar legacy-migration coalesce — WHERE it must and must NOT be applied
**What:** `respondToFilters` was a per-calendar boolean (`false` = default = always read unfiltered; `true` = "filter-aware," but dead since Phase 91 — see Pitfall 1). Locked migration: `respondToFilters:false` (or the historical implicit-absent-before-Phase-68 case) → `filterSelection` allow-list = **empty** ("respond to none"); `respondToFilters:true` → `filterSelection` = **undefined** (accept-all/default scope). Critically, **a brand-new calendar created after this phase ships** (where the `respondToFilters` key is never written at all, because the field and checkbox no longer exist) must ALSO resolve to accept-all — matching every other chart type's convention — NOT "respond to none." Since `respondToFilters === false` and `respondToFilters === undefined` have ALWAYS meant the same thing historically (`CalendarRenderer.tsx`'s current gate is `cfg.respondToFilters ?? false`), the only reliable signal to distinguish "pre-migration persisted calendar" from "calendar created before OR after respondToFilters existed at all" is **key presence**, not value:

```typescript
// packages/web/src/lib/coalesceCalendarFilterSelection.ts (NEW)
import type { FilterSelectionConfig } from "../types/filterSelection";

// Legacy calendar migration (Phase 109.2 — FSCOPE-V120-05).
// - cfg.filterSelection present (any value) -> use it as-is (explicit scope always wins).
// - cfg.filterSelection absent AND "respondToFilters" key present in the persisted config
//   (a calendar saved between Phase 68 and Phase 109.1, before this migration) ->
//     respondToFilters === true  -> undefined (accept-all / default scope)
//     respondToFilters === false -> { sourceMode: "allowlist", allowedSourceWidgetIds: [] } (respond to none)
// - cfg.filterSelection absent AND "respondToFilters" key absent (either a genuinely brand-new
//   calendar created after this phase ships, where the field no longer exists at all, OR a
//   pre-Phase-68 calendar that predates the field entirely) -> undefined (accept-all), matching
//   every other chart type's DEFAULT_FILTER_SELECTION convention.
export function coalesceCalendarFilterSelection(
  cfg: Record<string, unknown>,
): FilterSelectionConfig | undefined {
  if (cfg.filterSelection !== undefined) {
    return cfg.filterSelection as FilterSelectionConfig;
  }
  if (Object.prototype.hasOwnProperty.call(cfg, "respondToFilters")) {
    return cfg.respondToFilters === true
      ? undefined
      : { sourceMode: "allowlist", allowedSourceWidgetIds: [] };
  }
  return undefined;
}
```

**When to use — the 4 (+1 optional) call sites, exact and complete:**
1. `useCombinationOrchestrator.ts` STEP A table loop (~line 213): `const cfg = w.type === "calendar" ? coalesceCalendarFilterSelection(w.config) : (w.config.filterSelection as FilterSelectionConfig | undefined);`
2. `useCombinationOrchestrator.ts` STEP A dv loop (~line 293): same conditional, applied AFTER the existing `dvScopeDisabled ? undefined : ...` branch (i.e., `dvScopeDisabled` still short-circuits to accept-all first; only when NOT disabled does the calendar coalesce apply).
3. `useReverseFilterMap.ts`'s `enumerateVizDescriptors` widget loop (~line 79): `cfg: w.type === "calendar" ? coalesceCalendarFilterSelection(cfg) : (cfg.filterSelection as FilterSelectionConfig | undefined),`
4. `WidgetCard.tsx`'s `WidgetFilterBadge` `cfg` prop (~line 143): same conditional — **required** to avoid the exact "badge reads a stale/wrong source" bug class this project has hit before (see Pitfall 4).
5. (Optional, recommended, low-risk) `CalendarConfigPanel.tsx`'s `FilterSelectionPanel value=` prop (~line 727): pass `coalesceCalendarFilterSelection(cfg)` instead of raw `cfg.filterSelection` so a designer opening a legacy calendar's config SEES the true resolved state ("Customize ON, all sources unchecked") rather than a misleading "Accept all filters" hint. Purely a display read — `patch()` is only called on user interaction, so this cannot corrupt persisted config; the first real interaction writes a concrete `filterSelection` and the widget never needs coalescing again.

**Anti-pattern to avoid:** Do NOT apply the coalesce inside `resolveFilterSet.ts`/`resolveSpatialShapes.ts`/`stableComboHash.ts` (the shared pure resolvers). Those are widget-type-agnostic and used by bar/pie/table/timeline/numericline/layers too — baking a calendar-specific legacy check into a shared resolver would be exactly the kind of hidden coupling this project's `filterSourceTypes.ts` header comment (`"records" is intentionally EXCLUDED`) warns against. Keep the coalesce as a calendar-only pre-step, applied by each of the (small, enumerable) call sites, exactly as `dvScopeDisabled` is already handled today (a call-site-level `cfg = condition ? X : Y` right before invoking the shared resolver) — mirror that existing convention.

### Pattern 3: Calendar's read-path swap — mirror Timeline for table-bound, mirror `AggregatedWidgetRenderer`'s dv-branch for dv-bound
**What:** `CalendarRenderer.tsx` currently resolves its FROM target via (`respondToFilters` gate) → `useFilterViewStore.views[tableId]` / `.dvViews[dynamicViewId]` (dead store, see Pitfall 1). Replace with the SAME `vizToHash`-based pattern `TimelineRenderer.tsx` already uses for its table path (lines 224-239 of `TimelineRenderer.tsx`):
```typescript
// Source: TimelineRenderer.tsx:224-239 (existing, working pattern to mirror verbatim for
// Calendar's table-bound path)
const vizKey = `w:${widget.id}`;
const fvViewName = useFilterCombinationStore((s) => {
  const h = s.vizToHash[vizKey];
  return h && !h.endsWith(`:${NOFILTER_SENTINEL}`) ? (s.registry[h]?.viewName ?? "") : "";
});
const fvExpiresAt = useFilterCombinationStore((s) => {
  const h = s.vizToHash[vizKey];
  return h && !h.endsWith(`:${NOFILTER_SENTINEL}`) ? (s.registry[h]?.expiresAt ?? 0) : 0;
});
const fvMaterializing = useFilterCombinationStore((s) => {
  const h = s.vizToHash[vizKey];
  return h && !h.endsWith(`:${NOFILTER_SENTINEL}`) ? (s.registry[h]?.materializing ?? false) : false;
});
```
For Calendar's **dv-bound** path (Timeline/NumericLine have no dv picker — nothing to copy there), mirror `WidgetRenderer.tsx`'s `AggregatedWidgetRenderer` dv-branch instead (lines 586-602):
```typescript
// Source: WidgetRenderer.tsx:586-602 (AggregatedWidgetRenderer dv-branch) — mirror for
// CalendarRenderer's dv-bound FROM resolution (prefer dv-combo view, fall back to raw dv view).
const dvComboHash = useFilterCombinationStore.getState().vizToHash[vizKey];
const dvComboEntry =
  dvComboHash && !dvComboHash.endsWith(`:${NOFILTER_SENTINEL}`)
    ? useFilterCombinationStore.getState().registry[dvComboHash]
    : undefined;
const dvSource = dvComboEntry?.viewName || dvViewName; // dvViewName = raw dv view (unchanged read)
```
Delete: the `respondToFilters` local, the `dataFv*`/`dataDvFilter*` "neutralize when OFF" variables (lines 215-226 of current `CalendarRenderer.tsx`), the `if (respondToFilters) { ... } else { ... }` FROM-resolution branch (lines 285-329), and the `useFilterViewStore` import + `fvViewName`/`fvExpiresAt`/`fvMaterializing`/`dvFilterEntry`/`dvFilterViewName`/`dvFilterMaterializing` selectors (lines 190-213) — all of it becomes dead once the vizToHash pattern lands. **Keep** the click-handler's `useFilterViewStore.getState().markMaterializing(...)`/`markDvMaterializing(...)` calls in `handleCellClick` (lines 534-558) exactly as-is — Timeline's own `commitFilter` (line 472) keeps the identical legacy call for consistency/parity even though it too is now vestigial (nothing reads it); removing it is optional cleanup, not required, and out of scope here (don't touch Timeline in this phase).

**When to use:** This IS the calendar renderer migration. Every piece has a working, already-tested sibling to copy from — no novel logic.

### Anti-Patterns to Avoid
- **Do NOT introduce a new `SCOPE_BOUND_TYPES` set.** `NON_TRIGGER_TYPES`/`isTriggerType` already means exactly this; a second set would be redundant and a future drift risk (which set does a new widget type need to be removed from?).
- **Do NOT gate the coalesce inside the shared resolvers** (`resolveFilterSet`/`resolveSpatialShapes`/`stableComboHash`) — keep it a calendar-only, call-site-level branch (mirrors the existing `dvScopeDisabled` convention).
- **Do NOT touch Timeline/NumericLine renderer code.** Their `vizToHash` read paths are already correct and already unit-tested against a mocked combo store (see § Common Pitfalls / Blast Radius) — the ONLY thing missing was the orchestrator populating the binding.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| "Does this filter-scope config mean 0 filters apply?" | A new "is this NOFILTER" check | `stableComboHash(...).endsWith(':' + NOFILTER_SENTINEL)` (existing, already used everywhere) | Already the single source of truth; empty-allowlist naturally produces this sentinel via `resolveFilterSet`/`resolveSpatialShapes` returning `[]` — verified in `stableComboHash.ts` lines 45-48. No new "empty scope" concept needed. |
| Calendar's dv-bound FROM-target resolution | A bespoke calendar-specific dv-combo reader | Copy `WidgetRenderer.tsx`'s `AggregatedWidgetRenderer` dv-branch (lines 586-602) verbatim | Already handles the "prefer combo view, fall back to raw dv view, defensive-error on missing viewName" contract correctly; a second bespoke implementation risks silently diverging. |
| Legacy-flag migration | A server/DB migration script rewriting persisted `respondToFilters` → `filterSelection` | Read-time coalesce (`coalesceCalendarFilterSelection`) | Roadmap-locked decision; frontend-only, self-healing on first designer edit, zero server/data-layer risk this late in the milestone. |

**Key insight:** every piece of machinery this phase needs (hash sentinel, dv-combo resolution pattern, empty-allowlist semantics) already exists and is already exercised by bar/pie/table/records/Timeline/NumericLine. This phase is proportioned almost entirely to (a) two 1-line-diff `Set` edits, and (b) Calendar catching up to a pattern its siblings already use — not net-new engine design.

## Common Pitfalls

### Pitfall 1: Calendar's `respondToFilters:true` path is dead code TODAY (verify this before assuming it "half-works")
**What goes wrong:** Assuming `respondToFilters:true` currently gives Calendar *some* filter-aware behavior (just unscoped) that this phase needs to "narrow." It does not — it is completely non-functional.
**Why it happens:** `CalendarRenderer.tsx` reads `useFilterViewStore.views[tableId]` (table path) / `.dvViews[dynamicViewId]` (dv path). `AggregatedWidgetRenderer`'s Effect 1 — the ONLY code that ever called `setView`/`setDvView` on this store — was deleted in Phase 91 (table path) and Phase 94 (dv path); its own comment block (`WidgetRenderer.tsx` lines 500-506) documents the removal. `FilteringBadge.tsx`'s Phase-96-01 header comment independently confirms: *"nothing writes/clears filterViewStore.views[tableId].materializing anymore."* Net effect: `fvViewName`/`dvFilterViewName` never resolve (stay `undefined`/`""`) → FROM falls through to the base/unfiltered table. Worse: Calendar's OWN `handleCellClick` calls `useFilterViewStore.getState().markMaterializing(tid, dashboardId)` (line 537) — since nothing ever calls the matching `setView`/`clearView` to resolve it, `fvMaterializing` becomes permanently `true` after the FIRST cell click, and the fetch effect's suspend gate (`if (dataFvMaterializing) return;`) then blocks Calendar from ever re-fetching again for that session.
**How to avoid:** Don't try to "fix" the legacy path (e.g., by making something call `setView` again) — fully replace it per Pattern 3. Confirm during implementation (a quick manual grep + the removed `filterViewStore` import) that `CalendarRenderer.tsx` has zero remaining `filterViewStore` READ references after the migration (the two WRITE calls in `handleCellClick`, `markMaterializing`/`markDvMaterializing`, are kept for Timeline-parity per Pattern 3 — those are harmless now, not reintroducing the bug, since nothing reads them either).
**Warning signs:** A "fix" that keeps `useFilterViewStore.views[tableId]` as a read source anywhere is wrong — it can never resolve.

### Pitfall 2: The reverse-map (`enumerateVizDescriptors`) is config-only — it does NOT read the combo store
**What goes wrong:** Assuming the applies-to count/highlight (Phase 108) will "automatically" become correct once the orchestrator binds vizToHash, without also editing `useReverseFilterMap.ts`.
**Why it happens:** `computeReverseFilterMap` (the pure lib backing the panel) re-derives "does filter X apply to viz Y" purely from `resolveFilterSet(viz.cfg, activeFilters)` — it is intentionally decoupled from the combo store/materialization state entirely (by design, per its own header comment: "Badge data is computed LOCALLY — do NOT read filterCombinationStore here," which is actually `useFilterScopeSummary.ts`'s comment but the same design principle holds for the reverse-map). This means the "applies-to" DISPLAY logic and the orchestrator's actual materialize/read-path logic are two SEPARATE code paths that must independently agree — editing one without the other produces a display that's accurate-in-isolation but disagrees with what the chart actually renders (the exact symptom already reported: "isn't highlighted + wrong applies-to count").
**How to avoid:** Both `NON_TRIGGER_TYPES` edits (orchestrator AND reverse-map) are required, in the same commit/task — this phase's own plan should treat them as one atomic change, not two independently-schedulable ones.
**Warning signs:** If only one of the two files is edited, a manual test would show either (a) correct highlight/count but the chart still shows wrong data, or (b) correct chart data but wrong highlight/count — both are incomplete-fix states.

### Pitfall 3: The "unset-new" migration case looks identical to "explicit-false" unless you check key presence, not value
**What goes wrong:** A naive coalesce (`cfg.respondToFilters === false ? empty-allowlist : undefined`) treats `undefined` (brand-new calendar, field genuinely never existed) the SAME as explicit `false` (a real legacy calendar defaulted OFF) — both currently read as `false` via `cfg.respondToFilters ?? false`. Since `respondToFilters:false` has ALWAYS been `DEFAULT_CALENDAR_CONFIG`'s value since Phase 68 (i.e., essentially every existing calendar in the DB has this key set to `false` unless a designer explicitly toggled it ON), and the field is being deleted from the type/UI in this same phase, a coalesce keyed on VALUE rather than PRESENCE would make brand-new post-migration calendars silently default to "respond to none" instead of "accept all" — breaking every other widget type's accept-all convention for a subtle, hard-to-notice reason.
**How to avoid:** Use `Object.prototype.hasOwnProperty.call(cfg, "respondToFilters")` (key presence) as the discriminator, exactly as specified in Pattern 2's `coalesceCalendarFilterSelection`. `JSON.stringify`/round-trip through the SQLite JSON config column never persists an `undefined`-valued key, so "key present" reliably means "this config was saved by code that still had the `respondToFilters` field" (Phase 68 through Phase 109.1, inclusive) — a real, finite, closed window.
**Warning signs:** A test seeding `{ tableId: 1 }` (no `respondToFilters` key at all, simulating a brand-new post-migration widget) that asserts accept-all (`filterSelection === undefined` end-to-end, i.e., applies ALL active filters) is the regression guard for this pitfall — make sure the plan includes exactly this test case, distinct from the `{ tableId: 1, respondToFilters: false }` "legacy, respond to none" case.

### Pitfall 4: On-card badges are GENERIC and unconditional — they will start rendering for these 3 types the moment enumeration changes, whether or not you've coalesced them
**What goes wrong:** `WidgetCard.tsx` renders `<FilteringBadge>`/`<WidgetFilterBadge>` unconditionally for every non-`"map"` widget type already (lines 134-152) — this is NOT gated by `NON_TRIGGER_TYPES` at all. `FilteringBadge` will start correctly showing "Filtering..." for calendar/timeline/numericline the moment they get a `vizToHash` binding (its `registry` scan is already type-agnostic — no change needed there). But `WidgetFilterBadge` reads `w.config.filterSelection` RAW (line 143) — for a legacy calendar (`respondToFilters:false`, `filterSelection` absent), this raw read is `undefined` → `resolveFilterSet` treats it as accept-all → the badge computes `appliedCount === totalCount` → renders NOTHING (no "N of M filters" indicator) — silently implying "this widget takes all filters," when the ACTUAL post-migration behavior (once the orchestrator coalesce lands) is "this widget takes ZERO filters." This is precisely the "badges reading a legacy/wrong source go permanently stale" bug class this project has been bitten by twice already (`FilteringBadge`'s own Phase-96-01 fix, and the `filterCombinationStore` migration for filtering badges more broadly).
**How to avoid:** Apply the SAME `coalesceCalendarFilterSelection` conditional at `WidgetCard.tsx`'s `WidgetFilterBadge` `cfg=` prop (Pattern 2, call site 4). This is a small, isolated, additive change (no existing test references calendar/`filterSelection` in `WidgetCard.spec.tsx` today — confirmed via grep — so this is pure net-new coverage, zero regression risk).
**Warning signs:** A live-UAT walk-through (Phase 110) opening a legacy calendar with an active filter from an excluded source and seeing NO "0 of N filters" badge (when Timeline/NumericLine/other widgets correctly show theirs) is the visual tell for this specific gap.

## Open Questions

   - Recommendation: include it — it's a ~3-line addition riding along in the same file/task as the `respondToFilters` checkbox removal (`CalendarConfigPanel.tsx`), essentially free, and prevents a designer from seeing a misleading "Accept all filters" hint on a widget that actually ignores all filters.

   - Recommendation: leave untouched — out of scope for FSCOPE-V120-05, and the roadmap explicitly scopes this phase to calendar/timeline/numericline's SCOPE-BINDING + calendar's `respondToFilters` retirement, not a broader `filterViewStore` deprecation sweep.
