# Phase 109.2 Plan 02: Wire Custom-Panel Charts into Filter-Scope Engine — Calendar Renderer Migration Summary

**Swapped CalendarRenderer's dead filterViewStore/respondToFilters read path to the filterCombinationStore.vizToHash pattern already used by Timeline/NumericLine, fully retired respondToFilters (type/default/checkbox/gating), and coalesced the config-panel display + on-card badge so both reflect the true post-migration scope for legacy calendars.**

## Accomplishments

- `CalendarRenderer.tsx`: table-path FROM resolution now reads `filterCombinationStore.vizToHash[vizKey]` → `registry[hash]` (verbatim mirror of `TimelineRenderer.tsx`'s selector triplet + proactive-expiry `clearEntry()` call); dv-path FROM resolution mirrors `WidgetRenderer.tsx`'s `AggregatedWidgetRenderer` dv-branch (prefer the dv-combo view, fall back to the raw dv view).
- Deleted `respondToFilters` local, the "neutralize when OFF" dep block (`dataFilterVersion`/`dataFvViewName`/etc.), the `if (respondToFilters) {...} else {...}` FROM branch, and the dead `filterViewStore` READ selectors — zero `filterViewStore` READ references remain (only the `markMaterializing`/`markDvMaterializing` WRITE calls in `handleCellClick`, kept for Timeline-parity).
- `CalendarConfigPanel.tsx`: removed `respondToFilters` from the `CalendarConfig` type, `DEFAULT_CALENDAR_CONFIG`, and the local; deleted the "Respond to dashboard filters" checkbox block entirely; `FilterSelectionPanel`'s `value=` now reads `coalesceCalendarFilterSelection(cfg)` so a legacy calendar's Filter Scope panel shows its TRUE resolved state instead of a misleading accept-all hint.
- `WidgetCard.tsx`: `WidgetFilterBadge`'s `cfg=` prop is coalesced for calendar widgets only (`w.type === "calendar"` branch) — a legacy `respondToFilters:false` calendar with an active filter from an excluded source now correctly renders the "N of M filters" badge instead of nothing; non-calendar widgets are unaffected (raw `filterSelection` read, unchanged).
- All three spec files updated: `CalendarRenderer.spec.tsx` gained a `filterCombinationStore` selector-aware mock (mirrors `TimelineRenderer.spec.tsx`) and vizToHash-based FROM-resolution tests replacing the retired respondToFilters-gated tests; `CalendarConfigPanel.spec.tsx` replaced the checkbox tests with coalesced-display tests; `WidgetCard.spec.tsx` gained a legacy-calendar badge test + a non-calendar regression guard.

## Note on the plan's blanket `grep -rn "respondToFilters" packages/web/src/` verification line

The plan's `<verification>` section states this grep should return NO matches "fully retired across src, including specs." This is stricter than the plan's own per-file `<acceptance_criteria>` (which scope the zero-match requirement to `CalendarRenderer.tsx` and `CalendarConfigPanel.tsx` specifically) and is not achievable without breaking the migration design shipped in Plan 01: `coalesceCalendarFilterSelection.ts` MUST reference the literal string `"respondToFilters"` to perform its `Object.prototype.hasOwnProperty.call(cfg, "respondToFilters")` key-presence discriminator (RESEARCH.md Pitfall 3) — this is the entire point of a read-time migration coalesce for a retired field. Its unit spec, the orchestrator/reverse-map specs (Plan 01), and this plan's own migration-behavior tests (asserting a legacy `{respondToFilters: false}` config still resolves correctly) necessarily reference the same string. Verified instead, per the plan's own acceptance criteria:
- `grep -c "respondToFilters" packages/web/src/components/charts/CalendarRenderer.tsx` → 0
- `grep -c "respondToFilters" packages/web/src/components/charts/CalendarConfigPanel.tsx` → 0

Both pass. The field is fully retired from the type, default, UI checkbox, and renderer gating — the only remaining references are the (by-design, Plan-01-shipped) migration discriminator and its test coverage.
