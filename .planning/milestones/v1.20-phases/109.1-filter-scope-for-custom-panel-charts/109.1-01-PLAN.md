<objective>
Calendar Heatmap, Timeline Chart, and Numeric Line Chart currently do NOT expose the v1.18 per-visualization filter-scope control (`FilterSelectionPanel`). Their `CustomConfigPanel` REPLACES `ChartConfigPanel`'s generic body, which is the only place `FilterSelectionPanel` renders. bar/pie/table (generic panel) already have it.

This plan adds `FilterSelectionPanel` to all three custom panels, mirroring `ChartConfigPanel`'s generic usage (source-widget allow-list + `selfWidgetId` self-exclusion + `allowSpatial` + the dv/`dvFilterScopeDisabled` gate), so those three charts become full filter-scope-capable targets. After this, v1.20's filter panel + applies-to mapping represent them correctly and Phase 110 verification covers the complete feature.

Purpose: Close FSCOPE-V120-04 — a frontend-only gap-fill.
Output: `widgetId` threaded through `ConfigPanelProps` + the `<Custom>` slot; `FilterSelectionPanel` rendered in the three custom panels; new + preserved specs green.

FRONTEND-ONLY. No store/server changes: `filterSelection` already persists in widget config and is already consumed by the read-path resolvers (`resolveFilterSet` / `useFilterScopeSummary` / `computeReverseFilterMap`). This is UI-only. No new requirement beyond FSCOPE-V120-04. Do NOT touch bar/pie/table.
</objective>

ConfigPanelProps (registry.ts) ALREADY includes `widgets?: WidgetDto[]` and `dynamicViews?: DynamicViewRow[]`. It does NOT include `widgetId` — this plan adds it.

FilterSelectionPanel prop contract (FilterSelectionPanel.tsx):
```typescript
type FilterSelectionPanelProps = {
  value: FilterSelectionConfig | undefined;                     // undefined = accept-all (default)
  onChange: (next: FilterSelectionConfig | undefined) => void;  // undefined = revert to accept-all
  widgets: WidgetDto[];                                         // filtered internally to filter-producing types
  selfWidgetId?: number;                                        // excluded from the source checklist
  allowSpatial?: boolean;                                       // default true; false hides the spatial sentinel (dv-bound)
};
```
FilterSelectionPanel renders its OWN `<div className="config-group">` with a `<div className="config-group-label">Filter Scope</div>` and a checkbox `aria-label="Customize"`. Do NOT double-wrap it. When `value` is undefined it shows the hint "Accept all filters".

FilterSelectionConfig (src/types/filterSelection.ts):
```typescript
export type FilterSelectionConfig = {
  sourceMode: "all" | "allowlist";
  allowedSourceWidgetIds: (number | string)[];
};
```

WidgetDto (src/api/client.ts): `{ id: number; ...; type: string; config: Record<string, unknown>; ... }`

Auth store field (src/store/auth.ts): `useAuthStore((s) => s.dvFilterScopeDisabled)` — boolean, defaults `false`.

THE GENERIC USAGE TO MIRROR (ChartConfigPanel.tsx ~lines 939-953):
```tsx
const filterSourceWidgets =
  draftDynamicViewId !== undefined
    ? (widgets ?? []).filter((w) => (w.config.dynamicViewId as number | undefined) === draftDynamicViewId)
    : (widgets ?? []);
return selectedSource && !(draftDynamicViewId !== undefined && dvFilterScopeDisabled) && (
  <FilterSelectionPanel
    value={draft.filterSelection as FilterSelectionConfig | undefined}
    onChange={(next) => set("filterSelection", next)}
    widgets={filterSourceWidgets}
    selfWidgetId={widgetId}
    allowSpatial={draftDynamicViewId === undefined}
  />
);
```
In the custom panels the equivalents are: `set(...)` → the panel's `patch({...})`; `draft` → `cfg`/`config`; `draftDynamicViewId` → `cfg.dynamicViewId`; `selectedSource`/has-data-source → already satisfied because the block sits inside each panel's `tableId !== undefined` render branch. Calendar dual-writes `tableId` when dv-bound, so `tableId !== undefined` is true for dv-bound Calendar too.
