## v1.12 Drill-Down on Dynamic-View-Backed Widgets — Phase Details

> **Status:** 🚧 active (started 2026-06-15). A focused bug-fix-as-feature spanning both stacks. Restores click-through exploration (the v1.3 core value) for **dynamic-view-backed** widgets: drilling a dv widget filters the **dynamic view's own data**, isolated to widgets on that same dv — the source table and other dvs are untouched. Root-caused this session; no new domain research. Phase numbering continues from 61.

**Locked invariants (carry into every phase's success criteria):**
- `AggregatedWidgetRenderer` remains the **SOLE materialize trigger** (static-grep asserted; no new trigger added).
- **DV-isolated scope:** a dv drill filters ONLY that dynamic view; same-dv widgets update, source-table + other-dv widgets are untouched.
- **Table-backed drill-down path is UNCHANGED** (the existing `tableId`-keyed path keeps working; the dv path is added alongside).
- **No new server routes** — extend `POST /api/filter/materialize` only.
- **Test gates (separate gates):** frontend vitest 100% run from `packages/web`; web `tsc` clean; server `tsc` clean; server vitest is a **SET-BASED** gate (failing files ⊆ TD-V16-TEST-ISOLATION known-flaky list — NEVER a fixed pass-count).

### Phase 63.1: Map-Layer DV-Filter FROM-Swap (gap closure)
**Goal**: A WMS map layer bound to a dynamic view renders the **filtered-dv view** (`_kbi_filt_…_dv<id>_s…`) when a chart/table drill-down has materialized a dv filter, and reverts to the raw dv view when cleared — so map widgets update LIVE in lock-step with dv-bound charts. Closes the gap where the map kept rendering the unfiltered `_kbi_dv_…` view.
**Stack**: FRONTEND-ONLY (`packages/web`). ZERO server change — the dv-filter view is already materialized by the chart's Effect 1 (Phase 63); the map is a pure consumer.
**Depends on**: Phase 63
**Requirements**: DVDRILL-V112-02, DVDRILL-V112-04 (map render path)
**Success Criteria** (what must be TRUE):
  1. A dv-backed WMS map layer whose dv has an active materialized dv-filter emits `LAYERS=<filtered-dv viewName>` + `_mv=<dvFilter.materializeVersion>` — NOT the raw `_kbi_dv_…` name.
  2. Clearing the dv filter reverts the layer to the raw dv view; a dv-backed layer whose dv has NO filter, and any table-backed layer, are byte-unchanged (isolation).
  3. A dv-filter apply/clear/re-materialize re-fires the WMS layer rebuild (new `dvFilterViewsKey` subscription); the map visibly updates.
  4. Sole-materialize-trigger preserved (no `materializeFilter`/`dropFilterView` added to MapChartRenderer); frontend vitest 100% from `packages/web`; web tsc clean; zero `packages/server` diff.
**Plans**: TBD

### Phase 62: Server — Materialize From DV View
**Goal**: `POST /api/filter/materialize` can build a filtered sub-view of a dynamic view's own materialized view (`FROM <dv_view> WHERE <filter>`) instead of always filtering the source table — the one server-side piece, no new route.
**Stack**: SERVER-ONLY (`packages/server`). No frontend constraint applies to this phase.
**Depends on**: Nothing (first phase of v1.12; builds on the existing v1.3 materialize + v1.6 dynamic-view foundations)
**Requirements**: DVDRILL-V112-03 (server portion)
**Success Criteria** (what must be TRUE):
  1. `POST /api/filter/materialize` accepts a dynamic-view source descriptor and materializes `FROM <dv materialized-view name> WHERE <clicked filter>`, returning the filtered-dv view name; the existing table-source request shape is unchanged (full back-compat).
  2. When the dv source is not yet materialized / over-threshold / missing, the route fails safe (no crash; an actionable error the client can surface — mirrors the existing dv empty/pending UX contract).
  3. Targeted server specs for the extended materialize path pass in both auth modes; server `tsc` clean; server vitest set-based gate stays ⊆ TD-V16-TEST-ISOLATION (no NEW failing files introduced).
  4. No new server route was added (the extension lives entirely inside the existing `POST /api/filter/materialize`).

### Phase 63: Client — DV Drill-Down (Keying + Routing + Read-Path + Chips/Lifecycle)
**Goal**: Clicking a drill-eligible element on a dv-backed widget filters that dynamic view's data live, isolated to same-dv widgets — via dv-safe filter keying, dv-aware drill dispatch, a filtered-dv read-path swap, and removable chips with lifecycle reset.
**Stack**: FRONTEND-ONLY (`packages/web`). No server constraint applies to this phase (the server piece lands in Phase 62).
**Depends on**: Phase 62 (consumes the extended materialize endpoint)
**Requirements**: DVDRILL-V112-01, DVDRILL-V112-02, DVDRILL-V112-04, DVDRILL-V112-05 (+ client side of DVDRILL-V112-03)
**Success Criteria** (what must be TRUE):
  1. Clicking a drill-eligible element (pie slice / bar / line-or-scatter point / table-or-records row) on a dv-backed widget applies a drill-down filter to the **dynamic view's data**, NOT a filter on the underlying source table — for all drill-capable widget types.
  2. The drill updates LIVE: the clicked widget AND every other widget bound to the SAME dynamic view re-render to the filtered slice, while source-table widgets and other-dv widgets stay unaffected (dv-isolated scope); filter state is keyed so a dv id can never collide with a table id.
  3. A dv-backed widget's read FROM-swaps to the filtered-dv view when a dv filter is active and falls back to the raw dv view when cleared (precedence filtered-dv → dv); over-threshold / not-yet-materialized dv states still render the existing empty/pending UX (no crash).
  4. A dv drill shows a removable chip identifying the dynamic view + clicked value; removing it reverts the dv's widgets to the unfiltered dynamic view; dv filters reset on dashboard-switch + logout (consistent with the table-filter lifecycle).
  5. `AggregatedWidgetRenderer` remains the sole materialize trigger (no new trigger introduced; static-grep asserted); frontend vitest 100% from `packages/web`; web `tsc` clean.
