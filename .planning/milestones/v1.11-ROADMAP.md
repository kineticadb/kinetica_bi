## v1.11 Programmable Widgets (Cross-Widget Control)

**Goal:** Widgets can programmatically change other widgets' configuration. Ship a generic, serializable widget-action engine ("apply this config patch to target Y") plus a first control widget — a radio group where each option applies a configured action to a target (e.g. switch a map layer's class-break render mode). Architect the action contract so a future AI chat widget / MCP server reuses the same envelope — but build NO AI and NO MCP server this milestone.

**Locked context (do NOT re-litigate at roadmap level):**
- Action contract = serializable `{ target, configPatch }` envelope + zod (the only new dep; also the future MCP `inputSchema`). NOT JSON-Patch, NOT a typed command union.
- A **versioned allow-list** (`ALLOW_LIST_VERSION`) of patchable fields per target kind / widget type is the AI-safety contract — ships in the engine foundation (Phase 58), never retrofitted. No free-form `Object.assign`.
- Engine routes to THREE target kinds: (a) `widget.config` + (b) map-layer config via `useDashboardLayersStore` incl. top-level `track_config`/`cb_config` (primary, verified) and (c) dynamic-view config (`dashboard_dynamic_views`, lighter verification).
- Same-dashboard targeting only; dangling target (deleted widget/layer/dv or absent field) fails safe (no-op + surfaced signal, no partial write).
- Read-once-at-mount is the #1 risk (prior GAP-24-01-A / track gaps 54-01..09) → mounted-renderer LIVE-re-render **canary test is a Phase 58 day-0 deliverable**; target renderers read live config at render time.
- Fully decoupled from drill-down/filter + sole-materialize-trigger; static source-grep assertion (DataFilterRenderer Phase 44 precedent).
- MCP/AI is DESIGNED-FOR + documented only (SEAM); NO new server routes — existing `PATCH /api/widgets/:id` + layer/dynamic-view PATCH routes suffice.
- One unresolved IMPLEMENTATION tension (resolve at discuss/plan-phase, NOT here): thin `applyWidgetAction()` function (STACK) vs `useWidgetActionEngine` orchestrator hook + overlay store (ARCHITECTURE). Roadmap does NOT pre-commit.

**Test-gate reality (carry into every phase's success criteria):**
- Frontend vitest is DETERMINISTIC → must be 100% green (run from `packages/web`).
- Server vitest is flaky → SET-BASED gate only (failing files ⊆ TD-V16-TEST-ISOLATION known-flaky set — NEVER a fixed pass-count).
- web + server `tsc --noEmit` clean as SEPARATE gates.
- Phases 58-60 are frontend-heavy — likely ZERO server changes (flag if a server diff appears). Phase 61 verifies both stacks.

### Phase Details

### Phase 58: Action Engine + Contract + Allow-List + Canary
**Goal**: A generic, serializable, allow-list-guarded widget-action engine that LIVE-patches any of three target kinds through the existing config PATCH path — with the read-once-at-mount trap closed by a day-0 canary test and the filter/materialize systems provably untouched. No UI.
**Depends on**: Nothing (first phase of the milestone; builds on the shipped v1.0–v1.10 app).
**Requirements**: ENGINE-V111-01, ENGINE-V111-02, ENGINE-V111-03, ENGINE-V111-04, SAFETY-V111-01, SAFETY-V111-02
**Success Criteria** (what must be TRUE):
  1. A serializable `{ target (kind + id), configPatch }` envelope is defined and zod-validated — no closures or component refs — and is the single shape every caller (the radio widget, a future AI/MCP layer) produces; a unit test round-trips it through JSON unchanged.
  2. A single dispatch path applies an action to a MOUNTED target widget which re-renders LIVE from the changed config with NO remount — proven by the mounted-renderer re-render canary test (dispatch action → assert visual/config update without unmount).
  3. Dispatch routes correctly to all three target kinds: (a) a widget's `config`, (b) a map layer's config via `useDashboardLayersStore` incl. the top-level `track_config`/`cb_config` fields, and (c) a dynamic-view's config — (a) and (b) verified with tests, (c) exercised at least once.
  4. An action whose target no longer exists (deleted widget/layer/dynamic-view) or whose field is absent is a safe no-op with a surfaced typed signal (e.g. `{ status: "target_not_found" }`) — no crash, no partial/corrupt write.
  5. A versioned allow-list (`ALLOW_LIST_VERSION`) defines exactly which fields are patchable per target kind / widget type; patches to unknown keys, wrong-type values, enum violations, or meta keys (`id`/`tableId`/`type`/`__proto__`) are rejected by validation (5 rejection-case unit tests), and a static source-grep assertion proves the engine never imports any filter-store symbol (`materializeFilter`/`dropFilterView`/`addFilter`/`setBulkFilters`) nor bumps `filterVersion`.
**Plans**: 2 plans
- [ ] 58-01-PLAN.md — Serializable action envelope + zod schema + versioned allow-list + validateActionPatch (ENGINE-01, SAFETY-01)
- [ ] 58-02-PLAN.md — Session overlay store + applyWidgetAction dispatch + 3-kind routing (incl. map-layer render path) + dangling safety + live-re-render canary + decoupling grep (ENGINE-02/03/04, SAFETY-02)

### Phase 58.1: Action-Engine Foundation Fix (INSERTED)

**Goal:** Make the Phase 58 widget-action engine actually patch a layer's render mode — the headline use case. Phase 58 shipped a foundation that silently can't: (1) the allow-list keys `render_mode` (snake) but the real field is `config.renderMode` (camelCase, NESTED in the layer's `config` blob), whereas `track_config`/`cb_config` are TOP-LEVEL `DashboardLayerDto` fields; (2) the layer overlay merge (`MapChartRenderer.effectiveLayers`) is a FLAT top-level spread `{ ...l, ...override }` that reaches top-level fields but NOT nested `config.renderMode`; (3) the Phase 58 canary only tested top-level track_config/cb_config, so it passed without exercising render mode. This is the `track-config-toplevel-field` class of bug recurring; discovered during Phase 59 planning.
**Depends on:** Phase 58
**Requirements**: ENGINE-V111-03 (corrected — re-verifies the nested-config routing it claimed)
**Success Criteria** (what must be TRUE):
  1. The allow-list (`actionAllowList.ts`) uses the REAL field names and encodes per-field LOCATION (top-level-on-DTO vs nested-in-`layer.config` vs `widget.config`) — `renderMode` (not `render_mode`) is correctly declared as nested in `layer.config`; `track_config`/`cb_config` stay top-level.
  2. The layer overlay merge DEEP-merges nested config fields into `layer.config` (so `config.renderMode` actually changes) while keeping top-level fields (track_config/cb_config) top-level — `{ ...l, config: { ...l.config, ...nested }, ...topLevel }`.
  3. A canary case dispatches a render-mode action and asserts the MOUNTED MapChartRenderer's effective layer reflects `config.renderMode` changed with NO remount (this case fails against current code — proving the gap — then passes).
  4. Frontend vitest 100% green (run from packages/web); web tsc clean; ZERO server changes.
**Plans**: 1 plan
- [ ] 58.1-01-PLAN.md — Allow-list per-field location metadata + `renderMode` rename + ALLOW_LIST_VERSION bump; location-aware layer patch routing in applyWidgetAction + deep-merge effectiveLayers; render-mode canary (CASE C); Phase 58 spec migration (ENGINE-V111-03)

### Phase 60: Radio Renderer + Wiring + Persistence + MCP Seam Doc
**Goal**: Selecting a radio option fires its action through `applyWidgetAction`, the target updates LIVE and the change persists across dashboard reload, the radio's own selected option persists, and the dispatch entry point is documented as the AI/MCP seam.
**Depends on**: Phase 58 (engine), Phase 59 (authored config to consume).
**Requirements**: RADIO-V111-03, SEAM-V111-01
**Success Criteria** (what must be TRUE):
  1. Selecting a radio option applies its action and the target widget/layer/dynamic-view updates LIVE in the same render cycle (no manual refresh, no remount); the renderer reads its config from the prop at render time (not a mount snapshot) and carries the DataFilterRenderer static-assertion comment.
  2. The applied change persists across a full dashboard reload, and the radio's own selected option (`selectedIndex` in its config) persists so the control shows the correct active option after reload without re-firing the action.
  3. The action-engine overlay/state resets on dashboard-switch and logout (added as the next store in the canonical lifecycle cleanup chain), so a switched-to dashboard does not show stale overrides.
  4. `applyWidgetAction` and the `{ target, configPatch }` envelope are documented (module header / planning note) as the hook a future AI chat widget / MCP server reuses, with the concrete MCP tool shape noted (envelope as zod `inputSchema`, calling the existing PATCH routes) — and NO AI widget and NO MCP server are built.

> **Persistence reframe (locked at 60-CONTEXT):** a viewer's runtime selection is transient (session overlay, no PATCH) and clears on reload/dashboard-switch via the existing `widgetActionStore.reset()` (7th-store cleanup). "The radio's selected option persists" is satisfied by the DESIGNER-configured `defaultOptionId` re-applying on open — consistent with the transient-for-everyone decision. Switch-replace requires the store refactor to control-keyed contributions.

### Phase 60.2: Radio Dashboard Control — Multi-Target Options (INSERTED 2026-06-13)

**Goal:** A single Radio Dashboard Control option can drive MULTIPLE targets at once. `RadioOption.action` becomes `actions: WidgetAction[]` (mixed widget/layer/dv targets); selecting an option applies all its actions as ONE control contribution; switching options is switch-replace at the OPTION level (targets the new option doesn't set revert). The config panel authors a per-option target list (add/remove), reusing each target's existing editor (layer → the 60.1 full-form side-by-side). Legacy single-`action` options keep working via a normalizer (no DB migration).
**Depends on:** Phase 60 (dispatch + control-keyed overlay store), Phase 60.1 (full-form layer editor reused per layer target).
**Requirements**: RADIOMULTI-V111-01
**Why pulled forward (2026-06-13):** Operator asked how hard multi-target would be; the overlay store was built control-keyed/multi-target from day one, so it's a moderate, mostly-UI lift — worth doing before the v1.11 gate rather than deferring to v2 (CTRL-V2-03).
**Success Criteria** (what must be TRUE):
  1. A radio option holds an ordered `actions: WidgetAction[]`; selecting it applies ALL actions via a SINGLE `setControlContribution` write, and every target updates LIVE (no remount). Targets may mix widget / map-layer / dynamic-view kinds.
  2. Switch-replace at the option level: switching from an option targeting {L1, W2} to one targeting {L1} DROPS W2's overlay (no stranded targets) — proven by a test. Built by assembling the option's full contribution and replacing the control's contribution wholesale (NOT looping per-target merge).
  3. The config panel authors a per-option target LIST (add/remove a target); each target uses its existing editor — layer → the 60.1 full-form side-by-side, widget/dv → existing inputs; Advanced JSON fallback per target. `validateRadioOption` validates EVERY action (layer → validateLayerSnapshot, widget/dv → validateActionPatch).
  4. Back-compat: legacy single-`action` options load + edit + dispatch unchanged (normalized to a 1-element actions array; no DB migration). Frontend vitest 100%; web tsc clean; frontend-only (no server diff); single-target authoring stays clean/uncluttered.
