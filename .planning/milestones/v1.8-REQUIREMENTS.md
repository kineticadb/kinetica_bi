# Requirements: Kinetica BI — v1.8 Roles & Permissions (RBAC)

**Defined:** 2026-06-05
**Core Value:** Click-through data exploration — users drill into chart elements and the entire dashboard filters to that slice of data, enabling fast iterative analysis without writing SQL.
**Milestone goal:** App-level RBAC on top of existing per-user Kinetica/OIDC auth — 4 built-in roles + custom roles, app-local SQLite role registry, editable role→permission mappings, server-side enforcement + frontend gating, user/role management UI.

**Locked decisions (from milestone questioning):** app-local role registry (no user creation in app); custom roles supported; multiple roles per user with union semantics; analyst default for unassigned users; Kinetica `admin` username always app admin (env-overridable); shared workspace (no dashboard ownership); server-side enforcement authoritative.

## v1.8 Requirements

### Foundation

- [x] **SCHEMA-V18-01**: SQLite role registry (`roles`, `role_permissions`, `user_roles`) created idempotently (CREATE TABLE IF NOT EXISTS) and seeded (INSERT OR IGNORE) with the 4 built-in roles (admin, user_admin, designer, analyst) + default permission mappings; the 15-item `noun:verb` permission catalog is code-defined (new permissions require a release; mappings are DB-stored)
- [x] **SCHEMA-V18-02**: `getEffectivePermissions(username)` pure helper resolves the union of all assigned roles' permissions; usernames with zero `user_roles` rows resolve to the analyst role's current mappings (default-analyst fallback)
- [x] **SCHEMA-V18-03**: Bootstrap admin — `APP_ADMIN_USERNAME` env var (default `admin`) is always resolved as app admin regardless of DB state and can never be locked out; server logs a boot warning when `AUTH_MODE=oidc` and the var is unset/default (IdP-claim username mismatch risk)

### Server Enforcement

- [x] **GUARD-V18-01**: `requirePermission(perm)` middleware factory composes after existing `requireAuth` (which stays unmodified); denial returns 403 with a typed code (mirrors REAUTH_REQUIRED pattern) the frontend can dispatch on
- [x] **GUARD-V18-02**: All config-mutation routes are permission-gated: dashboards CRUD, widgets CRUD + config PATCH, tables association, views CRUD, dynamic-views CRUD, dashboard-layers CRUD + reorder
- [x] **GUARD-V18-03**: Analyst interaction routes remain gated by `requireAuth` ONLY — `POST/DELETE /api/filter/materialize`, `POST /api/info/query`, `GET /api/top-values`, column-stats, quantile, `POST /api/dynamic-view/materialize`, `POST /api/dynamic-view/:id/drop`, `/api/wms`, read-path SQL — the analyst-passthrough boundary is documented in code at the route registrations
- [x] **GUARD-V18-04**: RBAC management routes (list users, assign/revoke roles, role CRUD, mapping edits) are gated on `users:view` / `users:assign_roles` / `roles:view` / `roles:manage_permissions` / `roles:create_custom` / `roles:delete_custom`
- [x] **GUARD-V18-05**: Existing server test suite migrated via a `createAdminSession()` test helper (session + admin role seed) in the SAME phase that adds the middleware — RBAC introduces zero new test failures vs the pre-v1.8 baseline (582/689; TD-V16-TEST-ISOLATION untouched)

### Frontend Gating

- [x] **GATE-V18-01**: `/api/auth/me` response widened with `roles: string[]` + `permissions: string[]`; `useAuthStore` extended (NOT a new store; reset chain unchanged) with a `hasPermission(perm)` selector
- [x] **GATE-V18-02**: DashboardsPage action-bar buttons hidden per permission — New Dashboard (`dashboards:create`), Edit (`dashboards:edit`), Delete (`dashboards:delete`), Map Layers (`layers:manage`), Dynamic Views (`dynamic_views:manage`)
- [x] **GATE-V18-03**: Widget grid — add-widget and widget-delete hidden, drag/resize inert without `dashboards:edit`
- [x] **GATE-V18-04**: ChartConfigPanel renders read-only (save/apply hidden) without `widgets:configure`
- [x] **GATE-V18-05**: Sidebar nav — "User Management" gated on `users:view`, "Roles" gated on `roles:view`

### User Management

- [x] **USERS-V18-01**: Users page lists known usernames (sourced from session history + existing role assignments) with their assigned roles as chips
- [x] **USERS-V18-02**: User admin can assign and revoke roles per user; a user may hold multiple roles simultaneously
- [x] **USERS-V18-03**: Bulk role assignment — select multiple users and assign a role in one action
- [x] **USERS-V18-04**: Admin onboarding banner — "N users are currently on the default analyst role" with a link to User Management, shown to admins while unassigned users exist

### Role Management

- [x] **ROLES-V18-01**: Roles page shows built-in + custom roles with a role × permission matrix view of current mappings
- [x] **ROLES-V18-02**: Role→permission mappings are editable for ALL roles including built-ins (edit on a built-in shows "affects all users with this role" warning)
- [x] **ROLES-V18-03**: User admin can create custom roles composing any subset of the permission catalog
- [x] **ROLES-V18-04**: Custom roles can be deleted only when no users hold them; built-in roles cannot be deleted or renamed

### Safeguards

- [x] **SAFE-V18-01**: Last-admin protection — the API rejects a role revocation or mapping edit that would leave zero non-bootstrap users with admin (clear 400 message); bootstrap account is exempt because it cannot be removed
- [x] **SAFE-V18-02**: Privilege-escalation guards — a user admin (non-admin) cannot assign the admin role, cannot edit the admin role's permission mappings, and cannot grant a custom role permissions they do not themselves hold

### Audit

- [x] **AUDIT-V18-01**: Role assignment/revocation and mapping edits emit structured audit-log entries (extends existing OBS-01 JSON log) including actor, target, and before/after state

### Verification

- [x] **VERIFY-V18-01**: Live operator walk-through as each role — admin, user admin, designer, analyst, and one custom role — confirming gated UI + server 403s + analyst click-through exploration intact; frontend vitest/tsc + server tsc green; server vitest no worse than pre-v1.8 baseline

## Out of Scope

| Feature | Reason |
|---------|--------|
| Dashboard ownership / owner-only editing | Conflicts with established shared-workspace model; role-level not resource-level permissions (locked at questioning) |
| Per-dashboard visibility groups | Second permission axis multiplies management surface; Superset is removing its equivalent (SIP-152) |
| Row-level / data security in the app | Kinetica enforces data access per user already; app RBAC governs app capabilities only |
| Gating filter/drill-down interaction | Filtering IS the core product value; analyst retains full click-through exploration |
| Permission inheritance / role hierarchy | Hard to audit; flat composition + union semantics achieves the same end |
| User creation/deletion in the app | Identity stays Kinetica/OIDC; app only maps usernames → roles (locked at questioning) |
| Per-chart-type permissions | Catalog explosion; no reference BI tool does this |
