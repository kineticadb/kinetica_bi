<decisions>
## Implementation Decisions

### Bug 1: RolesPage dark in light mode (ROOT-CAUSED)
- Cause: `packages/web/src/components/RolesPage.css` references **non-existent CSS variables** (`--color-bg`, `--color-text`, `--color-text-muted`, `--color-border`, `--color-hover`, `--color-selected`, `--color-badge-bg`, `--color-badge-text`, `--color-danger` — 43 var() usages), so every one falls back to its hardcoded dark hex. The app's REAL theme tokens (global.css :root + :root[data-theme="light"]) are: `--bg`, `--panel`, `--text`, `--muted`, `--border`, `--card`, `--chip-bg`, `--accent`, `--accent-2`, `--input-bg`, `--shadow`.
- Fix: rewrite RolesPage.css onto the real tokens. Mapping guidance: `--color-bg`→`--panel`; `--color-text`→`--text`; `--color-text-muted`→`--muted`; `--color-border`→`--border`; `--color-hover`→`var(--card)` or a translucent that flips acceptably; `--color-selected`→accent-tinted translucent (verify readable in BOTH themes); badge bg/text→derive from `--accent-2` family or add explicit light override; danger red is fine but give it a light-mode-legible value if needed. NO fallback hexes that differ per theme — fallbacks must be theme-neutral or removed.
- Acceptance: zero references to `--color-*` variables remain in RolesPage.css (`! grep -q -- '--color-' RolesPage.css`); visually the page uses panel/light surfaces in light mode (operator re-check at UAT).

### Bug 2: Edit-roles popover clipped (ROOT-CAUSED)
- Cause: `.users-table-wrap { overflow-x: auto }` (global.css ~3852) establishes a clip/scroll context; the absolutely-positioned `.users-popover` (~4015, inside relative `.users-popover-wrap` ~4009) renders outside the wrap's bounds → clipped, scrollbar appears instead.
- Fix (Claude's discretion between):
  (a) `overflow: visible` on `.users-table-wrap` (preferred if the 5-column table doesn't actually need horizontal scroll at reasonable widths), or
  (b) keep the scroll container and reposition the popover (e.g. open upward/left when near the edge, or position: fixed anchored to the trigger's getBoundingClientRect).
- Acceptance: popover fully visible when opened on any row incl. the last; no spurious horizontal scrollbar on a normal-width viewport. RTL can assert class/structure; full visual is the UAT re-check.

### Bug 3: role chips unreadable in light mode (ROOT-CAUSED)
- Cause: `.role-chip` (global.css ~3933) hardcodes dark-theme greens: `color: #86efac`, translucent green bg/border — washed out on light backgrounds (operator screenshot: "admin" chip barely visible).
- Fix: add a `:root[data-theme="light"] .role-chip` override (e.g. `color: #15803d; background: rgba(34,197,94,0.14); border-color: rgba(21,128,61,0.35)`) or refactor to chip variables. The `--default` variant already uses theme vars and is fine — verify it still reads well.
- Same check for any other RBAC-page hardcoded colors that bypass tokens (Topbar user-menu, ProfilePage, UsersPage CSS added in 49/50.1 — sweep them: any hardcoded hex/rgba added in v1.8 phases must be either theme-token-based or have a light override).

### Process fix: UAT light-mode pass
- Patch `.planning/phases/51-verification-live-uat/51-02-PLAN.md` checklist: add an explicit item (e.g. §2.4 or a new §10): "Toggle light mode and walk Users, Roles, Profile pages + Topbar menu — all surfaces render with light theme, all text/chips legible." This catches the entire bug class going forward.

### Claude's Discretion

- Popover fix option (a) vs (b)
- Whether the light-mode sweep produces additional small overrides (apply them; list in SUMMARY)
