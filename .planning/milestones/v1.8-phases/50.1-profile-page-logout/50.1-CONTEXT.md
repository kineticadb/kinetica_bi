# Phase 50.1: Profile Page + Logout - Context

**Gathered:** 2026-06-06 (decisions captured conversationally at insertion — operator-requested pre-UAT work)
**Status:** Ready for planning

<domain>
## Phase Boundary

Two operator-requested UX gaps found while reviewing the running app before UAT: (1) no logout affordance exists anywhere (the server's `POST /api/auth/logout` shipped in v1.0 but was never wired to UI); (2) the Phase 48 Topbar role chips felt wrong in practice — identity detail moves to a dedicated read-only Profile page. NO new server capability; one small server check only if the logout route needs verification.

</domain>

<decisions>
## Implementation Decisions

### Topbar user menu (replaces role chips)
- The Topbar identity area becomes a **menu trigger**: initials avatar + username (+ caret). **Role chips are REMOVED from the Topbar** (reverses the Phase 48 chips decision — operator saw it live and preferred a quieter Topbar).
- Menu items: **"Profile"** (navigates to the Profile page) and **"Log out"**.
- Approved sketch:
```
          [DE ▾]
          ┌──────────┐
          │ Profile  │
          │ Log out  │
          └──────────┘
```
- Click-outside dismiss (DataFilterRenderer/UsersPage mousedown pattern — no new deps).

### Logout flow
- "Log out" → `POST /api/auth/logout` (route exists since v1.0 — verify its current behavior: clears session row + cookie) → then the FULL canonical client-side reset: the existing 6-store lifecycle reset chain + auth store cleared → user lands on LoginPage.
- Reuse the existing UNAUTHORIZED flow machinery where sensible (App.tsx already has the store-reset + LoginPage routing for session expiry — logout should converge on the same path rather than duplicating reset logic).
- Logout must work for every persona (it is auth-level, not permission-gated).

### Profile page (read-only)
- New page (Page union entry e.g. `"profile"`, NOT in the Sidebar nav — reached via the Topbar menu only; mirror Phase 49/50 App.tsx wiring incl. OIDC ReturnTo if trivial, else skip ReturnTo for profile).
- Contents:
  - **Username** + **auth mode** ("password sign-in" / "SSO") from useAuthStore/authMode
  - **Assigned roles** as chips — with the analyst-default distinction (muted "analyst (default)" when roles came from the fallback; the /me response reflects effective roles — if it does not distinguish explicit vs default, show roles as-is and note it; do NOT add server work just for the badge unless trivial)
  - **Effective permissions** grouped by category — REUSE the `NOUN_TO_GROUP` + `GROUP_ORDER` grouping from RolesPage (extract to a shared module if needed rather than duplicating)
- Approved sketch:
```
PROFILE
────────────────────
rpereira          (password sign-in)

Roles
[designer] [user_admin]

Effective permissions
Dashboards: view, create, edit, delete
Design: widgets, layers, dynamic views…
Users: view, assign roles
```
- All data comes from the existing /me payload already in useAuthStore — NO new API calls required.

- Update the plan file as part of this phase (or the orchestrator patches it) — do NOT let the UAT run against the stale item.

</decisions>
