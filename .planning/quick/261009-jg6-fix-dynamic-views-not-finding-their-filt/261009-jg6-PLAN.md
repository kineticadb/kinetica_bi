<objective>
Fix dynamic views that never find their filter view once v1.18 filter combinations are active. Also fix the second, client-side cause that leaves the Unlimited case blank. Then make the legend badge say WHY a dv layer is hidden.

Purpose: a dv-backed map layer (operator's "Avg NYC" on demo.nyctaxi) shows OVER THRESHOLD forever, with or without a narrow filter, and even with Unlimited ticked. Phases 138/139 (AI filters, session dvs) build on this path, so it must land first (STATE.md "Pending from Phase 133").

Output: server threads a combination key into the dv lookup. The orchestrator materializes and ref-counts each dv's source combination. The chain is driven from the combination store. The legend badge is reason-aware. Red-first regression tests cover each part.
</objective>

<confirmed_root_causes>
These were confirmed by reading the code during planning. The executor does not need to re-derive them.

1. **Client: the cascade is wired to a store that has been dead since Phase 91.** `useDynamicViewMaterializeChain.ts:86-90,145-147` keys on `useFilterViewStore.views[source_table_id].materializeVersion`. `filterViewStore.setView` has ZERO production callers: `grep -rn "\.setView(" packages/web/src | grep -v spec | grep -iv dynamicview` returns nothing. The only writers are `markMaterializing` calls, which write `materializeVersion: 0`. So `currentMatVer` is always 0, and the `!force && currentMatVer === 0` fast-path (`:173-187`) writes `over_threshold/no_filter` locally and returns. The server is never called, whatever the filters or `max_records` are. That explains BOTH symptoms, including Unlimited. Only `retry(force)` ever reaches the server. The existing spec stayed green because it drives the dead store directly (`useDynamicViewMaterializeChain.spec.ts:63-71` calls `useFilterViewStore.getState().setView`).
2. **Server: the dv lookup omits the combination suffix.** `index.ts:2075-2080` (materialize) and `:1973-1978` (preview) call `buildFilterViewName` without `combinationKey`. Since v1.18 the only filter-view creator is `useCombinationOrchestrator.ts:539,572`, and it ALWAYS passes `combinationKey: hash`. So the unsuffixed `_t<id>` view is never created anymore, and the probe at `:2111-2120` always misses and falls back to base. This happens with one filter as well, not only with "combined" filters.
3. **There is no combination for the dv to read anyway.** A dv is not a registered viz. The orchestrator enumerates widgets and layers only (`useCombinationOrchestrator.ts:189-338`). A combination equal to "all filters on the dv's source table" exists only by coincidence (an unscoped widget on the same table, or the ceiling fallback). Threading the key server-side is therefore not enough: the orchestrator (the sole materialize trigger) must also materialize and hold the dv's source combination.
4. **Other `buildFilterViewName` callers were audited.** `:1368` (dv-filter) and `:1471` (table) already pass the key. `:1535`/`:1547` (DELETE legacy dv/table branches) are fine: combination views are dropped by the `?viewName=` direct branch, which `dropCombinationView` uses. `:1973` (preview) has the same omission and is fixed here.
5. **The badge discards `reason`.** `LayersLegendPanel.tsx:159-166` `dvStatusBadgeLabel(status)` maps every over_threshold to "Over threshold". `MapChartRenderer.tsx:733-736` and `LegendRenderer.tsx:115-118` never forward `dvEntry.reason`.
</confirmed_root_causes>

<design_decisions>
- **Which combination does a dv read?** All active filters on its source table, column-only: `stableComboHash("table", dv.source_table_id, filters[dv.source_table_id] ?? [])`. NOFILTER maps to `undefined`.
  - A dv row has no filter_scope or filterSelection of its own. So "accept-all on the source table" is the faithful v1.6 meaning: the pre-v1.18 unsuffixed view held all of the table's filters.
  - This hash is byte-identical to the orchestrator's ceiling-fallback hash, so the per-table ceiling can never orphan it. It also dedupes with any unscoped, non-spatial widget on the same table.
  - `DISABLE_DV_FILTER_SCOPE` / `dvFilterScopeDisabled` is NOT involved. That flag governs how dv-bound consumers resolve `dvFilters[dvId]`, not which source rows feed the dv.
  - Spatial shapes deliberately do NOT narrow a dv's source in this fix (column-only, matching the existing dv-path convention). Note it as a follow-up in SUMMARY; do not implement it.
- **Sole-trigger invariant.** Only `useCombinationOrchestrator` calls `materializeFilter`. The chain only READS the registry and sends the hash to `/api/dynamic-view/materialize`.
- **Fast-path is kept, but narrowed.** It still applies when there is no filter AND `dv.max_records > 0`: no N-HTTP on mount, and the "Load full table" CTA (`retry`, force) behaviour is unchanged. When there is no filter and `max_records === 0` (Unlimited), the chain calls the server with no key, and the server takes the base-table branch.
- **Wire name.** The field is `combination_key` (snake_case, matching `dynamic_view_id` on these endpoints). The server passes it verbatim as `combinationKey`, and `buildFilterViewName` reduces it to `_c` + `hashKey8(...)`. The name therefore stays a safe 8-hex identifier whatever the client sends. Still validate: when present it must be a string of ≤ 4096 chars, else 400. An empty string is treated as absent.
</design_decisions>
