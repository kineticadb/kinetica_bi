## v1.23 — Zoom-Aware Layer Legend

The layers panel used to describe the *configuration*. Now it describes the *map*.

Layers carry an inclusive `[minZoom, maxZoom]` range, so as you zoom they drop in and out of view — but the panel rendered every layer identically regardless of whether it was actually drawing. You could not tell which layer was responsible for what was on screen.

| State | Appearance |
|---|---|
| Drawing at the current zoom | normal |
| Not drawing — **zoom out of range** | dimmed, with its range shown (e.g. `zoom 3–10`) |
| Not drawing — **eye toggled off** | today's existing styling, unchanged |

The two "not drawing" reasons are deliberately distinct: one you chose, one resolves itself by zooming. Live-updating as you zoom, in both the in-map legend and the standalone Legend widget.

### Reviewer notes

**1. This fixes a bug that was already shipped.**
`MapChartRenderer.tsx`'s info-click gate re-implemented the zoom-range check with raw inclusive bounds, diverging from what OpenLayers actually draws. The wire format is inclusive; OL's `minZoom` is exclusive (`internalMin = userMin - 1`). At fractional zoom just below a layer's `minZoom`, the layer was **visibly on the map but info-clicks on it were silently dropped** — click a layer you can see, get nothing.

Phase research found it; it was put in scope deliberately rather than logged as debt, because this phase was already extracting the shared predicate and leaving a second, wrong implementation is how the bug arose. **There is now exactly one zoom predicate** (`lib/zoomRangeBounds.ts`), and the verifier independently grepped the tree to confirm no third survives.

The boundary oracle was derived independently three times — research, plan checker, verifier — all agreeing: for `{minZoom:3, maxZoom:10}`, active at 2.9 / 3 / 10, inactive at 10.5. Fractional zoom is where the bug lived.

**2. `theme-guard` cannot see colour literals in `global.css`, and this was confirmed structurally.**
The spec allowlists that file and, for allowlisted files, asserts `hasHex === true` — it **never checks absence**. Any hardcoded colour there passes every automated gate unconditionally. This is how Phase 114's `.onboarding-banner` light-mode defect reached production.

Compensated for here with a hand-run hex + `rgba(` audit on the diff, executed **three times independently** (executor, orchestrator, verifier — all 0), plus **separate** light and dark operator checks rather than one merged "looks fine in both". Narrowing that exemption to `:root` blocks is now a well-evidenced candidate and is logged as `TD-V123-THEMEGUARD-HOLE`.

**3. The test suite was fixed this milestone, and it changed how verification feels.**
The web suite had been non-deterministic for an entire phase — 1-7 failures per full run, non-reproducible, repeatedly logged as "pre-existing contamination" and worked around with re-runs. Phase 117 verifications routinely needed 2-3 full-suite runs, each requiring a judgement call about whether a failure was real.

Root cause was **two async-query defects, not contamination**: Testing Library's `asyncUtilTimeout` defaults to 1000 ms and was never configured (while vitest's `testTimeout` is 5000 ms — two budgets 5× apart, the tighter one belonging to the library nobody configured), and one synchronous `getBy*` asserting on content from a later React commit. RTL reports async-query timeouts as `Unable to find …`, which reads exactly like an assertion failure — that single fact caused four wrong diagnoses. Bisection proved no contaminating file existed; the absence was the finding.

Fixed in `cde63ae`, 9 lines across 2 files. **Before: 0 of 4 runs clean. After: 4 of 4.** Every Phase 118 verification then passed on the first attempt. Full trail, including the wrong turns and an n=1 near-miss that almost ended the investigation prematurely, in `.planning/v123-flake-investigation-notes.md`.
