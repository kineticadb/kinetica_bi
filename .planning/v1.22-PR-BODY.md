## v1.22 — Dashboard Settings Links

Closes the one gap v1.21 left. `DashboardsPage` has five view modes (`list | view | edit | create | open`); v1.21 wired exactly one — `open`, the running dashboard at `?dashboard=<id>`. Phase 116 gave *tables* their view/edit URLs. Dashboards never got them.

Now they do:

| URL | Screen |
|---|---|
| `?dashboard=12` | the running dashboard — **unchanged** |
| `?dashboard=12&mode=view` | the settings screen (`DashboardDetail`) |
| `?dashboard=12&mode=edit` | the edit screen (`DashboardEdit`) |

**Frontend-only.** `packages/server` untouched. No new dependency, no router.

### Reviewer notes — four things worth knowing

**1. A bare `?dashboard=<id>` deliberately still means "open", and that asymmetry with tables is intentional.**
Bare `?table=12` opens a table's *view* screen; bare `?dashboard=12` opens the *running* dashboard. Both follow "a bare URL opens that entity's primary screen" — the primary screen just differs. Harmonising them would silently break every bookmarked dashboard link. `DSET-V122-08` exists solely to protect this, `readDashboardModeFromSearch` defaults to `open` for absent *and* unrecognised modes, and the ~132-test dashboard family still asserts the original behaviour unchanged. If this looks like an inconsistency, it is a deliberate one.

**2. `lib/tableUrl.ts` and `lib/dashboardUrl.ts` remain structural duplicates, now three implementations deep — deliberately.**
`TLINK-F4` was raised in v1.21 and deferred to "a phase whose gate permits touching the existing specs". This was that phase, so the decision was made rather than deferred again, and it was made by measurement: this feature already touched all 132 dashboard tests unconditionally, and extracting a shared core would additionally have put the table family's 100 tests in play — purely for de-duplication, inside the one phase whose highest-stakes requirement is not regressing a live URL. The rewritten `TLINK-F4` entry in `REQUIREMENTS.md` carries the rationale and an explicit reopening condition.

**3. Two corrections were made to the phase's own planning documents during execution, and both proved real.**
- The phase's RESEARCH proposed unmount-clear timers guarded on dashboard id alone. That wipes the URL one macrotask after an `edit→view` Save, because the id is still present under the *new* mode the Save just wrote. The timers ship scoped on **id AND mode**; a mutation probe holds it, and operator checks C11/C12 confirmed it in a browser.
- A plan's audit for `DSET-V122-08` used a bare `git diff` with no revision range. Because every task commits immediately, that command returns `0` unconditionally — a guard that cannot fail, protecting the phase's highest-stakes requirement. It now scopes by commit message; on its first real run it surfaced 5 deleted `it(` lines, which investigation confirmed were documented title-only renames.

**4. The test suite is non-deterministic under parallel load, and this is the phase's weakest evidence.**
Four spec files flaked at different points, non-reproducibly, with zero diff on disk; the closeout and the independent verifier each needed **three** full-suite runs to get one clean pass, failing on *different* files. Every endpoint is green and the failures never reproduced at a known-good commit — but a suite that reddens differently each run is weaker evidence than a stable one, and this phase leans heavily on automated coverage. Flagged in `deferred-items.md` and in the phase verification report rather than smoothed over. **This is worth fixing before it reddens in CI and blocks a release tag.**
