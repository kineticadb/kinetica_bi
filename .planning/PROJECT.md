# Kinetica BI

## What This Is

A business intelligence dashboard application for data engineers and business analysts to visualize, explore, and drill into data stored in Kinetica GPU-accelerated databases. Users build dashboards with configurable chart widgets, connect to Kinetica tables, and interactively explore data by clicking through visualizations. Click any chart element to apply an equality filter that instantly narrows all charts, records-tables, and map tiles on the same Kinetica table — driven by a server-side transient materialized view, not client-side WHERE injection. Authentication supports both Kinetica password mode and Generic OIDC SSO (mutually exclusive per deployment via `AUTH_MODE`), with app-level role-based access control (admin / user_admin / designer / analyst + custom roles) governing app capabilities on top of Kinetica's per-user data access.

## Core Value

Click-through data exploration — users drill into chart elements and the entire dashboard filters to that slice of data, enabling fast iterative analysis without writing SQL.

**Goal:** Remove two navigation frictions — a map that always opens on the whole world, and a dashboard you can only reach by clicking through the list page.

**Target features:**

**Locked scope decisions (2026-09-09):**
1. **Zoom AND center**, not zoom alone. Saving zoom alone would reopen the map at close range over `[0,0]` — the Atlantic. Two new config fields on the map widget.
2. **No router dependency.** The app has no routing today: no `react-router`, and zero uses of `history`/`location` in `src/`. Navigation is `page` + `dashboardViewMode` state in `App.tsx`. v1.21 syncs a URL param to that existing state via the native History API rather than restructuring App.tsx around routes.
3. **Dashboard identity only in the URL** — no filter state, no map viewport. Keeps the v1.4 "URL/DB persistence of info-selection state" exclusion intact; revisit only if a customer asks for shareable filtered views.
4. **Scope held to these two features.** Deliberately not padded from the backlog.

**Known integration constraints (found by reading the code, 2026-09-09):**
- `MapChartRenderer.tsx:1038` hardcodes `center: [0, 0], zoom: 2`. Phase 12-02 deliberately REMOVED auto-fit-on-mount and the zoom-to-data button, so this milestone reintroduces an initial view as an operator-controlled default, not as auto-fit.
- `mapViewportSyncStore` (Phase 104) holds `{center, zoom}` but is NOT reusable for this: it publishes only when the per-map "Sync viewport" toggle is on (default off, MAPSYNC-V119-06) and is keyed by `dashboardId`, not `widgetId` — one last-writer-wins broadcast slot, not a per-map registry. The config panel needs its own path to the live view of the map being configured.
- A dashboard URL must survive the two failure cases: not authenticated (the Phase 7 sessionStorage return-to-page pattern is the precedent) and no permission (v1.10 per-dashboard view permissions must fail with a message, not a blank screen).

## Context

- **Stack**: React 18 + TypeScript frontend (Vite), Express + TypeScript backend, SQLite for local persistence, Kinetica GPU-DB for data
- **Auth**: Either Kinetica password mode (Basic) or Generic OIDC (Bearer via openid-client@5), selected per deployment via `AUTH_MODE`. Both modes share an AES-256-GCM `sessions` table and the same 8-hour BI session TTL.
- **Charting**: Recharts library with 8 registered chart types
- **Layout**: react-grid-layout for draggable/resizable widget grid
- **State**: Zustand for user state, React local state for components, SQLite as server source of truth
- **Kinetica response format**: Columnar JSON (column_1: [...], column_2: [...]) that gets pivoted to rows client-side
- **Views model**: Each dashboard-table association auto-creates a view placeholder (view_name = original table, empty filter). Views are snapshots; filtering is client-side on top.
- **Test infra**: Server uses vitest@^4.1.5 + supertest. Frontend (added v1.1) uses vitest+jsdom+@testing-library/react with a Zustand store-reset shim. Server suite: 312 passing / 104 failing (104 pre-existing: TD-V11-04 OIDC mock divergence ~60 tests, TD-V13-01 fetch-mock brittleness ~44 tests — neither is a v1.3 regression; see MILESTONES.md v1.3 Known Gaps). Frontend suite: 347/347 passing.
- **Codebase size**: ~16,000 LOC TypeScript across `kinetica_bi/server/{src,tests}` + `kinetica_bi/src` (post-v1.3).
- **Known test issues at v1.3 close**: ~104 backend tests red (TD-V11-04 + TD-V13-01); production OIDC and all routes verified manually. Frontend fully green.
- **Audience**: Data engineers building pipelines + business analysts exploring data. Both need it reliable enough for daily use.

## Constraints

- **Database**: Must work with Kinetica's SQL dialect and columnar response format
- **Persistence**: SQLite for dashboard metadata (no external DB dependency)
- **Auth**: BI app sign-in validates against Kinetica; per-user credentials authorize every downstream call (no shared admin)
- **Milestone target**: Reliable enough for daily use by the team (not public production)
