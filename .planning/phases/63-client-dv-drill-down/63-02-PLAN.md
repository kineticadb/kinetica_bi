<objective>
Extend the client materialize/drop API helpers to carry an optional `dynamicViewId`, so the dv-bound widget (63-03) can materialize a filtered sub-view FROM the dynamic view's own materialized view (the Phase 62 server path) instead of always filtering the source table.

Purpose: Phase 62 already extended `POST /api/filter/materialize` (and DELETE) to accept `dynamicViewId` in the body / query and build `FROM <dv_view> WHERE <filter>` (verified — see 62-VERIFICATION.md). This plan wires the CLIENT side of DVDRILL-V112-03: pass `dynamicViewId` through, and — critically — make the in-flight dedup cache key incorporate `dynamicViewId` so a dv call `{dashboardId, dynamicViewId}` does NOT collapse with a table call `{dashboardId, tableId}` that happens to share numeric ids (the existing cache key is `${dashboardId}:${tableId}`).

Output: `MaterializeFilterArgs` gains optional `dynamicViewId?: number` (and `tableId` becomes optional); `materializeFilter` sends it in the body + uses a dv-aware cache key; `DropFilterViewArgs` gains optional `dynamicViewId?: number`; `dropFilterView` appends `?dynamicViewId=` + uses a dv-aware cache key.
</objective>
