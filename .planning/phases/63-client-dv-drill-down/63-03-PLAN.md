<objective>
Fix the v1.12 bug at its root: route a dv-backed widget's drill-down into the dv-scoped slices (63-01) and materialize a filtered sub-view FROM the dynamic view (63-02 / Phase 62), with the read-path FROM-swapping to the filtered-dv view. Today `dispatchDrillDown` always keys by `tableId` (WidgetRenderer ~103-135), so a dv drill mis-lands in `filters[sourceTableId]` and the dv-bound widget — which reads the raw dv view and SKIPS filter-materialize when `dynamicViewId` is set — never reflects the click.

Purpose: This is the user-visible fix (DVDRILL-V112-01/02/04 + client -03). dv-isolated scope is LOCKED — a dv drill filters ONLY that dv (same-dv widgets update; source-table + other-dv widgets untouched). The invariant: a dv drill must NOT bump `filters[sourceTableId]` (the bug was exactly that). Table-backed widgets keep the EXISTING path byte-unchanged.

Output: dv-aware `dispatchDrillDown`; `drillEnabled` true for dv widgets; a dv branch in BOTH AggregatedWidgetRenderer's Effect 1 AND RecordsTableRenderer's Effect 1 materialize triggers (gated on `dvStatus === "materialized"`, mirroring the existing `dvStatus === "pending"` early-return); read-path precedence `dvViews[dvId].viewName` → raw dv view in both renderers' chart-query effects; the mandatory isolation + read-path-swap tests.
</objective>
