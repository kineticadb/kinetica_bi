## Open observation — RESOLVED BENIGN 2026-09-30, with evidence

During G1 the added column `test_col` reported its LIVE type as `string(decimal(10,2))`. During
G2 the same column's STORED type read `float`.

Two readings, and the evidence available does not distinguish them:
1. **Benign** — the column was dropped and recreated as a float between the two observations.
   The screenshots are from different runs, so this is entirely plausible.
2. **A defect** — an apply stored a flattened type, which is exactly what `renderColumnsMap`
   exists to prevent and what `PARITY-class` guards against in the unit tests.

**RESOLVED: reading (1), benign.** The operator's own sync-history entry settles it — it records
`test_col` RETYPED `string(decimal(10,2))` → `float`. So the stored type WAS the precise
parameterised type, the column genuinely changed type in Kinetica, and the app detected and
recorded the retype correctly. No flattening occurred; `renderColumnsMap` did its job. The
history record is what proved it, which is a point in favour of the durable worklist. It does NOT block the phase: G6 passed, which means the
config panels offered the live columns after an apply, and reading (2) would be hard to reconcile
with that. Worth one deliberate check next time a column is added and applied in one sitting:
note the live type in the report, apply, then re-run the check and confirm the stored type
matches rather than having collapsed to its base.

### UAT-126-G8 — JUDGEMENT CALL: the text-gap caveat on `no_changes`
decision-required: yes
context: After an apply that reports **"Nothing to apply — the stored snapshot already matches
Kinetica"** (`outcome: "no_changes"`), the text-width caveat is deliberately **NOT** shown. It is
shown only after an apply that actually wrote (`outcome: "applied"`). The planner's reasoning: a
`no_changes` apply stored nothing, so no column was stored as `string`, and the caveat would
describe an event that did not happen. **ROADMAP criterion 6 says "after an apply" unconditionally,
so this decision NARROWS the criterion's literal wording** and no source settles it.
Reversing it is ONE line in `SchemaSyncModal.tsx`'s `resultBody()`:
`result.outcome === "applied"` → `result.outcome === "applied" || result.outcome === "no_changes"`,
plus flipping the `CAVEAT-applied-only` test. Probe P6 (126-02) already demonstrated the mutation
and showed the test catches it.
question: **Is this what you want, or should the caveat appear after EVERY apply including
`no_changes`?**
ruling: **REVERSED — show the caveat after `no_changes` too.** Criterion 6's literal wording stands.
Implemented: `resultBody()` now shows it on `applied || no_changes`. `CAVEAT-applied-only` became
`CAVEAT-no-changes` (asserts the caveat IS present), plus a new `CAVEAT-not-on-stale` so the widened
condition cannot drift into showing on a refusal. Probed: reverting the condition fails
`CAVEAT-no-changes` by name, and no other test.
ruled-on: 2026-09-30
