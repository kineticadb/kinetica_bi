<planner_decisions>
**Decision — history is a TAB inside the same modal, and it loads without a check having run.**
RESEARCH.md Open Question 2 flags this as Claude's discretion with no constraint in source.
Reason: "one entry point per table" is locked in CONTEXT, so a second modal is out; and the
"durable worklist" framing means the operator opens this to work through entries, typically
*without* wanting to re-run a check first. An always-visible panel below the check stage would
push the report — the thing criterion 1 is about — below the fold. A tab satisfies both.
</planner_decisions>

**From plan 01 (`packages/web/src/api/client.ts`):**

```ts
listTableSyncHistory(tableId: number): Promise<TableSyncHistory>
deleteTableSyncHistoryEntry(tableId: number, entryId: number): Promise<void>   // 204, no body

type SyncChangeset = { v: 1;
  added:   { column: string; liveType: string }[];
  removed: { column: string; storedType: string }[];
  retyped: { column: string; storedType: string; liveType: string }[] };

type TableSyncHistoryEntry = { id: number; table_id: number; ts: string; actor: string;
                               kind: "baseline" | "diff";
                               changeset: SyncChangeset | null;   // null for a baseline entry
                               report: ImpactReport | null };     // null for a baseline entry

type TableSyncHistory = { entries: TableSyncHistoryEntry[];   // newest first, id DESC
                          droppedCount: number; lastDroppedTs: string | null; cap: number };
```

**Server facts that shape this UI, verified in source:**
- `cap` is `SYNC_HISTORY_CAP` (`db.ts:698` = 20) and is ECHOED in the response precisely so the
  UI never hardcodes it (`db.ts:753-762` comment: *"Echoed so the UI never hardcodes the number."*).
- `droppedCount` is **deliberately NOT decremented** by a per-entry delete
  (`index.ts:2674-2677`): it records what the CAP removed, a different fact from how many entries
  remain. So the cap notice legitimately stays visible after the operator clears rows. Do not
  "fix" this by recomputing it client-side.
- An empty table returns `{ entries: [], droppedCount: 0, lastDroppedTs: null, cap: 20 }` —
  a valid response, not an error.
- The DELETE 404s for an unknown entry **or an entry belonging to a different table**
  (`index.ts:2691-2695`) — the table id in the path is load-bearing, not decorative.
- A baseline entry carries `changeset: null` and `report: null`. The expanded detail must handle
  that without crashing.
- `ImpactReport` rendering is already built: reuse plan 02's `ImpactReportView` sub-component for
  `entry.report`. Do NOT write a second renderer.

**The locked cap-notice wording** (CONTEXT): *"Showing the 20 most recent. N older entries were
dropped."* — with **20 interpolated from `history.cap`** and **N from `history.droppedCount`**,
shown **only when `droppedCount > 0`**.

**Existing classes to reuse:** `.ghost-sm`, `.ghost-danger`, `.btn-primary`, `.btn-sm`,
`.ds-actions`, `.muted`, `.config-hint`, `.data-table`, `.modal-section-title`, plus plan 02's
`.schema-sync-body`, `.schema-sync-message`, `.impact-*` family.

**A. `SchemaSyncModal.tsx`.**

Add a tab selector alongside the existing stage state:

```ts
const [tab, setTab] = useState<"check" | "history">("check");
const [history, setHistory] = useState<TableSyncHistory | null>(null);
const [historyError, setHistoryError] = useState<string | null>(null);
const [expanded, setExpanded] = useState<number | null>(null);
```

Tab bar, directly inside `.schema-sync-body`, above the stage content:

```tsx
<div className="schema-sync-tabs">
  <button
    className={tab === "check" ? "ghost-sm schema-sync-tab-active" : "ghost-sm"}
    onClick={() => setTab("check")}
  >
    Schema check
  </button>
  <button
    className={tab === "history" ? "ghost-sm schema-sync-tab-active" : "ghost-sm"}
    onClick={() => { setTab("history"); void loadHistory(); }}
  >
    Sync history
  </button>
</div>
```

`loadHistory` is an async function calling `listTableSyncHistory(table.id)` into `history`,
catching into `historyError`. It is called from the tab click handler and, additionally, from the
apply handler **after a `result.outcome === "applied"` result resolves** so the new entry is
visible without reopening the modal. It is NOT called on mount, NOT from a `useEffect`, and NOT on
any timer — ROADMAP criterion 2 still binds this file.

History panel (rendered when `tab === "history"`):

1. `historyError` → `<div className="schema-sync-refusal">{historyError}</div>`.
2. `history === null` → `<div className="muted">Loading sync history…</div>`.
3. `history.droppedCount > 0` → the cap notice, and ONLY then:
   ```tsx
   <div className="schema-sync-cap-notice" data-testid="schema-sync-cap-notice">
     Showing the {history.cap} most recent. {history.droppedCount} older entries were dropped.
   </div>
   ```
   **Interpolate `history.cap`. Never write the literal `20`.** The server echoes `cap` for
   exactly this reason (`db.ts:753-762`).
4. `history.entries.length === 0` → `<div className="muted">No syncs recorded for this table
   yet.</div>`.
5. Otherwise `history.entries.map(entry => …)` **in the order given** (the server returns newest
   first, `id DESC`; do not re-sort), each a `.schema-sync-history-row` containing:
   - `.schema-sync-history-meta` — `{entry.ts}` · `{entry.actor}` · the counts line, derived from
     `entry.changeset`: for a `diff` entry
     `` `${c.added.length} added, ${c.removed.length} removed, ${c.retyped.length} retyped` ``;
     for a `baseline` entry (`changeset === null`) the literal `Baseline established`.
   - `<div className="ds-actions">` holding
     `<button className="ghost-sm" onClick={() => setExpanded(expanded === entry.id ? null : entry.id)}>`
     labelled `Details` / `Hide` (a one-line ternary of two plain string literals), and
     `<button className="ghost-sm ghost-danger" onClick={() => void removeEntry(entry.id)}>Delete</button>`.
   - When `expanded === entry.id`, a `.schema-sync-history-detail` block rendering:
     the full changeset — three labelled groups listing every column name with its type(s), using
     the existing `.data-table` class for the rows — and, when `entry.report !== null`,
     `<ImpactReportView report={entry.report} />` (**reuse plan 02's component; do not write a
     second report renderer**). When both are null, a single neutral line
     (`<div className="muted">This was a baseline entry — there was no changeset to record.</div>`).

`removeEntry(entryId)`: `await deleteTableSyncHistoryEntry(table.id, entryId)` then remove that
entry from local state (or re-call `loadHistory`). **No `window.confirm`, no confirmation modal,
no undo.** CONTEXT: an entry is an audit note, not data. Do NOT recompute `droppedCount` locally —
the server's non-decrement is deliberate.
