# Phase 63.1: Map-Layer DV-Filter FROM-Swap (gap closure) - Context

**Gathered:** 2026-06-15
**Status:** Ready for planning
**Source:** Phase 64 live operator UAT — gap found. The chart/table dv drill-down (Phases 62/63) works (§1–§3 attested PASS), but a **WMS map layer bound to the same dynamic view keeps rendering the UNFILTERED dv view** when a dv drill-down filter is active. Operator evidence: the WMS request shows `LAYERS=_kbi_dv_uadmin_d5_3` (the raw dv materialized view from `buildDynamicViewName`), never the filtered-dv view (`_kbi_filt_…_dv3_s…`).

<domain>
## Phase Boundary

**Delivers (the user-visible fix):** When a chart/table drill-down materializes a dv-filter (Phase 62/63), a **WMS map layer bound to that same dynamic view** FROM-swaps its rendered tiles to the **filtered-dv view** — so the map updates LIVE to the same slice, in lock-step with the dv-bound charts. Clearing the dv filter reverts the map to the raw dv view. This completes **DVDRILL-V112-02** ("every other widget bound to the SAME dynamic view re-renders to the filtered slice") + **DVDRILL-V112-04** (the read-path FROM-swap) for the MAP render path, which Phase 63 wired only for the chart/records `WidgetRenderer`.

**FRONTEND-ONLY** (`packages/web`). ZERO `packages/server` changes — the dv-filter view is ALREADY materialized by the chart's Effect 1 (Phase 63). The map is a pure CONSUMER (reads `useFilterViewStore.dvViews[dvId]`), so the **sole-materialize-trigger invariant is preserved** (no new materialize caller; `AggregatedWidgetRenderer` remains the sole trigger).

**Out of scope:** spatial (bbox/lasso/circle) filtering OF a dv-backed map layer (DVX-V2-01 — that is drawing a filter ON the map, a different feature); cross-scope propagation (source-table/other-dv widgets — locked OUT); any server change.
</domain>

<decisions>
## Implementation Decisions (LOCKED)

### Root cause (confirmed in code)
- `lib/wmsUrlBuilder.ts` `buildWmsParams` (~257-298) has a 4-case LAYERS/_mv precedence (Phase 35 DV-V16-13). For a dv-backed layer it ONLY knows the RAW dv view: Case 1 `dynamicViewEntry.status === "materialized"` → `params.LAYERS = dynamicViewEntry.viewName` (the `_kbi_dv_…` name). There is NO case that consults the dv-FILTER view in `useFilterViewStore.dvViews[dvId]`. So a dv drill never changes the map's LAYERS.
- `components/charts/MapChartRenderer.tsx` builds the `dynamicViewEntry` arg at BOTH `buildWmsParams` call sites — Effect 2 (~1182-1208) and Effect 3 (~1416-1441) — from `useDynamicViewStore.getState().views[dvId]` (raw dv) + `dynamicViewVersion`. Neither reads `useFilterViewStore.dvViews[dvId]`.

### The fix — read-path precedence at the MapChartRenderer dv-entry resolution (recommended; keeps wmsUrlBuilder signature unchanged)
- LOCKED precedence for a dv-backed layer (`layer.dynamic_view_id != null`): **filtered-dv → raw-dv → skip**.
  1. Read `dvFilter = useFilterViewStore.getState().dvViews[dvId]`. If `dvFilter` exists, `dvFilter.materializing === false`, AND `dvFilter.viewName` is a non-empty string → an active materialized dv-filter. Build the `DynamicViewEntryInput` as `{ status: "materialized", viewName: dvFilter.viewName }` and pass `dynamicViewVersion = dvFilter.materializeVersion` (the `_mv` cache-buster). This makes `buildWmsParams` Case 1 emit `LAYERS=<filtered-dv view>` + `_mv=<filter materializeVersion>`.
  2. Else (no dv-filter / still materializing) → the EXISTING behavior: `dynamicViewEntry` from `useDynamicViewStore.views[dvId]` (raw dv) + `dynamicViewVersion` from `useDynamicViewStore.dynamicViewVersion`. Pending/over_threshold/error dv → unchanged (still returns null → layer skipped, over-threshold overlay preserved).
- LOCKED: do NOT change `buildWmsParams`'s signature or its 4-case precedence — a materialized dv-filter view IS a regular Kinetica view, so it slots into the existing Case-1 `dynamicViewEntry` path. (If the planner finds a cleaner seam INSIDE buildWmsParams via a new optional `dvFilterEntry` arg, that is acceptable IF the table path + existing dv path stay byte-compatible and all existing wmsUrlBuilder.spec cases pass — but the lower-risk cut is at the MapChartRenderer call sites.)
- LOCKED cache-bust correctness: because the dv-filter view name is session-scoped and STABLE across re-drills (`_kbi_filt_…_dv<id>_s<session>` — same name, CREATE OR REPLACE swaps the data), the `_mv` MUST come from `dvFilter.materializeVersion` so OL cache-busts when the filter VALUE changes (re-drill → same view name, new data, bumped materializeVersion). On apply/clear the LAYERS NAME itself flips (raw↔filtered) → URL changes → cache-bust automatic (Pitfall 5).

### New re-render subscription (so the map reacts to dv-filter apply/clear/re-materialize)
- LOCKED: add a `dvFilterViewsKey` selector in MapChartRenderer mirroring the existing `viewsKey` (~575) but over `useFilterViewStore.dvViews`, scoped to the dv ids of `includedLayers` with `dynamic_view_id != null`: per id `${dvId}:${dvViews[dvId]?.viewName ?? ''}:${dvViews[dvId]?.materializeVersion ?? 0}:${dvViews[dvId]?.materializing ? '1' : '0'}`, sorted ascending, joined. Add it to the dep arrays of Effect 2 + Effect 3 (alongside `viewsKey` / `dynamicViewsKey`) so a dv-filter materialize/clear re-fires the WMS layer rebuild. (The existing `dynamicViewsKey` tracks the RAW dv store only — it does NOT move when the filter store changes; that is exactly why the map is stuck today.)

### Optional consistency (planner's discretion — flag, don't force)
- The map info-query / legend dv resolution (~1654-1668) reads the raw dv view. For full consistency, clicking a feature on a filtered map could query the filtered-dv view too. This is SECONDARY to the rendered-tiles gap (the operator's actual complaint). Planner may include it as a small additional task IF low-risk; otherwise note it as a follow-up. The PRIMARY must-have is the rendered WMS tiles FROM-swap.

### Invariants
- Table-backed map layers + plain dv-backed (no active filter) layers: BYTE-UNCHANGED LAYERS/_mv (regression-test). Sole-materialize-trigger preserved (map is read-only; no `materializeFilter`/`dropFilterView` call added to MapChartRenderer). dv-isolated scope (a layer only swaps for ITS OWN dv's filter). Frontend vitest 100% from `packages/web`; web tsc clean. ZERO `packages/server` diff.
</decisions>
