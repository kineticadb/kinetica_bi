## The boot sequence — worked out, not left to luck

Three things now race to drive what renders on `App`'s first mount. The resolution order is:

1. **Auth bootstrap** (`App.tsx:77-84`, `status: "unknown" -> "authenticated"`). Until it finishes, `App.tsx:281` already returns the full-screen `Loading…`. `useDeepLinkDashboard` deliberately does nothing while status is not `"authenticated"`, so it simply stays `pending` behind that gate.
2. **The render gate, in this exact order** (this ordering is load-bearing):
   - `status === "unknown"` -> `Loading…`
   - `status !== "authenticated"` -> `<LoginPage />` — **checked BEFORE the deep-link hold**, otherwise an unauthenticated arrival would hang on `Loading…` forever instead of reaching login. (The logged-out deep link is Phase 115; this phase must merely not break it, and must not strip the param.)
   - `deepLink.status === "pending"` -> the SAME `Loading…` shell. One continuous loading state, never a flash of the wrong page.
3. **Phase 7 ReturnTo restore** (`App.tsx:202-238`) fires synchronously on the transition into `"authenticated"` and may `setPage(...)` to something other than `"dashboards"`. The deep link must win, because a pasted URL is a fresh explicit intent. It does win deterministically, not by luck: the ReturnTo effect is synchronous on that transition, whereas the deep-link outcome can only land after an awaited `listDashboards()` round-trip. The new `setPage("dashboards")` effect is therefore placed AFTER the ReturnTo effect in source order as well, so even a hypothetical synchronous resolution lands last.

**Do NOT modify the ReturnTo block (`App.tsx:200-238`) or the `ReturnTo` type (`App.tsx:35-38`).** Phase 115 must EXTEND that type to carry a dashboard id; nothing here may make that harder. This plan adds only new effects alongside it.
</boot_ordering>
