<objective>
Confirm in a REAL browser the two things the automated suite structurally cannot: that there is no visible flash of the dashboard list on a successful deep link, and that the failure banner reads identically for a deleted dashboard and for one the signed-in user simply cannot see.

Purpose: CLAUDE.md §"Writing verifiable acceptance criteria" is explicit that "no visible flash" is not automatically verifiable and must be routed to a human rather than dressed in a grep. Plans 01-02 prove the structural precondition — while a deep link is pending, `DashboardsPage` is not in the DOM at all, and both failure causes flow through one `setState({ status: "unavailable" })` and one exported message constant. Only a person watching a real tab can confirm that this actually reads as one continuous load, and only a second real account can confirm the not-permitted case end to end.

Output: `.planning/phases/114-deep-link-load-error-states/114-UAT.md` recording the operator's result for each check.

**Note before recording a FAIL on check 3 or 4:** landing a FAILED link on the dashboard LIST is the design, not a defect. ROADMAP criterion 1 ("without the dashboard-list page appearing first") governs the SUCCESS path only; a link that cannot be opened has nowhere better to land, and the operator chose list-plus-banner over a dead-end error page (114-CONTEXT.md).
</objective>

  <what-built>
    The app now reads `?dashboard=<id>` from the URL on boot. While it resolves — auth bootstrap plus one `GET /api/dashboards` — the screen holds the app's existing full-screen `Loading…`; the dashboards page is not rendered at all during that window, so the list cannot appear first. If the id is in the permission-filtered list, the dashboard opens directly and the param stays in the address bar. If it is not — whether because the dashboard was deleted or because this user is not permitted to see it, which the server deliberately does not distinguish — the user lands on the dashboard list with one dismissible banner reading "This dashboard isn't available — it may have been deleted, or you may not have access.", and `?dashboard=` is stripped from the address bar. A `?dashboard=abc` style junk param counts as no deep link and is likewise stripped. A deep-link arrival pushes no history entry of its own, so the in-app "Back to dashboards" button writes the list URL rather than popping the user out of the app. Visiting a link while logged OUT still goes to the login page and keeps the param — landing on the dashboard after login is Phase 115 and is NOT expected to work yet.
  </what-built>

  <how-to-verify>
    Start the dev server (`npm run dev` at the repo root, plus `npm run dev:server`). Have TWO accounts available: your normal one, and an analyst-style account that has NOT been granted access to at least one dashboard. Use a freshly opened tab for each paste, so the tab's history starts clean.

    1. **Deep link opens the dashboard — watch for the flash.** While signed in, open a dashboard normally and copy the address bar (it reads `…/?dashboard=<id>`). Open a NEW tab and paste it. Expected: after a brief plain loading screen you land directly ON that dashboard. **Watch the whole transition closely and say explicitly whether the dashboard LIST (the table of dashboard names with Open/View/Edit buttons) appeared at any point, even for a frame.** Any sighting of the list is a FAIL of ROADMAP criterion 1 — this check exists for exactly that. Repeat once with a hard reload (Cmd-Shift-R) so the bundle is cold and the window is at its widest.

    2. **Which loading screen did you see?** During check 1's transition, the screen should be the plain centred `Loading…` on an empty background — the same one you see when the app is starting up normally. It must NOT be the dashboards page with its heading, "Dashboards" title card and a "Loading dashboards…" line inside it. Record which of the two you saw, in your own words.

    3. **Nonexistent dashboard.** In a new tab, visit `…/?dashboard=999999` (any id you are confident does not exist). Expected: the dashboard LIST with a banner across the top. **Quote the banner text back verbatim**, and state what the address bar reads afterwards — it must no longer contain `dashboard=`. Then press reload: the banner must NOT come back (the error is not replayed). Confirm the banner's `×` dismisses it.

    4. **Real dashboard, no access — the non-leak check.** Sign in as the analyst account that has NOT been granted a particular dashboard, and visit that dashboard's REAL id: `…/?dashboard=<real id>`. Expected: the same landing on the dashboard list with a banner. **Quote this banner text back verbatim too.** The two quotes from checks 3 and 4 must be identical, word for word — if they differ in any way, the app is leaking which ids exist and that is a FAIL of ROADMAP criterion 3. Also confirm nothing from the dashboard itself (its name, its widgets) appears anywhere on screen or in the banner.

    5. **In-app Back after arriving by URL.** Repeat check 1 to land on a dashboard via a pasted link, then click the in-app "Back to dashboards" button. Expected: the dashboard list appears, the address bar is clean, and **you are still inside the application** — you must NOT be thrown out to a blank tab or to whatever the tab showed before. (This is the no-history-entry-to-pop case Phase 113 built for and could not previously be reached by hand.)

    6. **Junk parameter.** In a new tab, visit `…/?dashboard=abc`. Expected: the ordinary dashboard list, **no banner**, and the `?dashboard=abc` gone from the address bar. Seeing the banner here is a deviation from the locked decision (a junk param counts as "no deep link", not as a failure) — record it rather than accepting it.

    7. **Away and back.** Land on a dashboard via a pasted link (check 1), then click **Datasets** in the sidebar, then click **Dashboards**. Expected: the dashboard LIST, not the deep-linked dashboard re-opening itself, and a clean address bar.

    Record each check in `.planning/phases/114-deep-link-load-error-states/114-UAT.md`, one line per check, prefixed `UAT-114-1` … `UAT-114-7`.
