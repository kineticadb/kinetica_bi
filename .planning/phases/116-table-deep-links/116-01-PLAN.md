```typescript
/**
 * lib/tableUrl.ts — Phase 116 Plan 01 (TLINK-V121-01/06/07).
 *
 * The TABLE sibling of lib/dashboardUrl.ts. Deliberately a SEPARATE module, not a rename and not
 * a shared factory: renaming or parameterizing dashboardUrl.ts would force import-path edits
 * across 7 spec files / 132 tests, which ROADMAP §Phase 116 criterion 6 forbids (116-RESEARCH §Q1).
 * dashboardUrl.ts is NOT touched by this phase.
 *
 * Locked decisions inherited from 113-CONTEXT.md, unchanged for tables:
 *   - Query param, never a path or hash.
 *   - Numeric id, never a name/slug.
 *   - Opening pushes exactly ONE history entry, marked as ours.
 *   - Leaving pops that entry if we own it; an arrival with NO entry of ours WRITES the list URL
 *     instead, because history.back() there would eject the user out of the application.
 *
 * NEW for tables (116-CONTEXT.md §"THE ONE NEW DECISION"):
 *   - A `mode` qualifier: ?table=12 is VIEW, ?table=12&mode=edit is EDIT.
 *   - Absent-means-view, and an UNRECOGNISED mode value also means view — never a failure. The id
 *     is the identity and it is valid; refusing to open a real table over a typo in a secondary
 *     qualifier is worse for the user than quietly showing the safer of the two modes.
 *   - `create` and `list` are not linkable.
 */

export const TABLE_URL_PARAM = "table";
export const TABLE_MODE_PARAM = "mode";
export const TABLE_HISTORY_MARKER = "kbiTableEntry";

export type TableMode = "view" | "edit";
```

Then, in this order (each with a short doc comment stating WHY, as `dashboardUrl.ts` does):

1. `isValidTableId(value: unknown): value is number` — `typeof value === "number" && Number.isInteger(value) && value > 0`. A type-guard, not a boolean, for the same reason `isValidDashboardId` is one: the id arrives from TWO untrusted sources (the URL param and the `kbi_returnTo` blob) and callers need to narrow `unknown` straight to `number`.
2. `readTableIdFromSearch(search: string): number | null` — `new URLSearchParams(search).get(TABLE_URL_PARAM)`; reject with `/^\d+$/`; return `isValidTableId(id) ? id : null`.
3. `readTableModeFromSearch(search: string): TableMode` — returns `"edit"` **only** on an exact `"edit"` match, `"view"` for everything else including absent, empty, `"EDIT"` and `"banana"`. Comment the unrecognised-means-view decision here, citing 116-CONTEXT.
4. `hasTableParam(search: string): boolean` — `new URLSearchParams(search).has(TABLE_URL_PARAM)`. Same pairing rationale as `hasDashboardParam`: lets a caller tell "no deep link" from "junk deep link" and strip the junk.
5. `buildTableUrl(loc: { pathname: string; search: string; hash: string }, id: number | null, mode: TableMode = "view"): string` — on `id === null`, `params.delete(TABLE_URL_PARAM)` **and** `params.delete(TABLE_MODE_PARAM)`. Otherwise `params.set(TABLE_URL_PARAM, String(id))` and then `mode === "edit" ? params.set(TABLE_MODE_PARAM, "edit") : params.delete(TABLE_MODE_PARAM)` — view is expressed by the param's ABSENCE, so the URL of a view is the short, canonical one. Add a comment noting that `mode` is a generic param name and this module owns it exclusively today (grep confirms no other `?mode=` consumer in `packages/web/src`); if one is ever added, this delete becomes a collision.
6. `openTableUrl(id: number, mode: TableMode): void` — `pushState({ [TABLE_HISTORY_MARKER]: true }, "", buildTableUrl(window.location, id, mode))`.
7. `clearTableUrl(): void` — `replaceState(null, "", buildTableUrl(window.location, null))`. Comment: replaceState ONLY — correcting the CURRENT entry, not navigating; also drops our marker, which is correct because once the param is gone the entry no longer represents an open table.
8. `restoreTableUrl(id: number, mode: TableMode): void` — `replaceState(null, "", ...)`. Comment: needed because the OIDC success redirect returns the browser to a bare `/`, so after the round trip the bar must be re-synced or it would describe the table LIST while a table is open.
9. **`setTableMode(id: number, mode: TableMode): void`** — the ONE writer with no dashboard analogue. MUST be:
   ```typescript
   window.history.replaceState(window.history.state, "", buildTableUrl(window.location, id, mode));
   ```
   Comment it explicitly (this is 116-RESEARCH Pitfall 3): it changes the mode qualifier on the
   CURRENT entry **without disturbing whether that entry is "ours" (pushed from the list) or
   "arrived" (a fresh `?table=12&mode=edit` paste)**. `leaveTableUrl()`'s pop-vs-write branch must
   see the SAME answer after a Save as it would have before it. Writing `replaceState(null, ...)`
   would silently convert a self-opened edit into a write-instead-of-pop (losing a real history
   entry); writing `replaceState({[TABLE_HISTORY_MARKER]: true}, ...)` would make a deep-linked
   arrival start popping, ejecting the user out of the app. Neither hardcoding is correct — it
   must PRESERVE.
10. `leaveTableUrl(): "popped" | "wrote"` — read `window.history.state as Record<string, unknown> | null`; if `state[TABLE_HISTORY_MARKER] === true` then `window.history.back()` and return `"popped"`, else `clearTableUrl()` and return `"wrote"`. Carry `dashboardUrl.ts`'s comment about why the unmarked branch must not call `history.back()`.

Do NOT import anything from `lib/dashboardUrl.ts`. Do NOT edit `lib/dashboardUrl.ts`.
No React, no component imports — this module is pure + History API only.
