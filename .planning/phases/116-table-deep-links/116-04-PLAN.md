<precedence_rule_locked>
`?dashboard=` and `?table=` can coexist in a hand-crafted URL. `URLSearchParams` treats them as
independent keys; no code anywhere checks for the other's presence today (grep-confirmed: 0
occurrences of any such check). With two uncoordinated effects both calling `setPage`, the winner
would be decided by React batching and source-declaration order — an implicit, fragile outcome.

**LOCKED RULE: dashboard wins.** Arbitrary between the two (there is no product reason to prefer
either), chosen because it is the simplest rule to state and test AND because it means the
EXISTING dashboard effect needs zero changes — only the NEW table effect carries a guard clause.

Expressed strictly: the table effect acts **only when `deepLink.status === "none"`** — i.e. when
there is no dashboard link in play at all, in any state. Guarding on "opened or pending" alone
would leave the `unavailable`/`error` combination undefined, with the dashboard effect setting
`page` to dashboards and the table effect fighting it back to datasets.

When a dashboard link IS in play and a stale `?table=` sits in the bar, strip it — the address bar
must not describe two screens at once.
</precedence_rule_locked>

<parallel_refs_not_shared_ones>
`deepLinkConsumedRef` and `returnToWonElsewhereRef` must NOT be generalized or reused for tables.
Add SIBLING refs: `tableDeepLinkConsumedRef` and `tableReturnToWonElsewhereRef` (the latter is
written by Plan 05; declare it here so the table effect can read it).

What breaks if the dashboard refs are reused: the single `deepLinkConsumedRef` would be burned by
whichever entity resolves to `"opened"` FIRST, permanently suppressing the OTHER entity's
otherwise-valid, independent deep link for the rest of the session — a real, silent defect. Two
refs, cheaply, avoids it entirely.

Both must follow the codebase's StrictMode-safe idiom: `useRef(false)`, flipped INSIDE an effect,
never in the render body.
</parallel_refs_not_shared_ones>
