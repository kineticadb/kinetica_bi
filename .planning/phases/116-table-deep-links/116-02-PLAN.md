<the_non_leak_finding_you_must_record_verbatim>
114-CONTEXT's combined-message decision ("it may have been deleted, **or you may not have
access**") rests on a dashboard-specific server fact: there is no `GET /api/dashboards/:id`, and
`GET /api/dashboards` is permission-filtered server-side, so a missing id is genuinely ambiguous
between deleted and not-permitted.

**That reasoning does NOT hold for tables.** Research verified directly against
`packages/server/src/index.ts`:
- `GET /api/tables/:id` **does** exist (`index.ts:2352`) and carries no permission middleware.
- `GET /api/tables` carries no permission middleware either. Both sit behind the app-wide
  `app.use("/api", requireAuth)` (`index.ts:641`) and nothing else.
- There is **no `DATASETS_VIEW` permission** and no per-table ACL anywhere in
  `packages/server/src`. The only table permission is `DATASETS_MANAGE`, which gates WRITES only.
- The client agrees: `Sidebar.tsx`'s Datasets entry carries no `permission` field, and
  `DatasetsPage.tsx` contains zero `hasPermission` calls.

**Therefore "not permitted" is not a reachable state for tables today.** Every id either exists
(any authenticated user may view it) or does not (a real 404).

**OPERATOR DECISION (locked, 2026-09-14) — the failure-banner copy is NARROWED for tables.**
Use: `"This table isn't available — it may have been deleted."`
Do **NOT** reuse the dashboard's two-clause wording. Reasoning to record: Phase 114's combined
wording existed *because* deleted and not-permitted were genuinely indistinguishable for
dashboards. For tables they are not. Keeping the second clause would copy Phase 114's words while
discarding the reasoning that justified them.
**If per-table permissions are ever added, this copy must change alongside them** — leave that
sentence in the source as a comment.

Body, mirroring the dashboard hook:

```typescript
const authStatus = useAuthStore((s) => s.status);

const [state, setState] = useState<DeepLinkTableState>(() => {
  const id = readTableIdFromSearch(window.location.search);
  if (id !== null) {
    return { status: "pending", id, mode: readTableModeFromSearch(window.location.search) };
  }
  // Present but unparseable ("?table=abc"): NOT a deep link, but strip it so the address bar
  // matches the list that is about to render (TLINK-V121-06).
  if (hasTableParam(window.location.search)) clearTableUrl();
  // URL first, storage second — the same precedence Phase 114 established for dashboards.
  if (storedTable && isValidTableId(storedTable.id)) {
    return { status: "pending", id: storedTable.id, mode: storedTable.mode };
  }
  return { status: "none" };
});

const startedRef = useRef(false);

useEffect(() => {
  if (state.status !== "pending") return;
  if (authStatus !== "authenticated") return;   // logged-out arrival: the param must survive
  if (startedRef.current) return;
  startedRef.current = true;
  const pendingId = state.id;
  const pendingMode = state.mode;
  listTables()
    .then((list) => {
      const match = list.find((t) => t.id === pendingId);
      if (match) {
        setState({ status: "opened", table: match, mode: pendingMode });
        return;
      }
      clearTableUrl();
      setState({ status: "unavailable" });
    })
    .catch(() => {
      if (useAuthStore.getState().status !== "authenticated") {
        startedRef.current = false;   // re-arm: a same-tab re-auth retries
        return;
      }
      clearTableUrl();
      setState({ status: "error" });
    });
}, [state, authStatus]);

return state;
```

Comment the `storedTable` parameter exactly as the dashboard hook comments `storedId`: it is
consumed at MOUNT ONLY, because `App.tsx` reads `kbi_returnTo` in its own mount-time initializer
and the value must be present on App's FIRST render — accepting it later would mean the tables
LIST had already rendered for a frame, which is the flash TLINK-V121-02 forbids. The hook
deliberately does NOT read `sessionStorage` itself: `App.tsx` owns the ONE `kbi_returnTo` parser.
