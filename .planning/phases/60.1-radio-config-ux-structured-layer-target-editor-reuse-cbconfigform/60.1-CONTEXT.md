# Phase 60.1: Radio Config UX — Structured Layer-Target Editor (reuse the FULL layer form, side-by-side) - Context

**Gathered:** 2026-06-12
**Status:** Ready for planning (RE-SCOPED 2026-06-12 after operator review — supersedes the first 60.1 cut)
**Source:** Interactive design discussion + operator mockups (5 images) + 2 locked Q&A answers

> **RE-SCOPE NOTE:** The first 60.1 execution shipped a NARROW editor (render-mode `<select>` + standalone `CbConfigForm`, scoped to the 5-field allow-list). The operator reviewed it and wants the OPPOSITE: reuse the **entire `KineticaWmsLayerForm`** (the Map Layers config form) **side-by-side** in the radio config modal, so a radio option can set the layer's FULL appearance. This CONTEXT replaces the prior one. The prior narrow `RadioLayerConfigEditor` is SUPERSEDED (to be replaced); the `radioGroupLayerPatch` adapter is partly reused.

<domain>
## Phase Boundary

**Delivers:** When a radio-group option targets a MAP LAYER, the "Configure: Radio Group" modal becomes a **side-by-side** layout (mirroring the Map Layers modal): LEFT = the radio group config (title/orientation/options/the option being edited); RIGHT = the **full `KineticaWmsLayerForm`** for that option's target layer — render mode + ALL its style params, opacity, layer name, legend, zoom range, AND the INFO POPUP (info-click) section. The designer configures the layer exactly as in Map Layers; that configuration is captured as the radio option's action and applied (overlaid) live when the option is selected.

**Apply model (LOCKED):** FULL-CONFIG SNAPSHOT OVERLAY. The option stores the whole form-produced layer config (config blob + top-level `cb_config`/`track_config` + top-level `info_*`), and the engine overlays it wholesale onto the target layer. NOT a 5-field allow-listed patch.

**Patch scope (LOCKED):** render/style fields **+ info-click (info popup) details** (`info_enabled`/`info_columns`/`info_template`). **EXCLUDE for now: Data Source and Spatial Mode** — `table_id`, `dynamic_view_id`, `spatialMode`, and spatial columns (`latColumn`/`lonColumn`/`wktColumn`/`wkbColumn` + track x/y/id/order). A radio switches how a layer LOOKS, not which data it's bound to.

**Does NOT deliver / out of scope:**
- Changing a layer's data source / spatial mode / columns via a radio (those sections are hidden in this context).
- Any change to widget-target or dynamic-view-target authoring — they keep their CURRENT simple inputs, unchanged.
- Cross-dashboard targeting; new server routes. Frontend-only (flag any server diff).

**The safety reconciliation (LOCKED):** The strict per-field allow-list (`LAYER_ALLOW_LIST` = renderMode/visible/opacity/cb_config/track_config) was too narrow for "all the options." For the DESIGNER UI layer-snapshot path, validation switches to a DENYLIST (block `PERMANENTLY_BLOCKED_KEYS` + data-binding keys; allow all other render/style/info fields). The strict field allow-list REMAINS the contract for (a) widget + dynamic-view targets and (b) the future AI/MCP path — those do NOT author via this form. Rationale: the designer already has full layer-config power in Map Layers; a full-config snapshot is a "layer appearance bookmark," not arbitrary field injection. Meta keys (`id`/`tableId`/`type`/`__proto__`) stay permanently blocked.
</domain>

<decisions>
## Implementation Decisions (LOCKED)

### Layout — side-by-side (images #3, #4, #5)
- LOCKED: For a LAYER-target option, render a two-pane layout inside the radio config modal. LEFT pane = the existing radio group config (title, orientation, options list, the OptionRow being edited). RIGHT pane = the full `KineticaWmsLayerForm` for the selected option's target layer. Mirror the Map Layers modal's split (`LayersModal`).
- LOCKED: The config modal (`.modal-content.modal-config` in DashboardsPage.tsx ~line 1172) must WIDEN to accommodate two panes when a layer-target option is being edited. Widget/dynamic-view targets keep the current single-column width + inputs.
- Follow existing config-panel/LayersModal styling + theme tokens (no hardcoded colors; green accent section headers, etc. — operator catches UI-consistency deviations). See [[ui-consistency-conventions]].

### Reuse the FULL form (not a subset)
- LOCKED: Reuse `KineticaWmsLayerForm` WHOLESALE (do NOT rebuild any of it). It is a pure controlled component `{ config, onChange, columns, isValid?, infoEnabled?, infoColumns?, infoTemplate?, onChangeInfoConfig?, ... }`.
- LOCKED: SUPPRESS the DATA SOURCE section — simply do NOT pass `layer` / `onDataSourceChange` (the form already returns null for that section when they're absent — KineticaWmsLayerForm.tsx ~line 468: `if (!layer || !onDataSourceChange) return null;`). No code change needed for data-source suppression.
- LOCKED: SUPPRESS the SPATIAL MODE section — it currently always renders, so ADD an additive prop to `KineticaWmsLayerForm` (e.g. `hideSpatialMode?: boolean`, default false → existing callers unaffected) that omits the SPATIAL MODE + spatial-column block. Keep RENDER MODE + all mode params + opacity + layer name + legend + zoom + INFO POPUP.
- LOCKED: WIRE the INFO POPUP section — pass `infoEnabled`/`infoColumns`/`infoTemplate` (seeded from the snapshot/target layer) + an `onChangeInfoConfig` that folds `info_*` into the snapshot (top-level fields).

### The snapshot (option.action.configPatch for layer targets)
- LOCKED: For a layer target, `configPatch` is a FULL layer-config snapshot:
  - nested `config` blob: renderMode + ALL style keys the form edits (colormap, BLUR_RADIUS, POINTCOLOR/POINTSIZE/POINTSHAPE, contour params, opacity, layer name, legend/zoom keys, etc.) — but with DATA-BINDING/SPATIAL keys STRIPPED (`spatialMode`, `latColumn`, `lonColumn`, `wktColumn`, `wkbColumn`, track x/y/id/order columns).
  - top-level `cb_config`, `track_config` (JSON strings).
  - top-level `info_enabled`, `info_columns`, `info_template`.
  - NEVER: `table_id`, `dynamic_view_id`, `id`, `type`, `__proto__`, or other meta/binding keys.
- LOCKED: The cb_config top-level↔`config.cb_config` split still applies — `KineticaWmsLayerForm`/`CbConfigForm` read `config.cb_config`, but the snapshot/overlay store it top-level. Reuse/extend the existing `radioGroupLayerPatch` adapter (built in the first 60.1 cut) for this lift/lower, and keep it consistent with `widgetActionStore.deriveOverlays` / `MapChartRenderer.effectiveLayers` (`{ config, ...topLevel }`).
- LOCKED: Capture is "what the form currently shows" → snapshot. Seeding the form = snapshot → form config (lift cb_config into config.cb_config; surface info_* as the info props). This is a fuller version of `radioGroupLayerPatch.patchToLayerFormConfig` / `layerFormConfigToPatch`.

### Engine / validation (touches Phase 58 allow-list)
- LOCKED: Add a DENYLIST validation path for the layer-snapshot (designer UI) case — block `PERMANENTLY_BLOCKED_KEYS` (id/tableId/type/__proto__ — already defined in actionAllowList.ts ~line 38) PLUS data-binding keys (`table_id`, `dynamic_view_id`, `spatialMode`, `latColumn`, `lonColumn`, `wktColumn`, `wkbColumn`, track spatial columns); ACCEPT all other keys. Used by the radio-LAYER authoring path (save-time `validateRadioOption`) AND by `applyWidgetAction` dispatch for these snapshots.
- LOCKED: The strict per-field `validateActionPatch`/`LAYER_ALLOW_LIST` REMAINS unchanged and is still used for: widget targets, dynamic-view targets, and the future AI/MCP path. Do NOT widen `LAYER_ALLOW_LIST` itself. The denylist is a SEPARATE, layer-snapshot-only validation function (e.g. `validateLayerSnapshot`).
- LOCKED: The overlay/apply mechanism is the EXISTING one — `widgetActionStore` contributions + `MapChartRenderer.effectiveLayers` already deep-merge `{ config, ...topLevel }`, so a full snapshot overlays correctly with no engine-merge change. Confirm `info_*` (top-level) overlay reaches the renderer: `includedLayers`/`eligibleLayers` derive from `effectiveLayers` (MapChartRenderer ~lines 529/678), so an overlaid `info_enabled`/`info_columns`/`info_template` takes effect LIVE — VERIFY with a test (this is the GAP-61-01/02 read-live class of risk).

### Disposition of the first 60.1 cut
- LOCKED: REPLACE the narrow `RadioLayerConfigEditor` (render-mode `<select>` + standalone `CbConfigForm`) with the full-form side-by-side editor. The narrow component is superseded.
- LOCKED: KEEP + extend `lib/radioGroupLayerPatch.ts` (the cb_config split adapter) — still needed because the full form reads `config.cb_config`. Extend it from "4 allow-listed fields" to "full snapshot minus data-binding/meta."
- LOCKED: Keep the collapsible raw-JSON "Advanced" fallback for layer targets (escape hatch + back-compat for any option authored by the first cut).
- LOCKED: Widget + dynamic-view target authoring UNCHANGED.

- Whether the right pane edits the CURRENTLY-SELECTED option's target, or shows per-option (likely: the option being edited).

<specifics>
## Specific Ideas

- Add `hideSpatialMode?: boolean` (additive, default false) to `KineticaWmsLayerForm` — when true, omit the SPATIAL MODE radios + spatial-column pickers. Do NOT pass `layer`/`onDataSourceChange` from the radio editor (auto-hides DATA SOURCE). Pass `columns` (resolved from target layer's table/dv), `infoEnabled`/`infoColumns`/`infoTemplate` + `onChangeInfoConfig`, `tableRef`/`schema`/`tableName` for CbConfigForm auto-suggest.
- Extend `radioGroupLayerPatch.ts`: `patchToLayerFormConfig(snapshot)` (lift cb_config→config.cb_config; pass through all style/config keys; expose info_* separately for the info props) and `layerFormConfigToPatch(formConfig, infoPatch)` (lower cb_config→top-level; STRIP data-binding/spatial + meta keys; include info_* top-level). Unit-test: data-binding keys stripped, meta blocked, cb_config placement, info_* round-trip, output passes the denylist validator.
- New `validateLayerSnapshot(patch)` in actionAllowList.ts: reject if any key ∈ PERMANENTLY_BLOCKED_KEYS ∪ DATA_BINDING_KEYS; else valid. Used by `validateRadioOption` (layer + snapshot mode) and `applyWidgetAction`.
- Tests: RadioGroupConfigPanel spec — layer target renders the side-by-side `KineticaWmsLayerForm` (assert a known form section, e.g. RENDER MODE label, present; SPATIAL MODE absent; DATA SOURCE absent); editing render mode / a style param / info toggle updates the snapshot; data-binding keys never appear in the snapshot; widget/dv targets unchanged; Advanced JSON still present. Plus a MapChartRenderer test that an overlaid `info_enabled:0` removes the layer from `eligibleLayers` live.
- Verify the modal widens only for layer-target option editing (CSS class toggle).
</specifics>
