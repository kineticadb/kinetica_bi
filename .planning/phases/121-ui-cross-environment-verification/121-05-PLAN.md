## The tension, and how it is resolved

`cfg.sql` is a COMPLETE SELECT string, not a fragment. Three options were on the table:

**(a) Extract ChartConfigPanel's SQL builder into a shared pure lib that both panel and renderer call.**
Architecturally the cleanest, and it is what `TimelineRenderer` / `NumericLineRenderer` / `CalendarRenderer`
already do via `buildTimelineSql` / `buildNumericLineSql` / `buildCalendarSql`. **REJECTED**, for two
concrete reasons found by reading the code, not by preference:

1. **The renderer does not have the inputs.** `ChartConfigPanel.tsx:359-496` builds four SQL shapes and
   the heatmap branch (`:455-470`) calls `inferDataTypeFromColumn(col, columnTypeMap)` to decide whether
   a group-by column gets a `DATE_TRUNC` bucket. `columnTypeMap` comes from `selectedTable.columns`.
   `AggregatedWidgetRenderer` is invoked as `<AggregatedWidgetRenderer widget={effectiveWidget} />`
   (`WidgetRenderer.tsx:391`) — it receives **no `tables` prop at all**. Threading it in is possible, but
   on the async-load path `tables` is empty on first render, so a rebuild would emit an UNBUCKETED
   heatmap query (every instant its own one-cell row, over the 5000-cell limit) until the tables list
   lands. That is a new visible defect introduced by the fix.
2. **It rebuilds SQL for widgets that are not broken.** Even scoped to `customMode`, a rebuild replaces a
   saved query with a freshly generated one. Any config saved by an older builder version (limit ladders,
   sort direction defaults, `maxBarGroupBySeriesCap` multiplier, `customWhere` formatting) would silently
   start querying something different from what it queried yesterday. The defect is one wrong substring;
   a rebuild changes the whole string.

**(b) Targeted expression swap at render time.** **ADOPTED, hardened.** The naive form of (b) — split the
select list on commas — is genuinely unsafe: `ROUND(AVG(amount), 2) AS value` would be shredded. So (b) is
implemented as a real, depth- and quote-aware scanner in a dedicated pure lib with its own spec, and it is
**fail-closed**: any SQL it cannot fully account for is returned byte-identical, never partially rewritten.

**Why (b) is sufficient.** In all four SQL shapes the panel can emit for a custom metric, the metric
expression is the LAST select-list item and is aliased `AS value`:

| Shape | Source | Emitted form |
|---|---|---|
| scalar (bignumber) | `ChartConfigPanel.tsx:394-397` | `SELECT <expr> AS value FROM <t><cw>` |
| single-column group | `:472-483` | `SELECT <col>, <expr> AS value FROM <t><cw> GROUP BY <col> ORDER BY value <dir> LIMIT <n>` |
| multi-column group | `:472` (via `:415-421`) | `SELECT <cols>, <expr> AS value FROM <t><cw> GROUP BY <cols> ORDER BY value <dir> LIMIT <n>` |
| heatmap | `:455-470` | `SELECT <bucketed cols AS col>, <expr> AS value FROM <t><cw> GROUP BY <exprs> ORDER BY value <dir> LIMIT <n>` |

"Last select-list item, aliased `AS value`" is therefore a complete and unambiguous anchor — and it stays
unambiguous even when a group-by column is itself named `value`, because the rule is positional (LAST item),
not name-based.

**Blast radius, stated honestly.** The change is INERT unless `widget.config.metricId` is a number:
`applyLiveMetricExpr` returns the caller's own string reference on the non-custom path before touching the
parser. Verified: `grep -c metricId packages/web/src/components/charts/WidgetRenderer.spec.tsx` → **0**, so
all **125** existing `it(` blocks in that spec are real-column widgets and are expected to be unaffected —
that is an invariant plan 121-06 asserts, not a hope. `packages/server` is untouched. The export/import
file format and `dashboardImport.ts` are untouched (Phases 119/120 stay closed): fixing the renderer, not
the importer, also fixes the CONFIRMED single-environment staleness bug in environment A, which has never
been imported into. Regenerating `config.sql` in import Pass 2 would fix only the import symptom.

## Orphaned / deleted metric — specified behaviour

`resolveMetricExpr` returns `null` both when the metric was DELETED and when the table's metrics were never
loaded. Those two must not be conflated, so `isMetricsHydrated(tableId)` splits them:

| State | Discriminator | `applyLiveMetricExpr` returns | Rationale |
|---|---|---|---|
| not a custom metric | `!isCustomSelection(metricId)` | `{kind:"ready", sql: storedSql}` — **same reference** | zero blast radius on every non-custom widget |
| custom, `tableId` undefined (legacy widget) | `tableId === undefined` | `{kind:"ready", sql: storedSql}` | nothing to resolve against; status quo |
| custom, table never loaded | `!isMetricsHydrated(tableId)` | `{kind:"pending"}` | caller SUSPENDS — must not fire a query with the stale expression |
| custom, table loaded, id absent → **DELETED** | `resolveMetricExpr` → `null` | `{kind:"ready", sql: storedSql}` | frozen text is the only surviving definition; blanking a working widget would be a regression. The config panel already flags it via `isOrphanedMetric`. |
| custom, resolved, parse fails | `replaceValueSelectItem` → `null` | `{kind:"ready", sql: storedSql}` | fail-closed — never emit a query we could not fully parse |
| custom, resolved, parse succeeds | — | `{kind:"ready", sql: rewritten}` | the fix |

**Scanner state machine** (shared by both parser functions — write it once as a module-local walker):
walk the string char by char tracking `inSingle` (entered/left on `'`, where a doubled `''` stays inside),
`inDouble` (entered/left on `"`), and `depth` (`+1` on `(`, `-1` on `)`) — all three are ignored while
inside a quote. "Top level" means `!inSingle && !inDouble && depth === 0`.

`parseAggregatedSelectList(sql)`:
1. Require `sql.trimStart()` to begin with the literal `SELECT ` (case-SENSITIVE — `ChartConfigPanel` emits
   uppercase and is the only producer). Otherwise return `null`.
2. Scan forward from just past that `SELECT `. Record every top-level `,` as an item separator. Stop at the
   first top-level occurrence of the literal ` FROM ` (leading and trailing single space, case-SENSITIVE).
3. Return `null` if no top-level ` FROM ` is found, or if `depth !== 0` at that point, or if the scan ends
   inside a quote.
4. Return `{ items, fromStart }` where `items` are `{start, end}` offsets into the ORIGINAL string covering
   the span between `SELECT ` and `fromStart`, split at the recorded separators.

`replaceValueSelectItem(sql, newExpr)`:
1. `const parsed = parseAggregatedSelectList(sql); if (!parsed) return null;`
2. Take the LAST element of `parsed.items`. Its text, `trimEnd()`-ed, must end with the literal ` AS value`
   (case-SENSITIVE). Otherwise return `null`.
3. Validate `newExpr`: after `trim()` it must be non-empty, balanced on parens and quotes, and contain no
   top-level comma (run the same walker over it). Otherwise return `null`.
4. Compute the expression span: `exprStart` = the last item's `start` advanced past leading whitespace;
   `exprEnd` = `exprStart + <trimmed item text>.length - " AS value".length`.
5. Return `sql.slice(0, exprStart) + newExpr.trim() + sql.slice(exprEnd)`.

`applyLiveMetricExpr(storedSql, metricId, tableId)` — implement the six rows of the table in
`<design_decision>` IN THAT ORDER, so the cheap guards run before the parser:
```ts
if (!isCustomSelection(metricId)) return { kind: "ready", sql: storedSql };
if (storedSql === undefined || tableId === undefined) return { kind: "ready", sql: storedSql };
if (!isMetricsHydrated(tableId)) return { kind: "pending" };

if (expr === null || expr.trim() === "") return { kind: "ready", sql: storedSql };  // DELETED metric
return { kind: "ready", sql: replaceValueSelectItem(storedSql, expr) ?? storedSql }; // fail-closed
```
