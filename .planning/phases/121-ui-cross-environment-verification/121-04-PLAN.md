### Step 0 — Understand what this setup does and does not prove

You will run **two independent server processes against two separate SQLite files**, each with its
own Vite SPA. That gives two genuinely independent id spaces, so ids collide naturally and tables must
be MATCHED by `schema.name` rather than found by identity.

**It proves:** real portability of the export file between two installs; two independent
AUTOINCREMENT id spaces; the download and upload mechanics in a real browser against a real server.

**It does NOT prove:** the docker/nginx same-origin deployment path (both SPAs run under Vite, so the
blob-download path is exercised and the nginx same-origin path is not); a real network hop or a second
machine; a different Kinetica cluster — both servers share `packages/server/.env`, hence the same
`KINETICA_URL`. So this is a test of **metadata portability**, not of data-source portability. Say
exactly this in the approval record; do not let it be written up as more than it is.

### Step 1 — Build the source dashboard in your CURRENT environment (environment A)

Dashboard 4 ("Test Dashboard") is NOT sufficient: Phase 119 recorded `customMetrics: 0` and
`dynamicViews: 0` for it, and closing that exact gap is this phase's job. Build a NEW dashboard, or
extend one, so that it carries ALL of the following. Tell us which dashboard you used.

1. **A custom metric (REF-4).** Datasets -> click a table -> `Custom metrics` -> add one with a
   distinctive label (e.g. `RoundTripMetric`) and a real expression (e.g. `SUM(<a numeric column>)`).
   Then on a bar/pie/table widget bound to that table, open its config and set **Metric Column** to
   that metric from the "Custom metrics" optgroup.
2. **The same metric used in a metrics ARRAY (REF-5).** Add a **Timeline Chart** or **Numeric Line
   Chart** widget on that table and pick the custom metric in one of its metric rows. REF-5 is a
   *different code path* from REF-4 — this widget is the only thing that exercises it.
3. **A dynamic view, actually BOUND (REF-2).** Open the dashboard -> toolbar `Dynamic Views` -> create
   a view on one of the dashboard's tables with a `{view}`-templated filter SQL -> Preview it so its
   columns populate. Then bind it: either set a widget's **Data Source** to it (the "Dynamic Views"
   optgroup), or set a map layer's Data Source to it in `Map Layers`. **An unbound dv definition does
   NOT exercise REF-2** — `dynamicViewId` has to be written into a widget or layer config.
4. **A map widget with layers (REF-6)** and, if you can, **a standalone Legend widget bound to that
   map (REF-3)** and **a Radio Group whose options carry actions (REF-8)**. These three are already
   live-verified from Phase 119, but they are what ROADMAP criterion 4 asks you to exercise.

Note: `DEFAULT_VIEW_TTL_MINUTES=3` in `.env`. If a dv-bound widget goes empty after a few minutes of
idling, that is the materialized-view TTL expiring, not a remapping bug. Reload to re-materialize.

### Step 2 — Start environment B (second server, separate database, separate port)

Leave your current server and SPA running as environment A. In two NEW terminals:

```sh
# Terminal 3 — server B. Separate SQLite file, separate port.
# Inline vars WIN over .env (dotenv.config() does not override process.env), so nothing in
# packages/server/.env is edited or needs undoing.
# APP_ADMIN_USERNAME matters: server B boots with an EMPTY database, and a user with no
# user_roles rows falls back to the ANALYST role (dashboards:view only) — you would not see the
# Import button at all. Naming yourself the bootstrap admin short-circuits before any DB read
# and grants every permission. Use the SAME username you log into the app with.
cd packages/server && DB_PATH=./data/env-b.db PORT=4001 APP_ADMIN_USERNAME=<your-login-username> npm run dev
```

```sh
# Terminal 4 — SPA B, pointed at server B, on 5174 (already in CORS_ORIGIN — no server change).
cd packages/web && VITE_API_URL=http://localhost:4001 npm run dev -- --port 5174
```

**Cookie collision — read this before opening the second tab.** The session cookie `kbi_session` is
set on `localhost` with `path: "/"`, and cookies are NOT scoped by port. Sessions live in each
server's own SQLite file. So logging into B **overwrites the cookie A was using**, and B's session id
does not exist in A's database — A will bounce you to the login screen, and logging back into A will
do the same to B.

**Therefore: open environment B in a separate browser profile, or a private/incognito window.** This
is an operational property of running two dev servers on one host. It is NOT a defect in
export/import — do not file it as a finding against this milestone.

Sanity check before continuing: `packages/server/data/env-b.db` now exists, environment B's dashboard
list is EMPTY, and its Datasets page lists no tables. If B shows your existing dashboards, both
servers are on the same file — stop and fix `DB_PATH`.

**Copy the entire report modal contents into your approval message.** Specifically: the created

### Step 5 — Second import, to exercise the metric-conflict path with real data

### Step 6 — Compare the imported dashboard AGAINST THE SOURCE, side by side

Put A (`:5173`) and B (`:5174`) side by side and open the same dashboard in both.

**A widget pointing at the wrong table renders perfectly well — it just shows wrong numbers.** So do

| # | Check | How |

| 3 | **Timeline / Numeric Line widget (REF-5)** | same series, same shape, spot-check one bucket's value in both |
