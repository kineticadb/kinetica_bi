<hazards>

## The store-hydration regression — the single most likely way to ship a bug here

`customMetricsStore` is populated ONLY by `loadConfig`, and today the only callers are config panels
(`ChartConfigPanel`, `TimelineConfigPanel`, `NumericLineConfigPanel`, `CalendarConfigPanel`),
`CustomMetricsEditorModal`, `ColumnFormatEditorModal`, and three renderers
(`TimelineRenderer`, `NumericLineRenderer`, `CalendarRenderer`) — plus `BarRenderer`
(`WidgetRenderer.tsx:903-907`), which is a CHILD of `AggregatedWidgetRenderer` and only mounts AFTER data
has arrived. So when a dashboard is opened and no config panel is involved, the store is **EMPTY** at the
moment `AggregatedWidgetRenderer` computes its SQL. A naive `resolveMetricExpr` call there returns `null`
and blanks the widget. Commit `4a8c117` is the same class of bug one layer up (the picker read
`selectedTable?.id` while the fetch was keyed on `draft.tableId`).

Three defences, all mandatory:
1. `AggregatedWidgetRenderer` gets its OWN `loadConfig` hydration effect.
2. That effect is gated on `isCustomSelection(metricId) && tableId !== undefined` — a non-custom widget
   must not issue an extra HTTP request per dashboard load. This gate is also why the change is inert for
   all 125 existing `WidgetRenderer.spec.tsx` tests (`grep -c metricId` on that spec → **0**).
3. Pre-hydration is a SUSPEND, not a fallback. `{kind:"pending"}` means no query fires at all. Falling back
   to the frozen SQL would make every dashboard load flash the wrong number and then correct itself —
   shipping the defect for 200ms on every page view is not a fix.

## The dep-array trap

`sql` is already dep #1 of Effect 2, so a resolved-SQL memo re-fires the fetch for free. But there is a
transition where the SQL does NOT change and a fetch is still required: `pending` → `ready` where the
resolution outcome is "orphan" or "parse failed", both of which return the stored SQL unchanged. If only
`sql` is in the deps, that widget suspends forever. **`metricsPending` MUST be added to Effect 2's dep
array**, and this is what mutation probe M4 checks.

## FROM-swap composition

`Effect 2` computes `const finalSql = fromSwap(sql, effectiveViewName)`, and `fromSwap` replaces the FIRST
`\bFROM\s+[\w.]+` match. The metric expression must therefore be substituted BEFORE `fromSwap` runs — which
it is, automatically, because the resolution happens in a `useMemo` that produces `sql`. Do not move it.
This is the same ordering lock recorded for `CalendarRenderer` in v1.13 ("resolve fromTarget before
building the SQL string — DATE_TRUNC SQL can contain FROM tokens that a first-FROM regex would clobber").

## dv-bound widgets

A dv-bound widget persists BOTH `dynamicViewId` and `tableId` (= `source_table_id`, the Phase 35 dual-write
lock at `ChartConfigPanel.tsx:1071-1074`). Custom metrics are per SOURCE table, so resolving against
`cfg.tableId` is correct for dv-bound widgets too, and `fromSwap` then redirects the FROM to the dv view.
No special case is needed — but a test pins it.

## INHERITED RISK: a failed hydration fetch suspends the widget forever

Raised by the plan checker, 2026-09-18. The hydration effect this plan adds ends in
`loadConfig(tableId).catch(() => {})`. If that request REJECTS (network error, 5xx, server restarted
mid-session), `setConfig` never fires, so `isMetricsHydrated(tableId)` stays false, so the widget
suspends in `Loading...` **indefinitely, with no error surfaced and no retry**.

This is NOT introduced here. It is a byte-for-byte copy of the established idiom at
`TimelineRenderer.tsx:156-163`, which this plan is explicitly told to mirror, and the same silent
swallow already ships for Timeline / NumericLine / Calendar widgets. Deviating from it unilaterally
inside a gap-closure plan would put an unreviewed error-handling design into seven more widget types.

**Decision: copy the idiom as-is, and record the risk rather than silently inheriting it.** The
executor MUST:
- leave the `.catch(() => {})` exactly as the existing renderers write it — do NOT invent a retry,
  an error banner, or a fallback-to-stored-sql on rejection inside this plan;
- state this limitation explicitly in 121-06-SUMMARY.md under Issues Encountered, naming
  `TimelineRenderer.tsx:156-163` as the precedent, so it is carried forward rather than lost.

It is a genuine defect in the store-hydration idiom, project-wide and pre-existing. It is out of
scope here for the same reason the frozen-`config.sql` root cause was out of scope for plan 121-04:
a checkpoint records what it finds, it does not improvise fixes in a neighbouring subsystem. File it
as a follow-up; do NOT fix it in this plan.

</hazards>
