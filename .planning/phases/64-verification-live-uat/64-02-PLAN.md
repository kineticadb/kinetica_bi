<the_bug_being_proven_fixed>
<!-- The ORIGINAL bug (root-caused this session). The walk must reproduce the scenario and prove the fix. -->
ORIGINAL BUG: drilling a dynamic-view-backed widget mis-applied the filter to the underlying SOURCE TABLE — `dispatchDrillDown` always keyed by `tableId`, so the filter landed in `filters[sourceTableId]`, and the dv-bound widget read the RAW dv view and never reflected the click. Net effect: clicking a dv chart did nothing visible on that chart (or silently filtered the wrong scope).
THE FIX (Phase 62 server + Phase 63 client): a dv drill now materializes `FROM <dv materialized-view> WHERE <clicked filter>` (extended `POST /api/filter/materialize`, no new route), writes to a dv-scoped filter slice (`dvFilters[dynamicViewId]`, un-collidable with `filters[tableId]`), and the dv widget FROM-swaps to the filtered-dv view (precedence filtered-dv -> dv). The operator must SEE the dv chart + same-dv widgets update LIVE, the source-table widget stay still, and the chip clear back to the unfiltered dv.
</the_bug_being_proven_fixed>

<locked_invariants>
<!-- v1.12 locked invariants (ROADMAP §v1.12 "Locked invariants" + REQUIREMENTS.md). The walk attests these HOLD. -->
- DV-ISOLATED SCOPE: a dv drill filters ONLY that dynamic view. Same-dv widgets update; SOURCE-TABLE widgets + OTHER-dv widgets are UNTOUCHED. (Cross-scope propagation is explicitly OUT — DVX-V2-02.)

- NO NEW SERVER ROUTE: the dv path lives inside the existing `POST /api/filter/materialize`.
</locked_invariants>
