<gap_fix_protocol>
When the operator reports a scenario FAIL:
  1. Reproduce it (identify the widget/config/table + observed vs expected).
  2. Write a FAILING regression test FIRST at the right layer (unit spec for a pure helper — e.g. customWhere/yAxisScale/barGroupedSeries/customMetricSql/calendarBin; component spec for a renderer/panel; server supertest for a custom_metrics/route issue).
  3. Fix the minimal code to turn it green. Honor CLAUDE.md UI conventions (reuse existing global.css classes, theme tokens only — no raw hex, no invented class names; run theme-guard).
  4. Re-run the affected gate(s): web tsc + the relevant vitest (+ server tsc/vitest if server-touched, set-based).
  5. Commit: `fix(103): <gap> — repro-test + fix` (end with the Co-Authored-By trailer). If on a non-default branch is required, follow repo policy; commit only when the fix is green.
  6. Re-present the scenario to the operator; only mark PASS on operator re-confirmation. Log it in 103-UAT.md's resolution log.
Do NOT batch-fix or mark PASS speculatively. Do NOT introduce deferred-backlog features (VIZSQL-V2-01 map WHERE, METRIC-V2-01/02, YAXIS-V2-01, live viewer calendar switcher) — those are out of this walk.
</gap_fix_protocol>
