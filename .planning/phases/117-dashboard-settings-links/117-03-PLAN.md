<the_correction_this_plan_makes_to_research>
`117-RESEARCH.md` §Q3 supplies a code sketch for these two timers whose guard is:

```typescript
if (readDashboardIdFromSearch(window.location.search) !== openedId) return;
clearDashboardUrl();
```

**That guard is INSUFFICIENT for dashboards, and shipping it verbatim would break the feature
Plan 02 just built.** Work it through:

1. The user is on the edit screen. The bar reads `?dashboard=12&mode=edit`.
2. They Save. Plan 02's transition #11 calls `setDashboardMode(12, "view")`; the bar becomes
   `?dashboard=12&mode=view`, and `DashboardsPage` re-renders into its `view` branch.
3. React unmounts `DashboardEdit` and mounts `DashboardDetail`. `DashboardEdit`'s cleanup runs and
   schedules the deferred clear, capturing `openedId = 12`.
4. One macrotask later the timer fires. Auth is fine. `readDashboardIdFromSearch` returns **12**,
   which **equals** `openedId` — so the guard passes and `clearDashboardUrl()` wipes the URL the
   Save wrote one tick earlier. The settings screen is on screen with a bare `/` in the bar.

The identical failure happens in the opposite direction for transition #9 (the in-app Edit button:
`DashboardDetail` unmounts while `DashboardEdit` mounts on the same id).

This is the exact hazard Phase 116 hit and solved DIFFERENTLY: `116-03-PLAN.md` put the table's
single timer on the PAGE component rather than on `TableDetail`/`TableEdit`, precisely because "the
edit->view Save unmounts TableEdit and mounts TableDetail, and a per-subcomponent timer would fire
and wrongly wipe the param that the Save just rewrote."

**Dashboards keep the per-component shape (two timers, per research's recommendation) and close the
hole by making the guard id-AND-MODE-scoped.** Each component captures BOTH the id and the mode it
was mounted for; the timer only clears when the bar still describes THAT screen:

- `DashboardEdit` captured `("edit")`; after a Save the bar reads `mode=view` -> guard returns, no clear. Correct.
- `DashboardDetail` captured `("view")`; after an in-app Edit the bar reads `mode=edit` -> guard returns, no clear. Correct.
- Either screen on a genuine leave (sidebar click, page unmount): the bar still reads the captured
  mode -> clear. Correct.
- Either screen after an in-app Back: `leaveDashboardUrl()` has already popped or cleared, so
  `readDashboardIdFromSearch` returns null -> guard returns. Correct, and harmless.

Task 2's behaviour bullets 5 and 6 and mutation probe B exist ONLY to hold this correction in place.
If the mode half of the guard is ever removed, probe B must redden the suite.
</the_correction_this_plan_makes_to_research>

```typescript
  // App.tsx renders DashboardsPage conditionally, so a sidebar click to Datasets/Settings fully
  // unmounts this component while the bar still says ?dashboard=<id>&mode=view — copying the link
  // at that moment shares a screen the user is no longer on.

  // NET-NEW: this screen had no such timer before Phase 117, because it was not linkable.
  // Deliberately its OWN small effect, NOT folded into DashboardOpen's existing unmount timer —
  // that one is entangled with a 13-Zustand-store reset and is keyed to a different component's
  // lifecycle.
  //
  // Deferred by one macrotask, mirroring DashboardOpen's timer, for two reasons:
  //  (a) StrictMode runs mount -> cleanup -> mount on the SAME hook state in dev (main.tsx), so the
  //      spurious cleanup fires right after a URL write; deferring lets the re-mount cancel it.
  //  (b) it lets the auth status settle, so a 401/logout teardown is reliably seen as unauthenticated.
  //
  // ⚠️ THE GUARD IS ON id AND MODE, NOT id ALONE. The in-app Edit button (transition #9) unmounts
  // THIS component while the SAME dashboard id stays in the bar under a different qualifier. An
  // id-only guard — which is all DashboardOpen ever needed, because `open` has no in-place sibling
  // transition — would pass and wipe the ?mode=edit that the click just wrote. Mode-scoping is what
  // makes a per-component timer safe here at all; DatasetsPage solved the same hazard by putting a
  // single timer on the PAGE instead.
  const detailClearUrlTimer = useRef<number | null>(null);
  useEffect(() => {
    if (detailClearUrlTimer.current !== null) {
      clearTimeout(detailClearUrlTimer.current);   // StrictMode re-mount: cancel the spurious clear
      detailClearUrlTimer.current = null;
    }
    const openedId = dashboard.id;
    return () => {
      detailClearUrlTimer.current = window.setTimeout(() => {
        if (useAuthStore.getState().status !== "authenticated") return;              // 401/logout: leave it for the re-auth journey
        if (readDashboardIdFromSearch(window.location.search) !== openedId) return;  // not OUR param (already clean, or another dashboard's)
        if (readDashboardModeFromSearch(window.location.search) !== "view") return;  // we moved to edit in place — that URL is current, not stale
        clearDashboardUrl();
      }, 0);
    };
    // eslint-disable-next-line react-hooks/exhaustive-deps -- mount/unmount-lifetime effect; dashboard.id is fixed for this instance
  }, []);
```
