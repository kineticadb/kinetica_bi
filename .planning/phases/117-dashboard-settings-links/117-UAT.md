# Phase 117 — Dashboard Settings Links — Operator Walkthrough

**What was built:** Dashboard settings and edit screens are now reachable by URL, exactly as a
table's are, while the bare running-dashboard link is unchanged:
- `?dashboard=<id>` — the RUNNING dashboard (unchanged; this is the link people already have)
- `?dashboard=<id>&mode=view` — the settings/detail screen
- `?dashboard=<id>&mode=edit` — the edit screen

jsdom proves the state machine end to end: the right URL is written, the right screen mounts,
the marker is preserved across in-place mode changes, and the bar is cleared on every genuine
leave (220 tests across the seven dashboard-family spec files, mutation-probe verified — see
`117-05-SUMMARY.md`). It structurally **cannot** prove three things, which is what this
walkthrough is for: whether the in-place Edit transition FLASHES in a real browser, whether the
failure banner READS correctly in both themes, and whether an arrival can eject the user out of
the application.

Each check below has an unambiguous PASS condition and a stated failure shape, per
`CLAUDE.md`'s "Writing verifiable acceptance criteria" rule — state plainly what PASS looks
like and what FAIL looks like, never bury the real expectation in a parenthetical.

**Report per check:** the check ID, PASS or FAIL, and for any FAIL, what you saw instead. A FAIL
is a bug in Plans 01-05's code, not a reason to amend these steps.

## KNOWN NOT COVERED

State this explicitly so the operator does not test for it and report a false defect:

- **Unsaved changes in the dashboard edit form are discarded silently** on Cancel, on sidebar
  navigation away, and on browser Back. This is DELIBERATE and matches the Phase 116 operator
  decision for tables (`TLINK-F1` in `.planning/REQUIREMENTS.md` — "both or neither"; Phase 117
  built neither). It is NOT a regression: before this phase, browser Back from a dashboard edit
  left the application entirely; after this phase it lands on the dashboard list, which is
  strictly better even without a dirty-state guard.
- `create` screens are not linkable, by design (`DSET-F1` — nothing to identify a not-yet-saved
  dashboard by).
- Roles and Settings pages are still not linkable (`DLINK-F4`, unchanged by this phase).
- Sidebar "Dashboards" is a no-op while a dashboard is already open (`TLINK-F3`, pre-existing,
  affects both Datasets and Dashboards). Confirmed present, deliberately not fixed here.
- A hand-crafted `?dashboard=5&table=12&mode=edit` URL loses the table's `mode` qualifier if the
  dashboard leaves (`DSET-F2`). No UI path produces this URL; it is reachable only by manually
  editing the address bar.
