<objective>
Surface the "Custom filter (SQL)" field on the three CustomConfigPanel widgets (timeline, numeric-line, calendar) — whose registry `fields: []` is empty, so the field must be added inside each panel, not via the registry loop — and thread `cfg.customWhere` from each renderer into its `buildXSql` call(s). The builders already accept `customWhere?` (plan 98-01). Empty/absent → byte-identical (VIZSQL-V119-03). Invalid → existing per-widget error state (VIZSQL-V119-04).

CRITICAL: the three config types are CLOSED (no index signature). `TimelineConfig` (TimelineConfigPanel.tsx:33), `NumericLineConfig` (NumericLineConfigPanel.tsx:29), and `CalendarConfig` (CalendarConfigPanel.tsx:45) do NOT currently declare `customWhere`. Both the panels (`config as Partial<XConfig>`) and the renderers (`widget.config as Partial<XConfig>`) read through these typed objects, so every `cfg.customWhere` access is `TS2339` until each type declares an OPTIONAL `customWhere?: string;` member. The FIRST step of each task is to add that member.

CRITICAL invariant (CalendarRenderer): thread customWhere as a BUILDER ARG only — never post-process the SQL string. CalendarRenderer pre-resolves `fromTarget` before building SQL (the no-fromSwap-in-renderer rule; DATE_TRUNC SQL contains FROM tokens a regex would clobber). Introduce NO new fromSwap anywhere in this plan.

Purpose: Completes the own-SQL widget set (timeline/numeric-line/calendar). These are a distinct mechanism from the aggregated/records path (98-02) — they inject at build time via pure builders, not at config-save. Depends on 98-01 (builder signatures). No file overlap with 98-02 → runs in parallel within wave 2.
Output: 3 config types gain an optional `customWhere`; 3 config panels gain the field; 3 renderers thread customWhere into their builder calls; tests lock injection + byte-identical-when-empty per renderer.
</objective>
