<objective>
Close the loop: consume the restored id after the OIDC round trip, put the dashboard back in the
address bar, and enforce the locked conflict rule at the restore boundary.

Purpose: Plan 02 made the id survive the IdP redirect. This plan makes it LAND — and makes it not
land when the more recent intent was an expiry captured somewhere else. Two things happen here
that nothing before this plan does: `restoreDashboardUrl` gets called (the bar is bare after
OIDC, which would silently break Back, copy-link and refresh for OIDC users only — DLINK-V121-07),
and a stale deep link gets SUPPRESSED rather than merely DELAYED.

⚠️ **THIS PLAN AMENDS ONE PASSING PHASE 114 TEST.** `App.deeplink.spec.tsx:183-191`
("DEEPLINK-114: a pasted link beats the Phase 7 ReturnTo page restore") sets up
`kbi_returnTo = { page: "roles" }` + URL `?dashboard=7` and asserts the dashboard wins. Under
115-CONTEXT.md's locked conflict rule that EXACT state is the expiry-while-elsewhere case, where
Roles must win. The two phases disagree about one identical state; Phase 115's rule is the newer,
explicitly-locked one, and 115-CONTEXT.md describes it as "the mirror image of Phase 114's rule".
Phase 114's *intent* is preserved — a fresh paste still beats a leftover ReturnTo — because Plan
02's commit write always pairs the id with `page: "dashboards"`, which is the shape a real fresh
paste now produces. Only the test's hand-written setup, which the app never actually produces for
a paste, is reclassified. Task 2 replaces that one test with TWO tests and a comment recording
this amendment. Do NOT silently delete it and do NOT weaken the replacement.

Output: two edits in `App.tsx`, and `App.deeplink.spec.tsx` extended + amended.
</objective>
