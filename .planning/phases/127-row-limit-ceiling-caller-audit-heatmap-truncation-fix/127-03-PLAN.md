Background for the design (planner analysis, verified against code):
- Every widget query carries its OWN SQL `LIMIT n`. Kinetica's `has_more_records` refers to the SQL-bounded result, so it is true ONLY when the app's envelope (the deployment per-query max, plan 127-01) cut that result short. It can never say "more rows than the widget's own LIMIT exist".
- So "more rows than my own limit exist" needs the fetch-limit+1 pattern (explicitly allowed by D-14): ask `LIMIT n+1`, render at most n, and if n+1 came back the own limit was hit.
- The heatmap SQL is persisted in `widget.config.sql` ending `... ORDER BY value DESC|ASC LIMIT <n>` (ChartConfigPanel.tsx:466); `bumpTrailingLimit` rewrites that trailing clause at fetch time.

<interfaces>
Contract this plan CREATES (plans 04/05/06 code against it verbatim):
```ts
export type TruncationReason = "result-limit" | "deployment-max";
export interface TruncationInfo { shown: number; reason: TruncationReason }

/** has_more_records from a /api/sql response; undefined unless it is a real boolean. */
export function readHasMore(res: unknown): boolean | undefined;

/**
 * fetched = rows the query returned (BEFORE slicing to ownLimit);
 * ownLimit = the widget's own row limit n (the query asked for n+1), or null if the widget has none / it could not be bumped;
 * serverHasMore = readHasMore(res).
 */
export function detectTruncation(args: { fetched: number; ownLimit: number | null; serverHasMore: boolean | undefined }): TruncationInfo | null;

/** Rewrites a trailing `LIMIT <n>` (optional trailing `;`/whitespace, case-insensitive) to `LIMIT <n+1>`. null if the SQL does not END in a plain `LIMIT <int>` (e.g. `LIMIT 10 OFFSET 5`, no LIMIT, LIMIT only inside a subquery). */
export function bumpTrailingLimit(sql: string): { sql: string; limit: number } | null;

/** Shared tooltip guidance for the deployment-max case (D-15). */
export const DEPLOYMENT_MAX_HINT = "Ask an admin to raise KINETICA_MAX_ROWS_PER_QUERY.";
```
