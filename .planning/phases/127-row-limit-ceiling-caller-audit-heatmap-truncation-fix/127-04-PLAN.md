<objective>
Fix the headline bug (EXPRT-V126-01): the in-browser CSV download pages on the server's authoritative more-rows signal (D-10) and reaches its cap (D-06), the cap is clamped by the admin ceiling (D-07), the cap message says how much was left out (D-08), the button shows progress (D-09), and a records page silently cut by the deploy max gets a notice (D-12).

Purpose: "a CSV download of a large table came back with exactly 1,000 rows and no indication anything was missing" — every change here is measured against that.
Output: RecordsTableRenderer changes + CSV/records specs.

Design note (planner analysis, verified against code): the CSV page SQL carries its own `LIMIT ${limit} OFFSET ${offset}`, so Kinetica's has_more_records for that page is true ONLY when the server's envelope cut the page short. The correct exhaustion rule is therefore: `done = readHasMore(res) !== true && rows.length < limit`. A short page WITH has_more_records=true (the exact old 1,000-row failure, or an admin-lowered max below PAGE=5000) keeps paging from `offset + rows.length`. A missing field (older server / mocked response) falls back to today's short-page rule, so existing tests keep their meaning.
</objective>
