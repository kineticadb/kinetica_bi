<objective>
Correct a Phase 58 foundation defect so the widget-action engine can actually patch a map layer's render mode — the headline use case for v1.11.

Phase 58 shipped an engine that silently CANNOT switch a layer's render mode:
1. The allow-list keys `render_mode` (snake_case) but the real field is `config.renderMode` (camelCase, NESTED in the layer's `config` blob — proven by `wmsUrlBuilder.ts` reading `config.renderMode`).
2. The allow-list treats `render_mode`/`visible`/`opacity` as if they were TOP-LEVEL `DashboardLayerDto` fields, but only `track_config`/`cb_config` are top-level — `renderMode`/`visible`/`opacity` are NESTED in `layer.config` (proven by `wmsUrlBuilder.ts` + `layerVisibility.ts` + MapChartRenderer comments reading `config.visible`/`config.renderMode`).
3. The `effectiveLayers` merge in `MapChartRenderer.tsx` is a FLAT top-level spread `{ ...l, ...override }` that reaches top-level fields but can NEVER reach `config.renderMode`.
4. The Phase 58 canary only exercised top-level `track_config`/`cb_config`, so it passed without ever proving render-mode routing.

This is the `[[track-config-toplevel-field]]` class of bug recurring (some fields are top-level, some are nested — the engine conflated them). Discovered during Phase 59 planning.

Purpose: re-verify the nested-config routing ENGINE-V111-03 claimed but never actually exercised, so Phases 59-61 can build the radio widget on a foundation that works.

Output: corrected allow-list with per-field location metadata, a deep-merge layer overlay, location-aware patch routing, and a render-mode canary that fails pre-fix and passes post-fix — all Phase 58 specs updated to the new (correct) contract and still green.

SCOPE: FRONTEND-ONLY (`packages/web`). ZERO server changes.
</objective>
