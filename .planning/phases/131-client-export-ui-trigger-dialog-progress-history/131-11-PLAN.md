<design_decisions>
Read this before Task 1. These decisions were made during planning, and the evidence was gathered on this machine on 2026-10-08.

**DD-1: Write our own zip writer with `node:zlib` (`createDeflateRaw` + `zlib.crc32`), not yazl.** Reasons:
- `zlib.crc32` exists in every runtime we ship. Dev is Node v24.14.1. Docker `node:20-alpine` (the Dockerfile `build`, `proddeps` and `server` stages) resolves to v20.20.2: `docker run --rm node:20-alpine node -e "console.log(process.version, typeof require('zlib').crc32)"` printed `v20.20.2 function`. `zlib.crc32` needs ≥ 20.15 / ≥ 22.2, and the floating `node:20-alpine` tag can only move forward within 20.x.
- `@types/node` 25.9.1 declares `crc32(data, value?)`, so tsc is fine.
- Our one-entry case needs about 150 lines, with no new dependency and no operator dependency checkpoint.
- yazl would add a dependency and lockfile churn for something node:zlib already does.

`createZipEntryStages` still throws a clear error if `zlib.crc32` is missing, so an old runtime fails loudly as an internal_error instead of writing a corrupt file.

**DD-2: The local header ALWAYS carries a ZIP64 extra field (sizes 0), and the data descriptor is ALWAYS the 24-byte ZIP64 form.** The central directory and the ZIP64 end records are written only when needed (or when forced in tests). Evidence: six layout variants of the same 1 MB CSV, extracted with `ditto -x -k` (the Archive Utility engine), `unzip -t`, Python `zipfile` and `bsdtar`:
- Plain (no ZIP64 anywhere): all four OK.
- Go/Java style (local header WITHOUT the ZIP64 extra but a 24-byte ZIP64 descriptor and a ZIP64 central directory, which is how most streaming writers do >4 GiB): **ditto FAILS** with "Couldn't read pkzip signature". unzip, python and bsdtar are OK.
- Local ZIP64 extra + 24-byte descriptor, with either a plain or a ZIP64 central directory: all four OK, including the forced-ZIP64 layout and an empty entry.

A streaming writer can't know at the local header whether the entry will pass 4 GiB. So the only layout that works in Archive Utility at every size is "local header always announces ZIP64". (Info-ZIP `zip` does the same when it streams.)

**DD-3: Data descriptor (general-purpose bit 3) and UTF-8 names (bit 11).** The flags are `0x0808` in both the local and the central header. The sizes and CRC are unknown until the end, and the file is written through a stream (byteCap → `.part`). The entry name is UTF-8 because display names can be non-ASCII (e.g. "Résumé – 数据 - Q1.csv"). ditto, unzip and python all extracted that exact name correctly in the prototype.

**DD-4: Serve AND clean up legacy `.csv.gz`, don't just clean up.** A job completed before the deploy has a `.csv.gz` on disk and stays listed as "complete" with a Download button for up to 24 h. Cleanup-only would turn that button into a 410 for a file that still exists. Serving costs one more allowed suffix (send's mime gives `application/gzip`). The existing `EXPRT129-dl-gzip` test stays as the legacy-serving proof. No new job can produce `.csv.gz`.

**DD-5: Rename the option and DTO field `gzip` → `compress`. POST still accepts `options.gzip` as a deprecated alias.** "gzip" would be a false name for a zip. The web client is the only consumer of the DTO and no UI reads the DTO flag, so the DTO field is renamed outright. For legacy rows, the DTO reads `compress` as `options_json.compress === true || options_json.gzip === true`. The alias exists only for a tab that loaded before the deploy. Every remaining server `gzip` token must sit on a line that contains the word `legacy` or `alias`, so new code doesn't spread the old name.

**DD-6: The entry name inside the zip = the outer download base + `.csv`.** A new pure helper `exportDownloadBase(name, id, createdAt)` in `exportName.ts` returns `exportFileBase(name) ?? \`export-${createdAt.slice(0, 10)}-${id.slice(0, 8)}\``. `exportDownloadName` (outer name) and the runner (entry name) both use it, so `Q1.zip` always contains `Q1.csv`. It lives in `exportName.ts` because `exportJobAccess.ts` imports `exportRunner.ts`, so putting it in `exportJobAccess` would create an import cycle.
</design_decisions>

<zip_byte_layout>
All integers are little-endian. `n` is the UTF-8 byte length of the entry name. `U32 = 0xFFFFFFFF`. 64-bit fields use `buf.writeBigUInt64LE(BigInt(x))`. Sizes are JS numbers (exact up to 2^53). The prototype of this exact layout passed ditto, unzip -t, python zipfile and bsdtar.

**Local file header** — `localFileHeader(name: Buffer, dt: DosDateTime): Buffer`, length `30 + n + 20`:
| off | type | value |
|---|---|---|
| 0 | u32 | 0x04034b50 |
| 4 | u16 | 45 (version needed: ZIP64) |
| 6 | u16 | 0x0808 (bit 3 data descriptor, bit 11 UTF-8) |
| 8 | u16 | 8 (deflate) |
| 10 | u16 | dt.time |
| 12 | u16 | dt.date |
| 14 | u32 | 0 (CRC, in descriptor) |
| 18 | u32 | U32 (compressed size → ZIP64) |
| 22 | u32 | U32 (uncompressed size → ZIP64) |
| 26 | u16 | n |
| 28 | u16 | 20 (extra length) |
| 30 | bytes | name |
| 30+n | u16 | 0x0001 (ZIP64 extra id) |
| 32+n | u16 | 16 |
| 34+n | u64 | 0 (uncompressed, unknown) |
| 42+n | u64 | 0 (compressed, unknown) |

**Data descriptor** — `dataDescriptor(crc: number, compressedSize: number, uncompressedSize: number): Buffer`, ALWAYS 24 bytes: `0 u32 0x08074b50 · 4 u32 crc · 8 u64 compressedSize · 16 u64 uncompressedSize`.

**Central directory header** — `centralDirectoryHeader(a: { name: Buffer; dt: DosDateTime; crc: number; compressedSize: number; uncompressedSize: number; zip64: boolean }): Buffer`, length `46 + n + (zip64 ? 20 : 0)`:
| off | type | value |
|---|---|---|
| 0 | u32 | 0x02014b50 |
| 4 | u16 | 0x032D (made by: Unix (3) << 8 | 45) |
| 6 | u16 | 45 |
| 8 | u16 | 0x0808 |
| 10 | u16 | 8 |
| 12 | u16 | dt.time |
| 14 | u16 | dt.date |
| 16 | u32 | crc |
| 20 | u32 | zip64 ? U32 : compressedSize |
| 24 | u32 | zip64 ? U32 : uncompressedSize |
| 28 | u16 | n |
| 30 | u16 | zip64 ? 20 : 0 |
| 32 | u16 | 0 (comment) |
| 34 | u16 | 0 (disk start) |
| 36 | u16 | 0 (internal attrs) |
| 38 | u32 | 0x81A40000 (external attrs: Unix 0100644 << 16) |
| 42 | u32 | 0 (local header offset: the single entry is at 0) |
| 46 | bytes | name |
| 46+n (zip64 only) | u16,u16,u64,u64 | 0x0001, 16, **uncompressedSize, then compressedSize** (APPNOTE 4.5.3 order) |

**End records** — `endOfCentralDirectory(a: { cdOffset: number; cdSize: number; zip64: boolean }): Buffer`. Length is 22, or 56 + 20 + 22 = 98 when zip64.
- When zip64, first the **ZIP64 EOCD record** (56): `0 u32 0x06064b50 · 4 u64 44 · 12 u16 0x032D · 14 u16 45 · 16 u32 0 · 20 u32 0 · 24 u64 1 · 32 u64 1 · 40 u64 cdSize · 48 u64 cdOffset`.
- Then the **ZIP64 EOCD locator** (20): `0 u32 0x07064b50 · 4 u32 0 · 8 u64 (cdOffset + cdSize) · 16 u32 1`.
- Always last, the **EOCD** (22): `0 u32 0x06054b50 · 4 u16 0 · 6 u16 0 · 8 u16 zip64 ? 0xFFFF : 1 · 10 u16 zip64 ? 0xFFFF : 1 · 12 u32 zip64 ? U32 : cdSize · 16 u32 zip64 ? U32 : cdOffset · 20 u16 0`.

**`needsZip64(a: { compressedSize: number; uncompressedSize: number; cdOffset: number }): boolean`** = any of the three `>= 0xFFFFFFFF`.

**`dosDateTime(d: Date): { time: number; date: number }`** in local time: `time = (h << 11) | (min << 5) | (sec >> 1)`, `date = ((year - 1980) << 9) | (month1to12 << 5) | day`. A year before 1980 clamps to `{ time: 0, date: 33 }` (1980-01-01). Example: `new Date(2026, 9, 8, 14, 30, 59)` → `{ time: 29661, date: 23880 }`.
</zip_byte_layout>
