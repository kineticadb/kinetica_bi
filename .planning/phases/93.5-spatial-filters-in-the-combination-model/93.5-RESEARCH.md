## Summary

Phases 88-93 shipped the combination model for COLUMN filters. The orchestrator (`useCombinationOrchestrator`) fires on `filterVersion`, resolves per-viz filter sets, hashes them, and fires exactly one POST per new unique combo. Phase 93 added `SPATIAL_DRAWS_SENTINEL = "__spatial_draws__"` to `allowedSourceWidgetIds` as a stored-but-not-yet-resolved marker. Phase 93.5 closes the loop: spatial shapes fold into the combo hash, the orchestrator owns spatial materialization, and the legacy per-table trigger paths (`useMapOnlySpatialMaterialize`, RecordsTableRenderer spatial Effect 1) are reconciled.

The server side is already complete and requires zero changes: `composeWhereClause` composes `(spatial OR-chain) AND (column chain)`; `buildFilterViewName` appends `_c<hash8>` when `combinationKey` present; `materializeFilter` sends `spatialFilters` + `spatialTarget` + `combinationKey` in the POST body. The client-side inFlight dedup cache already keys on `combinationKey` when present. The DV path explicitly rejects spatial with HTTP 400. WKB targets are rejected with HTTP 501.

The six open questions from the brief are all answered below with HIGH confidence from code.

**Primary recommendation:** Extend `stableComboHash` with an optional fourth `shapes?` param; add `resolveSpatialShapes` pure function; add `spatialFilterVersion` to the orchestrator dep array; fold spatial into the orchestrator's STEP A hash; remove `useMapOnlySpatialMaterialize`; neutralize the RecordsTableRenderer table-path spatial trigger; confirm server needs no edit.

## Q1: stableComboHash Spatial Extension

### Algorithm (locked)

`stableComboHash` currently takes `(sourceType, sourceId, filters)`. The spatial extension adds an optional fourth param:

```typescript
export function stableComboHash(
  sourceType: "table" | "dv",
  sourceId: number,
  filters: ActiveFilter[],
  shapes?: Pick<Shape, "wkt">[],   // NEW — optional; defaults to no shapes
): string
```

**Order-independent, deterministic shape hashing:**

1. Sort accepted shapes by `wkt` ascending (lexicographic — pure strings, always stable).
2. Each shape contributes a single segment: the raw `wkt` string.
3. Append the spatial segment list after the column filter segments, separated by a distinct delimiter — `";s:"` — so spatial segments cannot collide with column segments (column segments contain `|`, spatial segments are raw WKT polygons that do not contain `|`).

Concretely:

```typescript
// Column segments (existing)
const colSegments = sorted.map(f => `${f.column}|${f.operator ?? "eq"}|${JSON.stringify(f.value)}`);

// Spatial segments (NEW)
const spatialSegments = shapes && shapes.length > 0
  ? shapes.slice().sort((a, b) => a.wkt.localeCompare(b.wkt)).map(s => s.wkt)
  : [];

// Combined
if (colSegments.length === 0 && spatialSegments.length === 0) {
  return `${sourceType}:${sourceId}:${NOFILTER_SENTINEL}`;
}
const allSegments = colSegments.length > 0
  ? colSegments.join(";") + (spatialSegments.length > 0 ? ";s:" + spatialSegments.join(";s:") : "")
  : "s:" + spatialSegments.join(";s:");
return `${sourceType}:${sourceId}:${allSegments}`;
```

**Why WKT only, not id/label/addedAt:**
- `id` is `crypto.randomUUID()` — session-random per shape, identical shapes drawn twice get different ids.
- `label` is `"Bbox 1"` etc. — session-counter, not geometry-identity.
- `addedAt` is `Date.now()` — same reason `addedAt` was already excluded from column segments in Phase 88.
- WKT is the geometry itself: two shapes with the same WKT drawn in different orders are semantically identical spatial filters — they MUST produce the same hash.
- `measurement` is a display string, not a SQL predicate input.

**No-break guarantee on existing callers:** Fourth param is optional with default `undefined`. All existing `stableComboHash("table", id, filters)` calls produce byte-identical output because `spatialSegments` is empty.

**No-break guarantee on Phase-88 unit tests:** Tests pass `stableComboHash("table", 1, [filter])` — unchanged call-site, same output.

**comboShortHash/djb2 is unchanged:** It operates on the full string, so spatial content is naturally incorporated via the extended string. No djb2 change needed.

**Confidence:** HIGH.

## Q2: resolveSpatialShapes

### Contract

New pure function, co-located in `packages/web/src/lib/resolveFilterSet.ts` or its own `resolveSpatialShapes.ts`:

```typescript
import type { Shape } from "../store/spatialFilterStore";
import type { FilterSelectionConfig } from "../types/filterSelection";
import { SPATIAL_DRAWS_SENTINEL } from "../components/charts/filterSourceTypes";

/**
 * Returns the spatial shapes accepted by this visualization given its filter-scope config.
 *
 * Accept-all (cfg === undefined OR sourceMode === "all") → all shapes (same as v1.5/v1.17).
 * Allowlist mode + SPATIAL_DRAWS_SENTINEL ∈ allowedSourceWidgetIds → all shapes accepted.
 * Allowlist mode + SPATIAL_DRAWS_SENTINEL NOT in allowedSourceWidgetIds → no shapes (empty []).
 *
 * Spatial is all-or-nothing per visualization: there is no per-shape selection,
 * only a per-viz "accepts spatial draws" toggle (the SPATIAL_DRAWS_SENTINEL).
 *
 * Never mutates inputs. Returns a slice() for accept-all (stable ref, mirrors resolveFilterSet).
 */
export function resolveSpatialShapes(
  cfg: FilterSelectionConfig | undefined,
  allShapes: Shape[],
): Shape[] {
  if (cfg === undefined || cfg.sourceMode === "all") return allShapes.slice();
  // allowlist mode: accept spatial only when the sentinel is in the list
  const accepts = cfg.allowedSourceWidgetIds.includes(SPATIAL_DRAWS_SENTINEL);
  return accepts ? allShapes.slice() : [];
}
```

**Why all-or-nothing:** There is no per-shape sourceWidgetId (shapes come from the map draw tool, not from individual widgets). The sentinel is a single toggle. Partial shape acceptance would require per-shape metadata not present in the store.

**Unit test cases (required):**
1. `resolveSpatialShapes(undefined, shapes)` → all shapes
2. `resolveSpatialShapes({ sourceMode: "all", ... }, shapes)` → all shapes
3. `resolveSpatialShapes({ sourceMode: "allowlist", allowedSourceWidgetIds: [SPATIAL_DRAWS_SENTINEL] }, shapes)` → all shapes
4. `resolveSpatialShapes({ sourceMode: "allowlist", allowedSourceWidgetIds: [42] }, shapes)` → `[]`
5. `resolveSpatialShapes({ sourceMode: "allowlist", allowedSourceWidgetIds: [] }, shapes)` → `[]`
6. `resolveSpatialShapes(cfg, [])` → `[]` (empty shapes passthrough — no mutation, no crash)

**Confidence:** HIGH.

## Q3: Orchestrator Wiring

### Where to read shapes

Read shapes **imperatively** inside the setTimeout callback: `const shapes = useSpatialFilterStore.getState().shapes;`. Same pattern as `useMapOnlySpatialMaterialize` line 114. Do NOT subscribe to `s.shapes` (array reference — re-render storm), do NOT capture in the outer hook scope (stale closure).

### spatialFilterVersion in dep array: no-loop proof

The orchestrator's Effect dep array is currently:
```
[filterVersion, dashboardId, widgetsKey, layersKey, ceiling]
```

Add `spatialFilterVersion`:
```
[filterVersion, spatialFilterVersion, dashboardId, widgetsKey, layersKey, ceiling]
```

**No-loop risk:** `spatialFilterVersion` is a primitive integer from `useSpatialFilterStore`. The no-loop invariant bans `combinationVersion` because `setEntry` bumps it — making it a dep would re-fire the orchestrator after every successful materialize. `spatialFilterVersion` bumps only when the user draws/removes/clears shapes. `setEntry` does NOT bump `spatialFilterVersion`. Therefore adding `spatialFilterVersion` to the dep array does NOT cause a loop.

**How to subscribe (S-02 compliant):**
```typescript
const spatialFilterVersion = useSpatialFilterStore((s) => s.spatialFilterVersion);
```
This is a primitive integer selector — identical pattern to `filterVersion`. Safe in the dep array.

### STEP A changes (per-viz spatial resolution)

Inside the orchestrator's STEP A loop, after computing `resolved` and `hash`, also compute accepted shapes:

```typescript
// Read shapes once (outside the loop, at top of setTimeout callback)
const shapes = useSpatialFilterStore.getState().shapes;
```

For each widget in the widget loop:
```typescript
const cfg = w.config.filterSelection as FilterSelectionConfig | undefined;
const allFilters = (filterState.filters[tableId] ?? []);
const resolved = resolveFilterSet(cfg, allFilters);
const acceptedShapes = resolveSpatialShapes(cfg, shapes);
const spatialTarget = targetsByTable.get(tableId); // eligible targets only
// Only fold spatial into hash when there's an eligible target AND accepted shapes
const shapesForHash = (spatialTarget && acceptedShapes.length > 0) ? acceptedShapes : [];
const hash = stableComboHash("table", tableId, resolved, shapesForHash);
```

For the layer loop (STEP A Phase 92 extension), same pattern:
```typescript
const cfg = layer.filter_scope ?? undefined;
const allFilters = (filterState.filters[tableId] ?? []);
const resolved = resolveFilterSet(cfg, allFilters);
const acceptedShapes = resolveSpatialShapes(cfg, shapes);
const spatialTarget = targetsByTable.get(tableId);
const shapesForHash = (spatialTarget && acceptedShapes.length > 0) ? acceptedShapes : [];
const hash = stableComboHash("table", tableId, resolved, shapesForHash);
```

### targetsByTable computation

`aggregateSpatialTargetsByTable(widgets)` already produces a `Map<tableId, SpatialTarget>` inside `useMapOnlySpatialMaterialize`. The orchestrator must compute this too:

```typescript
// At the top of the main Effect, inside setTimeout (imperative read)
const targetsByTable = aggregateSpatialTargetsByTable(widgets);
```

`aggregateSpatialTargetsByTable` iterates `widgets` synchronously; it can be called inside the async callback. It is pure (no side effects, no randomness).

**No widgetsKey dep change needed:** `widgetsKey` already encodes trigger-type widget ids + tableIds. Spatial target eligibility changes only when a map widget's `spatialTargets` config changes, which is a widget mutation → `widgetsKey` changes → dep fires. This covers the "operator adds/removes spatial column config" case.

### materializeFilter args with spatial

In STEP D, when firing `materializeFilter`, include `spatialFilters` + `spatialTarget` when the accepted shapes are non-empty AND an eligible target exists:

```typescript
// Retrieve the accepted shapes for this hash from the desired entry
// (need to store them — extend DesiredEntry to carry acceptedShapes + spatialTarget)
type DesiredEntry = {
  tableId: number;
  resolved: ReturnType<typeof resolveFilterSet>;
  acceptedShapes: Shape[];         // NEW
  spatialTarget?: SpatialTarget;   // NEW
};

// In materializeFilter call:
const spatialArgs = desiredEntry.acceptedShapes.length > 0 && desiredEntry.spatialTarget
  ? {
      spatialFilters: desiredEntry.acceptedShapes.map(s => ({ id: s.id, wkt: s.wkt })),
      spatialTarget: desiredEntry.spatialTarget,
    }
  : {};

materializeFilter(
  { dashboardId, tableId, filters: resolved, combinationKey: hash, ...spatialArgs },
  ctrl.signal,
)
```

**Critical: the hash already encodes the accepted shapes, so the view name is unique per spatial-combo. No separate combinationKey derivation is needed — the `hash` already serves as the combinationKey.**

## Q6: Accept-All Correctness Gate

**Correctness gate:** With default accept-all config (`filterSelection === undefined` on all vizs) and one active spatial draw on a table that has an eligible spatial target, the orchestrator produces ONE combination hash that incorporates BOTH the column filters and the spatial shapes. All vizs on that table share this one hash → one POST → one Kinetica view → both the chart and the map read it.

**This is "spatial correctly applied under accept-all / one shared view"** — it is NOT byte-identical to the buggy post-Phase-91 state (which dropped spatial entirely). It IS byte-identical to v1.5/v1.17 behavior: one view per table, spatial included.

**Concrete correctness check:**
- Pre-93.5: orchestrator fires on `filterVersion` tick only; `spatialFilterVersion` not in deps → drawing a shape does NOT trigger the orchestrator → the combo view does NOT include spatial predicate → both chart and map show unfiltered/column-filtered data without the spatial constraint. This is the gap.
- Post-93.5: orchestrator fires on `spatialFilterVersion` tick too → re-hashes with shapes → new hash (spatial-extended) → fires new POST with `spatialFilters + spatialTarget` → new view with spatial WHERE → both chart (via combo store) and map (via combo store comboViewsKey) read the spatial-filtered view.

**Accept-all with NO shapes:** `resolveSpatialShapes(undefined, [])` → `[]`. `shapesForHash = []`. Hash is column-only (same as today). No change in behavior. Byte-identical to v1.17 (zero shapes = no spatial extension to the hash).

**Accept-all with zero active column filters AND shapes:** `resolved = []`, `acceptedShapes = shapes`. `stableComboHash("table", id, [], shapes)` → NOT NOFILTER (shapes are non-empty, so the hash includes the spatial segment). The orchestrator fires the POST with `{ spatialFilters: shapes, spatialTarget: target, filters: [] }`. The server accepts spatial-only combos (validation step 2 passes because `hasSpatial = true`). The Kinetica view contains only the spatial WHERE clause. This is correct behavior: a table filtered only by spatial draw, no column filter active.

**Confidence:** HIGH.

## Common Pitfalls

### Pitfall 1: Folding shapes into hash when no eligible spatial target exists

If `targetsByTable.get(tableId)` is `undefined` (table has no map widget or no configured spatial columns), the hash must NOT include spatial segments even if shapes are drawn. Otherwise two vizs on a non-spatial table would get different hashes (one with spatial-extended hash, one without) depending on whether they called `resolveSpatialShapes` — producing a dedup failure.

**Guard:** `const shapesForHash = (spatialTarget && acceptedShapes.length > 0) ? acceptedShapes : [];`

### Pitfall 2: Shape id/label in hash (S-02 analog)

Using `shape.id` (UUID, session-random) or `shape.label` ("Bbox 1", session counter) in the hash produces a different hash every time the same geometry is drawn. Two vizs drawn at different times with identical geometry would NOT share a combo view. Only `shape.wkt` is the geometry fingerprint.

### Pitfall 3: Adding spatialFilterVersion to dep array causes loop?

NO LOOP: `spatialFilterVersion` only bumps on user draw events (addShape, removeShape, clearAll). `setEntry` in filterCombinationStore bumps `combinationVersion`, NOT `spatialFilterVersion`. No feedback loop exists. Verified by reading `spatialFilterStore.ts` (the `set` calls in `addShape/removeShape/clearAll` do not touch `combinationVersion`).

### Pitfall 4: Sending spatial args on the dv path

The server rejects `dynamicViewId + spatialFilters` with 400. The orchestrator already skips dv-bound layers and dv-bound widgets. Confirm via grep after the change: no `materializeFilter` call inside the orchestrator should set `spatialFilters` without verifying `spatialTarget !== undefined` (which only exists for table-bound paths).

### Pitfall 5: useMapOnlySpatialMaterialize removal breaks map-only tables

The orchestrator enumerates layers in STEP A (Phase 92). Every map-displayed table has a `DashboardLayerDto` row with a `table_id`. The orchestrator resolves `l:<layerId>` vizKeys for all table-bound layers → assigns combo hashes → fires materialize for new combos. Map-only tables (no chart widget) ARE covered via their layers.

**Exception to verify:** if a table appears ONLY in a map widget's `spatialTargets` config but has NO layer row (`DashboardLayerDto`), it would NOT be enumerated by the orchestrator. In practice this cannot happen: a layer row is always created when the operator binds a table to a map — the layer IS the binding. Confirm: `aggregateSpatialTargetsByTable` iterates `widgets` (map widget `spatialTargets` config), which is different from `layers` (the layer store rows). The hook's spatial target info comes from map widget config; the orchestrator's layer enumeration comes from the layer store. These are ALWAYS the same physical tables (because layers are always created for the map widget's data source).

### Pitfall 6: RecordsTableRenderer reads filterViewStore (not combo store)

Even after Phase 93.5, RecordsTableRenderer still reads `filterViewStore.views[tableId]` for its viewName (lines 1725-1740). The table-path spatial Effect 1 currently writes to `filterViewStore` (via `markMaterializing` + `setView`). If we gut the Effect 1 materialize call but leave the `filterViewStore` read path, the records widget will read `undefined` for `viewName` and show unfiltered data.

**Resolution:** Phase 93.5 scope is limited to removing the duplicate materialize call from the records widget. The records widget read path migration (filterViewStore → combo store) is Phase 91 scope debt. For Phase 93.5, a pragmatic approach: remove the materialize call from the records table-path Effect 1 but keep the `dropFilterView + clearView` call for the empty case. The records widget temporarily reverts to unfiltered when no combo is active — acceptable because the records widget hasn't been migrated to the combo read path yet.
