<objective>
Close the one gap the automated suite structurally cannot close.

Plan 03 proves the walk covers the EIGHT reference kinds research found. It cannot prove there is no
NINTH — the tests and the implementation share the same inventory, so a kind missing from both is
invisible to both. Research said so explicitly: *"a new chart type or a new config-panel field could
introduce a 9th reference kind — re-grep `components/charts/` before trusting this inventory."*

The cost of being wrong is asymmetric and delayed: Phase 120 builds its remapper against this
format, Phase 121 ships it, and the defect surfaces in a customer's target environment as a widget
silently rendering the wrong table. Ten minutes of operator attention now is the cheapest place to
catch it.

Output: a recorded audit result and an operator verdict. No production code.
</objective>

  <what-built>
    `GET /api/dashboards/:id/export` returns a single pretty-printed JSON file containing the
    dashboard, every widget with its full config, every map layer (style blobs intact), every
    dynamic view, the referenced table definitions (`schema`, `name`, `columns`), and the custom
    metrics those widgets reference. It carries `schemaVersion: 1` and an `exportedAt` timestamp,
    and deliberately omits access grants, column display config and materialized-view bookkeeping.

    Automated coverage already in place: all eight reference kinds asserted present from one
    kitchen-sink fixture; three seeded canaries proven absent from the raw bytes; denial and
    nonexistence proven to return byte-identical 404s; twenty mutation probes across Plans 01 and 03.

    What the automated suite CANNOT prove: that the inventory of eight is the whole inventory. The
    tests and the implementation were written from the same research. Only a real dashboard you
    built yourself can catch a ninth kind.
  </what-built>

  <how-to-verify>
    1. Start the app as you normally do and log in.

    2. Pick a dashboard you know well — ideally your most complicated one. Good candidates use a
       map with layers, a standalone Legend, a custom metric, a dynamic view, a RadioGroup, or a
       Filter Scope allow-list. If you have a dashboard with a dataset staged in the Datasets tab
       that no widget uses yet, that one is especially valuable.

    3. Note its numeric id from the URL, then fetch the export. Either paste this into the browser
       address bar while logged in:

           http://localhost:<your port>/api/dashboards/<ID>/export

       (the browser will download it), or from a terminal with your session cookie:

           curl -OJ -b "kbi_session=<your cookie>" \
             http://localhost:<your port>/api/dashboards/<ID>/export

    4. Open the downloaded file in your editor and check, against what you KNOW that dashboard
       contains:

       a. **Widgets** — does `widgets` list every visualization you see on the dashboard? Count them.
       b. **Tables** — does `tables` include every dataset the dashboard uses, INCLUDING any you
          staged in the Datasets tab but have not wired into a widget yet?
       c. **Custom metrics** — if any widget uses a custom metric, is that metric in `customMetrics`,
          with the right `label` and `expression`?
       d. **Map layers** — does `layers` list every layer, with its class-break / track styling
          (`cb_config`, `track_config`) still present?
       e. **Dynamic views** — is every saved dynamic view there, with its `template_sql`?
       f. **Nothing extra** — search the file for your own username, for any other user's name, and
          for a role name. Access grants must NOT be in there. Search for a materialized view name
          (something starting `_kbi_`). That must not be in there either.
       g. **`danglingReferences`** — is it empty? If it is not, read the entries: each one names a
          widget/layer and a reference that points at something not on this dashboard. That may be a
          genuine pre-existing broken binding in your dashboard (useful to know!) or a defect in the
          walk. Say which you think it is.
       h. **Readability** — is the file actually diffable and reviewable, per the reason we chose a
          file format in the first place? Is the suggested filename sensible?

    5. Optional but high value: repeat with a second, differently-shaped dashboard.

    Report back either "approved", or a list of anything that is missing, extra, or wrong. If
    something a widget depends on is missing from the file, that is a ninth reference kind and it
    must be fixed here — Phase 120 will build its id remapper directly on this format, and anything
    absent now becomes a silently-broken widget in a target environment later.
  </how-to-verify>

  <resume-signal>Type "approved", or list what is missing / extra / wrong.</resume-signal>
