# Phase 60.2: Radio Dashboard Control — Multi-Target Options - Context

**Gathered:** 2026-06-13
**Status:** Ready for planning
**Source:** Feasibility discussion (operator asked "how hard to have each option drive multiple targets?" → pulled forward from CTRL-V2-03)

<domain>
## Phase Boundary

**Delivers:** A single Radio Dashboard Control **option** can drive **multiple targets at once**. Today each `RadioOption` carries one `action: WidgetAction` (one target + one configPatch). This phase makes an option carry an ordered `actions: WidgetAction[]` — each an independent `{ target, configPatch }`, targets may mix widget / map-layer / dynamic-view kinds. Selecting the option applies ALL its actions as ONE control contribution; the config panel authors a per-option target LIST (add/remove a target).

**Key insight (de-risks the whole phase):** the overlay store is ALREADY multi-target. `widgetActionStore.setControlContribution(controlId, { widget:{id:patch}, layer:{id:patch}, dynamicView:{id:patch} })` keys many targets per control, and `effectiveLayers`/`effectiveWidget` already merge them. The engine/live-render/switch-replace plumbing needs NO new capability — the work is the option model, the dispatch that assembles one contribution from N actions, validation, and the authoring UI.

**Out of scope:** "dashboard-wide parameters" (the other half of CTRL-V2-03) stays v2. No new target KINDS. No new server surface. Frontend-only. The full-form layer editor itself (60.1) is reused as-is per layer target.
</domain>

<decisions>
## Implementation Decisions (LOCKED)

### Data model
- LOCKED: `RadioOption.action: WidgetAction` → `actions: WidgetAction[]` (ordered). Add a normalizer `getOptionActions(option): WidgetAction[]` = `option.actions ?? (option.action ? [option.action] : [])`.
- LOCKED: BACK-COMPAT — legacy persisted options carry `action` (singular) in the widget.config blob (DB). Read them via the normalizer (no DB migration). On SAVE, write the new `actions` array; keep reading both. Decide (planner): whether to also keep mirroring a single `action` for one-target options (not required if all readers use the normalizer — prefer NOT mirroring; normalize everywhere).

### Dispatch (the correctness-critical part)
- LOCKED: Add `applyWidgetActions(actions: WidgetAction[], lookups, controlId)` that: validates EACH action (layer → `validateLayerSnapshot`; widget/dv → `validateActionPatch`), builds ONE combined contribution `{ widget, layer, dynamicView }` from all valid actions, and calls `setControlContribution(controlId, combinedContribution)` exactly ONCE.
- LOCKED: This gives OPTION-LEVEL switch-replace for free: `setControlContribution` replaces the control's ENTIRE contribution, so switching from Option A (targets L1+W2) to Option B (targets L1) DROPS W2's overlay automatically. Do NOT loop the existing per-target-merge `applyWidgetAction` (that would strand targets the new option doesn't set — the one real bug to avoid).
- LOCKED: Per-action failures (dangling target / rejected) — collect, toast a combined message, still apply the valid ones (or planner's call: all-or-nothing vs best-effort). Default: apply valid actions, surface a toast listing any that failed (mirrors current single-action toast behavior). No partial/corrupt writes within a single action (existing guarantee).
- LOCKED: `RadioGroupRenderer` calls `applyWidgetActions(getOptionActions(option), widget.id)` on select (was `applyWidgetAction(option.action, widget.id)`). Default-on-open + selectedIndex persistence unchanged.

### Validation
- LOCKED: `validateRadioOption` loops over `getOptionActions(option)`; an option is valid iff every action is valid (+ existing empty-guard). Layer actions → `validateLayerSnapshot`; widget/dv → `validateActionPatch`. Surface per-action reasons.

### Config panel UI (the bulk of the work)
- LOCKED: Each OptionRow renders a per-option **target list**: N target editors with add/remove ("+ Add target"). Each target reuses its existing editor: layer → the full-form side-by-side `RadioLayerConfigEditor` (60.1); widget → existing widget inputs; dynamic-view → existing dv inputs. Raw-JSON "Advanced" fallback stays per target.
- LOCKED: One option may now have multiple LAYER targets → multiple full forms. UX (planner decides exact pattern, keep it usable): a target sub-list where one target's editor is expanded at a time (accordion), OR stacked. Keep the modal-widen behavior for layer editing. Single-target options must still look clean (don't force list chrome that clutters the common case).
- LOCKED: Widget/dynamic-view target authoring inputs themselves are UNCHANGED — they're just now repeatable within an option.

### Claude's Discretion
- All-or-nothing vs best-effort dispatch on mixed valid/invalid actions (recommend best-effort + toast).
- Accordion vs stacked layout for multiple targets per option; the "+ Add target" affordance placement.
- Whether to drop the legacy single `action` field on save or keep mirroring (recommend: normalize-everywhere, write `actions` only).
</decisions>

<specifics>
## Specific Ideas
- The switch-replace-drops-stale-targets test is the MOST important correctness test: select Option A (Layer 1 + Widget 2 overlays present), select Option B (Layer 1 only) → assert Widget 2's overlay is GONE and Layer 1's is B's.
- `getOptionActions` round-trip + back-compat unit tests (legacy `{action}` and new `{actions:[]}` both normalize correctly; empty → []).
- Frontend vitest 100% run FROM `packages/web` (NOT `--root` from repo root — cwd pitfall on static-assertion specs). web tsc clean. Frontend-only (server-diff guard). Watch the CbConfigForm/isValid mock infinite-render pitfall in panel specs (signal via useEffect).
- Theme/UI consistency: follow existing config-panel tokens; the "+ Add target" + remove controls mirror the existing "+ Add option" / Remove affordances in RadioGroupConfigPanel.
</specifics>
