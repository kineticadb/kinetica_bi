## Key Behaviors Delivered

### SC1: ONE setControlContribution write per applyWidgetActions call
`applyWidgetActions` builds a FRESH combined contribution object `{ widget: {}, layer: {}, dynamicView: {} }` from all valid actions, then writes `setControlContribution(controlId, combined)` exactly once (or zero times if no valid actions and no prior contribution). No per-target-merge loop.

### SC2: Switch-replace drops stale targets
Because `setControlContribution` REPLACES the control's entire contribution wholesale, switching from Option A (targeting L1 + W2) to Option B (targeting L1 only) automatically drops W2's overlay. The mandatory test (`SWITCH-REPLACE: Option A {L1+W2} then Option B {L1} → W2 overlay is GONE`) passes in `applyWidgetAction.spec.ts`.

### SC3: validateRadioOption validates EVERY action
Iterates `getOptionActions(option)`, validates each action with the correct validator (layer → `validateLayerSnapshot` denylist; widget/dv → `validateActionPatch` strict allow-list). Empty-guard: options with no actions return `{ valid: false, reasons: ["no targets..."] }`.

### SC4: Legacy single-action back-compat via getOptionActions
`getOptionActions(option)` = `option.actions ?? (option.action ? [option.action] : [])`. Options without `actions` but with the legacy `action` field normalize to a 1-element array. Both the spec and the renderer handle legacy options transparently. NO DB migration.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] validateRadioOption 2nd param back-compat for RadioGroupConfigPanel**
- **Found during:** Task 4 (web tsc gate)
- **Issue:** Changing `widgetType?: string` to `widgetTypeFor?: (id: number) => string | undefined` broke the config panel which calls `validateRadioOption(option, widgetType)` where `widgetType` is a string. The plan notes "Plan 02 (the panel) is the only production caller and is updated there" but the tsc gate caught it in plan 01.
- **Fix:** Made the 2nd param a union `string | ((id: number) => string | undefined) | undefined`. When a string is passed, it becomes a constant resolver. This is fully transparent to both callers.
- **Files modified:** packages/web/src/lib/radioGroupConfig.ts
- **Commit:** f137033

**2. [Rule 1 - Bug] RadioOption.actions required broke RadioGroupConfigPanel tsc**
- **Found during:** Task 4 (web tsc gate)
- **Issue:** Making `actions: WidgetAction[]` required meant the panel (which creates options with only `action`) had TS errors. Making `actions?: WidgetAction[]` optional and `action?: WidgetAction` optional triggered TS18048 errors on all `option.action.xxx` accesses in the panel.
- **Fix:** Both `actions` and `action` made optional in the type (getOptionActions handles runtime normalization). Added `// eslint-disable-next-line @typescript-eslint/no-non-null-assertion` + `!` assertions at panel error sites (14 sites). Panel functionality unchanged; plan 60.2-02 will replace all `option.action` accesses with the new `actions[]` model.
- **Files modified:** packages/web/src/lib/radioGroupConfig.ts, packages/web/src/components/charts/RadioGroupConfigPanel.tsx
- **Commit:** f137033
