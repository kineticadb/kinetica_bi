### Important Behavioral Notes

**`actions?` vs `actions` type:** The PLAN specified `actions: WidgetAction[]` (required) but the implementation uses `actions?: WidgetAction[]` (optional). This is a deliberate, correct back-compat decision: legacy DB blobs carry `action` (singular) not `actions`, so making `actions` optional allows the type to describe real DB blobs. The `getOptionActions` normalizer handles the `undefined` case (returns `[]`). This deviation from the type spec does not affect behavior.

**`validateRadioOption` second param:** The PLAN specified `widgetTypeFor?: (id: number) => string | undefined` as the only accepted shape. The implementation additionally accepts a `string` (normalized to a constant-resolver function) for back-compat with pre-60.2 panel callers. This is a strict superset — the function shape works identically to the spec.
