<objective>
Add the `combinationKey` field to `MaterializeFilterArgs` and branch the `inFlightMaterialize`
cache key so that multiple DISTINCT combinations for the same tableId no longer collapse into a
single in-flight promise. This is the REQUIRED first step (LOCKED decision #2): without it, the
Plan 03 orchestrator firing combo A then combo B (same tableId, different hash) would have B join
A's in-flight promise and receive A's view name.

Purpose: COMBO-V118-01 — one Kinetica view per UNIQUE combination. The network-layer dedup must
key on the combination, not just the table.
Output: `client.ts` extended (additive, backward-compatible) + a unit spec for the cache-key branch.
</objective>
