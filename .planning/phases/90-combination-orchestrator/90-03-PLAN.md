<objective>
Build `useCombinationOrchestrator`, the dashboard-level hook that is the SOLE owner of
combination-view materializations (COMBO-V118-01). On each `filterVersion` tick it enumerates
in-scope (table-bound, trigger-type) widgets, resolves each widget's filter set via
`resolveFilterSet`, hashes via `stableComboHash`, builds the unique desired registry, diffs it
against `filterCombinationStore.registry`, fires exactly ONE POST per NEW unique combination (via
the Plan 01 `combinationKey` path), ref-counts via acquire/release, DROPs combos that drop to
refCount 0, and enforces the per-table ceiling (Plan 02 env var, fallback to the all-filters view +
an "info" toast). It runs ALONGSIDE the legacy AggregatedWidgetRenderer Effect 1 (LOCKED decision
#1 — dual-trigger; combination views have a distinct `_c<hash8>` suffix so they never collide, and
NO renderer reads them yet — that is Phase 91/92).

Purpose: COMBO-V118-01 (one view per unique combination, dedup, ref-count DROP) + COMBO-V118-03
(ceiling enforcement + fallback + warning).
Output: the hook + an 11-scenario spec + the mount in DashboardsPage. Effect 1 is NOT touched.
</objective>
