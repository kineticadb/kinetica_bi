<objective>
Extend the pure view-name composer `buildFilterViewName` (lib/viewNaming.ts) with an OPTIONAL `dynamicViewId?: number`. When present, the `_t<tableId>` segment is swapped for `_dv<dynamicViewId>` so the dv-filter view name is distinct from the table-filter view AND the dv's own materialized view. When absent, output is byte-identical to today (table-path back-compat).

Purpose: This is the naming contract the Phase 62-02 route handler (and Phase 63 client, indirectly) depends on. Isolating it in a pure module with TDD locks the byte-unchanged table-path regression before any route wiring.
Output: Extended `buildFilterViewName` + unit tests proving both branches.
</objective>
