## Why this is a TWO-PASS import, not a clever ordering

The obvious design — "create tables, then layers, then widgets, remapping each reference as you go"
— **cannot work**, and it is worth being precise about why, because the reason is not the one
CONTEXT.md names.

CONTEXT.md flags REF-3 (`sourceMapWidgetId`: widget → widget) as the ordering problem. That alone
would be solvable by ordering widgets among themselves. The real problem is a **two-way cycle
spanning two different entity kinds**:

- **widget → layer**: `config.includedLayerIds` (REF-6) and `config.options[].actions[].target`
  with `kind: "layer"` (REF-8).
- **layer → widget**: `dashboard_layers.filter_scope.allowedSourceWidgetIds` (the sixth site).

No topological order satisfies both. The codebase's own write API already concedes this — read
`createDashboardLayer`'s signature in `db.ts:719`:

```ts
export const createDashboardLayer = (
  dashboardId: number,
  input: { table_id: number; layer_type?: "KineticaWms"; position?: number; config?: Record<string, unknown> }
): DashboardLayer => { /* ... */ };
```

**It accepts no `filter_scope` and no `dynamic_view_id` at all.** Only `updateDashboardLayer` can set
them. The existing API has ALREADY been forced into a two-step layer lifecycle by this same cycle.
Import reuses that shape rather than inventing a new accessor.

So: **Pass 1 creates every row with placeholders, accumulating five old→new id maps. Pass 2 runs only
once all five maps are complete, and rewrites every widget config and every layer `filter_scope`.**
REF-3 stops being a special case; it is just one more edge the second pass resolves.
</the_cycle>

<atomicity_design>
## How the mid-import failure is induced — and why this diverges from RESEARCH Q5

RESEARCH Q5 recommended a NATURAL fault: seed the target with a `(table_id, label)` pair that
collides, and let SQLite's real `UNIQUE(table_id, label)` fire when import tries to create it.

**That fault is no longer reachable**, and the reason is a feature, not a bug: Plan 120-02's
`resolveCustomMetrics` does a fresh `listCustomMetrics(newTableId)` lookup per metric and REUSES on
exact label match. Any row a test seeds out-of-band is visible to that same `SELECT`, so the import
matches it instead of colliding with it. Research designed the fault before the matching rule
existed. Say so plainly in the SUMMARY rather than pretending the recommendation was followed.

**Use a SQLite TRIGGER instead.** It is strictly better than both alternatives research considered:
it needs **zero test-only code in production** (unlike a `failAfter` seam), it is fully deterministic
(unlike a constraint race), and it can be attached to ANY table, so rollback is provable at several
points in the sequence rather than one.

```ts
db.exec(`CREATE TRIGGER kbi_test_abort_layers BEFORE INSERT ON dashboard_layers
         BEGIN SELECT RAISE(ABORT, 'induced import failure'); END;`);
try {
  expect(() => applyDashboardImport(file)).toThrow();
} finally {
  db.exec("DROP TRIGGER IF EXISTS kbi_test_abort_layers;");
}
```
The `finally` is mandatory — a leaked trigger would redden unrelated specs and get misattributed to
`TD-V16-TEST-ISOLATION`.

**The claim being proven is the STRONG one.** Attaching the trigger to `dashboard_layers` means
tables, the dashboard row, dynamic views and widgets have ALREADY been inserted inside the same
transaction when it fires. Asserting the layer insert failed proves nothing. Asserting that the
`tables` / `dashboards` / `widgets` / `dashboard_dynamic_views` row counts are **identical to their
pre-import values** proves that rollback undid work across multiple tables — which is what
DXIM-V124-09 actually requires.

**Do NOT add a `failAfter` / `__testFail` option to `applyDashboardImport`.** An acceptance criterion
below asserts zero occurrences.
</atomicity_design>

**Pass 1 — create everything, accumulating the five maps.** In this exact order:

1. **Tables.** `const t = resolveTables(file.tables);` → `maps.table = t.map`.
2. **Dashboard.** `createDashboard(file.dashboard.name, file.dashboard.description)`. Then, if
   `file.dashboard.filter_display_mode` is `"topbar"` or `"panel"`,

3. **Dynamic views.** For each: resolve `source_table_id` through `maps.table`. If unresolvable,
   SKIP the dv, push a `warnings` entry naming it, and do NOT add it to `maps.dynamicView` (widgets
   pointing at it will have that reference stripped and reported — the correct outcome). Otherwise
   `createDashboardDynamicView(newDashboardId, { source_table_id, name, template_sql, max_records, columns_json })`
   and `maps.dynamicView.set(dv.id, created.id)`.
4. **Widgets.** `createWidget(newDashboardId, { title, type, position, config: {} })`.
   **The placeholder is `{}` — never `w.config`.** Two reasons, both worth a comment:
   the real config cannot be written yet (it may reference a sibling widget or a layer that has no
   new id until step 5), and writing the ORIGINAL config would put OLD ids in the target database. If
   Pass 2 then missed that widget, those old ids would point at whatever pre-existing records happen
   to carry them — the exact silent failure this phase exists to prevent. With `{}`, a missed rewrite
   produces a visibly EMPTY widget instead of a confidently wrong one.
   `maps.widget.set(w.id, created.id)`.
5. **Layers.** Resolve `table_id` through `maps.table`; if unresolvable, SKIP the layer with a
   `warnings` entry (`dashboard_layers.table_id` is NOT NULL, so there is nothing valid to write).
   Otherwise:
   ```ts
   const created = createDashboardLayer(newDashboardId, {
     table_id: newTableId, layer_type: l.layer_type, position: l.position, config: l.config,
   });
   updateDashboardLayer(created.id, {
     dynamic_view_id: l.dynamic_view_id == null ? null : (maps.dynamicView.get(l.dynamic_view_id) ?? null),
     info_enabled: l.info_enabled, info_columns: l.info_columns, info_template: l.info_template,
     cb_config: l.cb_config, track_config: l.track_config,
   });
   ```
   `filter_scope` is deliberately NOT set here — it names widgets, and Pass 2 owns it.
   `maps.layer.set(l.id, created.id)`.
   Note the `?? null` on `dynamic_view_id` is a MAP MISS, not a fallback-to-old-id — an unresolvable
   dv binding becomes "table-bound", which is the app's existing well-defined state. This is the one
   place a `??` is correct; comment it so a reader does not mistake it for Pitfall 3.
6. **Custom metrics, LAST.** `const m = resolveCustomMetrics(file.customMetrics, maps.table);`
   → `maps.customMetric = m.map`. Metrics are deferred to the end of Pass 1 deliberately: nothing in
   steps 3-5 needs a metric id, only Pass 2 does, and putting the final creation step late maximises
   how much already-written work a mid-import failure has to roll back.

**Pass 2 — rewrite, only now that all five maps are complete.**

7. For each widget in the file (in file order):
   ```ts
   const outcome = remapWidgetConfigRefs(w.config, maps);
   updateWidget(maps.widget.get(w.id)!, { config: outcome.config });
   ```
   Accumulate `outcome.stripped` into `report.strippedReferences` tagged `from: "widget:<oldId>"`.
   If `outcome.layerFilterWidened`, push a `warnings` entry of the form
   `Widget "<title>" (file id <oldId>): every layer in its includedLayerIds was unresolvable, so the list is now EMPTY — which means ALL LAYERS. Review this widget after import.`
   Count the rewrites; after the loop, if the count does not equal the number of widgets created,
   `throw new Error("dashboardImport: pass 2 rewrote N of M widgets")`. This invariant is cheap and
   it converts a future refactor bug into a rolled-back failure instead of a silent partial import.
8. For each layer in the file with a non-null/non-undefined `filter_scope` AND a resolved new id:

   const { value, stripped } = remapFilterSelection(l.filter_scope, maps.widget);

     filter_scope: value === null ? null : JSON.stringify(value),

   on read. The type says `string | null` and lies about the read side; write side is genuinely a

Three details that will bite if skipped:

1. **`DROP TRIGGER` must be in a `finally`.** `applyDashboardImport` throws by design in these tests;
   an `expect(...).toThrow()` that leaves the trigger installed would make every subsequent spec in
   the whole run fail on an unrelated insert, and `test-gate.mjs` would re-run those files alone,
