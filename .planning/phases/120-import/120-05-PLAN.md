## Why the fixture is built the way it is — read this before writing a line of test code

A weak per-kind test looks like this and is worthless:

```ts
expect(importedBar.config.tableId).toBe(report.tablesCreated[0].newId);   // ✗ weak
```

It is worthless when the old id and the new id happen to coincide, and it is worthless as evidence
that a MISSED remapping would be caught, because a missed remapping leaves the OLD id — and if
nothing in the target carries that old id, the widget is merely broken rather than wrong, which any
test would catch. **The dangerous case is the one where the old id DOES resolve to something in the
target.** That is the case that renders confidently wrong data with no signal.

So the fixture arms the trap deliberately:

1. Seed the kitchen-sink dashboard (all eight reference kinds) exactly as
   `tests/routes.dashboard-export.spec.ts` does. **Leave it in place.**
2. `GET /api/dashboards/:id/export` → `file`.
3. Rewrite ONLY `file.tables[].schema` to `"kbi_target"`. This is the single change that makes the
   import behave like a foreign environment while staying in one database:
   - table `schema.name` no longer matches anything → tables are **created**, so `tableIdMap` is
     genuinely old→new rather than the identity map a same-database import would produce;
   - the new tables carry no custom metrics → metrics are **created**, so `metricIdMap` is genuinely
     old→new too. Without this step, REF-1, REF-4 and REF-5 would all be tested against identity
     maps and could not discriminate anything.
   - `config.tableRef` (a `"schema.name"` STRING) goes stale. It is a research-verified
     NON-reference and is not remapped — ignore it.
4. `POST /api/dashboards/import` with the modified file.

Now **every old id in the file still resolves to a real, pre-existing record** — the original
kitchen-sink dashboard's own widgets, layers, dynamic views, tables and metrics are all still there.
An import that skipped remapping entirely would produce widgets pointing at those records. Nothing
would error. The dashboard would render. And every test below would fail.

**Assert that the trap is armed.** The meta-test `IMPNEW-decoy` below checks that each old id
genuinely still resolves in the target. If it ever stops holding, every other test in this file
silently weakens, and nobody would notice. That is the single most valuable assertion in the file.

**Honest limitation, state it in the SUMMARY:** this is still one database. It proves reference
remapping, not cross-environment portability. The real cross-environment round trip is Phase 121's
operator UAT, and CONTEXT.md already says so.
</the_armed_fixture>
