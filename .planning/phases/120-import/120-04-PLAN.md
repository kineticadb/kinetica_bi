Expose the import as an endpoint, and make every way it can fail produce a message an operator can
act on.

`tests/routes.dashboard-import.spec.ts`.

<decisions>
## Route shape — Claude's Discretion, decided here

**`POST /api/dashboards/import`, JSON body, not multipart.** The envelope is already JSON; a
multipart wrapper would add a parse step and a `multer` dependency on the path for no gain, and
Phase 121's UI can `JSON.parse` the uploaded file client-side and POST it. Verified there is no
route collision: `index.ts` has `app.post("/api/dashboards")` and `app.patch/delete
("/api/dashboards/:id")` but **no `app.post("/api/dashboards/:id")`**, so the literal `import`
segment cannot be captured as an `:id` param on this verb. Mount it immediately after
`app.post("/api/dashboards", ...)` anyway — the file already puts a literal before a param at
`app.patch("/api/dashboards/:id/layers/reorder")`, so this matches house style.

**Permissions: `dashboards:create` AND `datasets:manage`. No new permission.** Verified in
`lib/permissions.ts`: `designer` holds BOTH, `admin` holds all 18 by construction, `analyst` holds
only `dashboards:view`, `user_admin` holds neither — exactly the split import needs, with zero
role-mapping changes. `requirePermission()`'s own doc comment states its element [0] `requireAuth`
is "idempotent; safe to call twice", which is precisely what makes two back-to-back spreads a real
AND-gate:
```ts
app.post(
  "/api/dashboards/import",
  ...requirePermission(PERMISSIONS.DASHBOARDS_CREATE),
  ...requirePermission(PERMISSIONS.DATASETS_MANAGE),
  handler
);
```
Adding a permission would ripple across `lib.permissions.spec.ts`, `db.rbacMigration.spec.ts`, web
`permissions`, `RolesPage.spec.tsx` count assertions and `permissionGroups` wiring. Compose, do not
add.

**No non-leak 404 here.** The five per-dashboard GETs collapse "not found" and "not permitted" into
an identical 404 so export cannot be used to enumerate dashboard ids. Import CREATES; there is no
existing id to leak. The RBAC 403 is the correct and honest answer. State this in a route comment so
a future reader does not "fix" it into a 404.

## Body size — Claude's Discretion, decided here

**Keep the global `express.json({ limit: "1mb" })` cap (`index.ts:144`). Do not raise it, do not add
a route-specific override, do not switch to multipart.**

Measured context: the operator's real Phase 119 export — 7 widgets, 4 layers, 3 tables — is **17 KB**.
The cap has roughly **60x headroom**. Raising it globally would weaken every other route's DoS
posture to solve a problem no measured artifact has.

A route-specific override would not work anyway: `app.use(express.json(...))` at line 144 runs
BEFORE the router, so it throws before any route-level middleware is reached.

**What must change is the message, not the limit.** Teach `errorMiddleware` about body-parser's two
error types so both produce something actionable.
</decisions>

```ts
  // v1.24 Phase 120 (DXIM-V124-03/10/11): dashboard import.
  //
  // Gate: dashboards:create AND datasets:manage. Both already exist — designer and admin hold both,
  // analyst and user_admin hold neither. requirePermission()'s element [0] (requireAuth) is
  // documented idempotent, which is what makes two back-to-back spreads a genuine AND-gate.
  // No new PERMISSIONS entry is added; doing so would ripple across four spec files and
  // permissionGroups wiring for no behavioural gain.
  //
  // NOTE: no non-leak 404 here. The per-dashboard GETs collapse "missing" and "denied" into one 404
  // so export cannot enumerate dashboard ids. Import CREATES — there is no existing id to leak — so
  // the RBAC 403 is the correct and honest answer. Do not "fix" this into a 404.
  app.post(
    "/api/dashboards/import",
    ...requirePermission(PERMISSIONS.DASHBOARDS_CREATE),
    ...requirePermission(PERMISSIONS.DATASETS_MANAGE),
    (req, res) => {
      // Tier 1 runs entirely in memory, BEFORE any transaction opens — which is what makes
      // DXIM-V124-11's "changes nothing" guarantee true by construction rather than by rollback.
      const result = validateImportFile(req.body);
      if (!result.ok) {
        return res.status(400).json({ error: result.rejection.message, code: result.rejection.code });
      }
      try {
        const report = applyDashboardImport(result.file);
        return res.status(201).json({ data: { ...report, preflightDangling: result.dangling } });
      } catch (err) {
        console.error(
          JSON.stringify({
            ts: new Date().toISOString(),
            level: "error",
            event: "dashboard_import_failed",
            message: err instanceof Error ? err.message : String(err),
          })
        );
        return res.status(422).json({
          error: "Import failed partway through and was rolled back. No dashboard, widgets, layers or table entries were created.",
          code: "IMPORT_FAILED",
        });
      }
    }
  );
```
