**1. `resolveWidgetTableId`** — exported, because Plan 123-04's `configPatch` blocks and Plan
123-03's layer resolution mirror it and there must be exactly one rule:

```ts
export const resolveWidgetTableId = (
  config: Record<string, unknown>,
  dynamicViews: DashboardDynamicView[],
): { tableId: number | null; tableScope: ColumnRefTableScope } => { ... };
```

Rules, in order — do not reorder:
1. If `config.dynamicViewId` is a positive integer: look it up in `dynamicViews` by `id`. Found ->
   `{ tableId: dv.source_table_id, tableScope: "scoped" }`. NOT found ->
   `{ tableId: null, tableScope: "unresolved" }` — do NOT fall back to `config.tableId`.
2. Else if `config.tableId` is a positive integer -> `{ tableId, tableScope: "scoped" }`.
3. Else -> `{ tableId: null, tableScope: "unresolved" }`.

Comment the WHY, because step 1 looks redundant: `ChartConfigPanel.tsx:1071-1084` dual-writes BOTH
`config.tableId` (= `dv.source_table_id`) AND `config.dynamicViewId` on a dv-bound widget, so the
two normally agree — they agree in every row of the dev DB today. But that equality is a save-time
convention enforced by ONE call site, not a schema-level guarantee, so the dv is the authority and
`config.tableId` is a cache. Reuse `dashboardExportRefs.ts`'s `asId` PREDICATE SHAPE (a positive
integer, never `Number()`/`parseInt`) but write it locally — do NOT import from that module; zero
diff to it is a phase success criterion.

**2. The structured-site emitter** — one file-local helper all structured sites use:

```ts
const emitStructured = (args: {
  value: unknown;               // only a non-empty string can produce a finding
  column: string;
  site: ColumnRefSite;
  path: string;
  recordKind: ColumnRefRecordKind;
  recordId: number | null;
  recordLabel: string;
  resolved: { tableId: number | null; tableScope: ColumnRefTableScope };
  query: ColumnQuery;
  emit: (ref: ColumnRef) => void;
}): void => { ... };
```

Rules:
- Skip unless `typeof value === "string"` and `value.trim() !== ""` and `column !== ""`.
- Match is `value === column` — EXACT and case-SENSITIVE. This is the same identity question
  `schemaDiff.ts` answers case-sensitively; the case-INSENSITIVE rule belongs to free-SQL text
  scanning ONLY, and unifying the two is explicitly forbidden by 123-CONTEXT.md.
- Emit only when `resolved.tableScope === "unresolved"` OR `resolved.tableId === query.tableId`.
  An `unresolved` record is ALWAYS reported: a missed finding is the expensive failure.
- `confidence: "exact"`, `matches: []`, `tableId`/`tableScope` from `resolved`.
