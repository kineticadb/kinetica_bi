  <files>.planning/phases/113-dashboard-url-sync/113-UAT.md</files>

  <what-built>
    Opening a dashboard now pushes one history entry and writes `?dashboard=<id>` into the address bar immediately. The in-app "Back to dashboards" button pops that entry (so the app's Back IS the browser's Back), and a `popstate` with no `dashboard` param returns the screen to the dashboard list. Two further paths keep the address bar honest without ever opening a dashboard from a URL: pressing browser **Forward** back into an entry already left rewrites the URL down to the list in place, and **unmounting the dashboards page** (which is what a sidebar click to another section does) clears the param — unless the session has ended, in which case the id is deliberately left for Phase 115. Nothing reads the URL on load yet — that is Phase 114.
  </what-built>

  <how-to-verify>
    Start the dev server (`npm run dev` at the repo root, plus `npm run dev:server`) and open the app in a **real browser tab that you have just opened** (so the tab's history starts clean). Then:

    1. **Address bar on open.** From the Dashboards list, click "Open" on any dashboard. The address bar must change to `…/?dashboard=<that dashboard's id>` the instant the dashboard screen appears — before its widgets have finished loading. Expected: yes, and the id matches the dashboard you opened.

       (If the param appears and then vanishes a moment later, that is the StrictMode double-invoke defeating the unmount cleanup — a real defect, not a quirk. Record it as a FAIL on this check.)

    2. **Browser Back.** With that dashboard open, press the browser's Back button. Expected: the dashboard **list** comes back on screen AND `?dashboard=…` disappears from the address bar. Both, not one.

    3. **In-app Back leaves the stack shallow.** Open the dashboard again, then click the in-app "Back to dashboards" button. Expected: you are on the list with a clean URL. Now press the browser's Back button once more. Expected: you **leave the application** (back to whatever the tab showed before, or a blank new-tab page) — you must NOT land back on the dashboard you just left. Seeing the dashboard re-open here means the in-app button pushed a second entry instead of popping the one we pushed, which is the rejected design.

    4. **Copy-paste sanity.** With a dashboard open, copy the address bar, and confirm it reads `…/?dashboard=<id>` with the numeric id — not a name or slug. (Pasting it into a new tab is expected to land on the dashboard **list** for now; opening from a URL is Phase 114. That is correct behaviour at this point, not a failure.)

    5. **Back, then physical Forward.** Open a dashboard, click the in-app "Back to dashboards" button (you are on the list, clean URL), then press the browser's **Forward** button. Expected: the address bar stays clean — **no `?dashboard=…` reappears** — and the dashboard **list** remains on screen. Watch the address bar for a full second: a param that flashes in and stays is a FAIL. Seeing `?dashboard=<id>` sitting in the address bar while you are looking at the list is precisely what DLINK-V121-07 forbids ("the URL never describes a view the user is no longer on"). Seeing the dashboard actually re-open is ALSO a FAIL, but a different one — opening from a URL is Phase 114's job and must not have leaked in here.

    6. **Sidebar navigation away.** Open a dashboard (address bar shows `?dashboard=<id>`), then click a different sidebar section — **Datasets** is the reliable one. Expected: the Datasets screen appears AND `?dashboard=…` disappears from the address bar. This is the everyday one-click flow, not an edge case: if the param lingers, copying the link at that moment shares a dashboard you are not looking at. Then click **Dashboards** in the sidebar to come back. Expected: the dashboard **list**, with a clean URL.

    Note on the no-history-to-pop case: it is fully covered by the automated test `writes the list URL when there is no history entry to pop` in `src/lib/dashboardUrl.spec.ts`, and it is not reachable by hand in a real browser until Phase 114 makes deep-link arrival possible. Do not try to reproduce it manually.

    Note on logout: the param is deliberately **preserved** if the session ends (401 / Sign out) while a dashboard is open — Phase 115 may need it to survive re-auth. Do not record that as a failure of check 6.

    Record each check's result in `.planning/phases/113-dashboard-url-sync/113-UAT.md`, one line per check, prefixed `UAT-113-1` … `UAT-113-6`.
